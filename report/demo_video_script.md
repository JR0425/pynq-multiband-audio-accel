## 演示方案（定稿 2026-10-15）

**器材**：PYNQ-Z2 板子、带麦耳机、有源音箱（已购）、公对公 3.5mm 线、笔记本（录屏 + 录声）。

**板子上只有两个 3.5mm 口**（原理图第 7 页，实测过）：

| 口 | 方向 | 接什么 |
|---|---|---|
| `HP + Mic` | **一口两用**（TRRS 四段）：出声音 + 进麦克风 | 耳机，或音箱 |
| `Line-in` | **只能输入** | 电脑（当音源） |

**关键约束：外放和拾音物理互斥。** 音箱必须插 `HP + Mic`，而插上音箱就没有麦克风了。
所以演示**不是同时接，是换插头**，分两段：

| 段 | 插法 | 演什么 | 出声 |
|---|---|---|---|
| ① 实时（说话型） | 带麦耳机 → `HP + Mic` | 对着麦说话，耳机里实时听到处理后的声音；屏幕同时刷时域/频谱 | 耳机 + 屏幕 |
| ② 对比（放音频型） | 音箱 → `HP + Mic` | 预录的 **原声 vs 处理后** A/B | 音箱 |

**三条硬要求**：

1. **对比那段必须等响度。** 只放"原声 vs 压缩后"，评委听到的是"变响了"，会归因成"调大了音量"，不是"压缩"。`fir_audio_loop.py` 存了三份：① `loop_1_录进来.wav`（原声）、② `loop_3_过核_压缩.wav`（压缩后，整体变轻）、③ `loop_5_过核_压缩_最狠.wav`（压缩后**补回等响度**）。**A/B 要比的是 ①和③**；②不算证据，它只是音量小了。这条最容易翻车，别省。
2. **耳机那段不能让"听感"只存在于一个人耳朵里。** 戴耳机的是操作的人，评委听不到。变化要靠**屏幕上的波形**和音箱那段来说。
3. **四段增益必须单段大幅改（−41.9 dB）**，别用对称的 ±6 —— 实测听不出来（见分镜 3 末尾）。

**②段怎么放**：最省事、最可控的是**笔记本直接放 wav 进音箱**，板子不参与（板子的作用①段已经证过了）。
想再展示"板子真的在中间"，就 电脑 → 公对公线 → 板子 `Line-in` → 板子 `HP + Mic` → 音箱；但这一段要现场跑，成败和①一样取决于板子当时的状态，所以**留成可选项，别当主路径**。

**现场顺序**：先做拔插仪式（实测 18 秒，拔到电平表跳起来）→ 拍①实时段（含单段 −41.9 dB 的增益示范）→ 拔耳机、换音箱 → 拍②对比段。**切换点就落在拔插上，不用另外安排。**

**提交的视频以预录为主**（可控、可重录）；①段的实时片段剪进去一小段作证即可。

```

    LIVE_EXTRA="LIVE_VOLUME=35 LIVE_SCOPE=1" sh run_live.sh 40'
```

**纵轴是钉死满量程的，不自动缩放** —— 自动缩放会把"电平变了"重新归一化掉，
看上去永远一样大。钉死才看得出"这一段被压下去了"。所以拍的时候：
滑块拉到 −41.9 dB 的那一刻，**屏幕上那一段的波形和频谱要同时塌下去**，
这就是给评委看的"信号真的在变"。

- **别用对称设置**（比如低段 +6、高段 −6）。2026-10-15 实测：增益确实生效
  （出核/进核电平比从 1.00 变成 1.23），但一升一降**总响度几乎不变**，只剩音色微变，
  人耳在说话声上听不出来。**要让人听出来，必须让单段的电平真的大幅改变。**
- **用单段大幅改变**：把一段拉到 **−41.9 dB**（`fir_live.py` 的 `GAIN_LIMIT_DB`，
  也是 Q7.8 能表示的下限，1.0 = 256），音色会有明显可辨的变化
  （低频段压掉 → 声音变"薄"；高频段压掉 → 声音变"闷"），再拉回 0 dB 复原。
  建议拍 2~3 次"压掉 → 复原"，让变化可重复。
- **拍之前同样先做拔插仪式**，全程别碰插头。
- 这一段的数字侧旁白可用 2026-10-15 那趟 66 秒的实测：
  六次改动板上全接住、逐位自检在"增益变过 8 次"下仍是 **960000/960000**、实时倍率 **1.00 倍**
  （原始输出 `data/results/fir_gain_ab_run_20261015.txt`，复现脚本
  `board/scripts/gain_ab_live.sh`）。

## 分镜 4 ｜ 数据（1:50–2:20）

**画面**：`data/results/accel_cpu_vs_fpga.md` 里那张表，或者直接把下面三行做成图。

| | 单采样耗时 | 相对 48 kHz 实时预算（20.83 µs） |
|---|---|---|
| PL 里的加速核（100 MHz，Q1.15 定点） | 实测 0.317 µs（那版 `v19`，理论 0.310 µs） | 实测 65.7 倍 |
| 板上的 ARM（float64 + scipy） | 6.199 µs | 3.36 倍 |
| **同芯片加速比** | **19.5 倍**（6.199 / 0.317，v19） | |

**旁白**：
"核跑在 100 MHz 上，板上实测每个采样 0.317 微秒，理论值是 0.310 微秒 ——
48 kHz 的实时预算是 20.83 微秒，所以核有六十几倍的实时余量，
三秒的声音，核实际计算的时间只有 0.057 秒。
Zynq 里那颗 ARM 跑纯软件的对比也在板上量了：同一套算法、同样的乘法次数，
ARM 每采样 6.199 微秒，核 0.317 微秒 —— 同一颗芯片上，**19.5 倍**。"

**这段必须带上的几条**（剪辑的时候打成小字放屏幕上，或者旁白里说）：

- **这组数是 2026-10-08 那次板上量的**，当时板上的核还是没加每段增益的 `v19`（31 拍）。
  现在出货的 [`v20_gain`](data/results/impl_metrics.md) 多了每段增益，每采样 35 拍、理论 0.350 µs，
  **没有重新和 ARM 对测过**，按拍数折算约 17 倍（折算不是实测）。**若视频里板上跑的是当前 bit，
  这句话要按这个口径说。**
- 两边精度不同：CPU 是 float64 双精度，核是 Q1.15 定点 16 位。核做的是更粗的活。
- CPU 那边用的是 scipy 的 C 实现，属于优化过的软件，不是随便写的。
- 核**没有**靠滤波器对称性少算乘法：折叠开关 `FIR_FOLD` 是关着的，
  核和 CPU 两边都是 579 次有效乘法（旧版"核只算 291 次、少做一半"的说法已作废）。
- 核的 0.317 µs 里含每块约 52 µs 的 Python 开销（写寄存器 + cache 维护 + 轮询 DONE），
  占 8000 点长块实测的约 2%。纯硬件那一段是 0.310 µs。
- 反过来说也要讲：CPU 那边不是极限，手写 NEON 还能更快，
  所以这 19.5 倍是"相对 scipy 参考实现"，**不能说成"FPGA 比 CPU 快 19.5 倍"**。

**别拿桌面电脑的数字来比**。桌面上是 0.140 µs/采样，和板载 100 MHz 的核（理论 0.31~0.35 µs）
不是一回事 —— 一个 3 GHz 的 x86 扛 SIMD，一个 100 MHz 的 FPGA，放一起相除没有意义。

**如果时间还够，可以再加一句**（这条其实比数字本身更有信息量）：

"这个核现在每采样 35 个时钟周期。它原来要 450 个周期，其中 398 个（88%）
纯粹花在把延迟线整体挪一格这种搬运上，真正算乘法只占 11 个周期。
后来我们只是换了个编译开关（`-DFIR_SHIFT_CHAIN=1`，把值串在标量临时变量上、展成寄存器链），
算法一个字没改，拍数就从 450 掉到几十 —— 改的是一个开关，不是电路。
（换开关那一步到的是 31 拍，现在的 35 拍是又加上了每段增益。）"

  如果只能录屏幕，就把四个 wav 的声音单独录一轨，剪辑时合并。

  压缩前后听不出差别。

  这个无所谓，是本地地址。
