# 2026-10-23 36 拍核的验收:延迟一点没降,演示档却从 31.0 ms 换成了 16.2 ms

> 结论先写:核从 49 拍降到 36 拍,**三档延迟和改之前逐档相同**(差 ≤0.04 ms)。
> 提速只体现在 CPU 余量上 —— dsp 线程每块占预算的 13~18%。
> 600 秒长跑两档都是 0 丢块。演示默认档换成 L=360 / NBUF=2,嘴到耳 **16.2 ms**。
> 换它的理由不是「更快能被听出来」,恰恰相反:两档听众都听不出差别,
> 换的原因是演示的核心动作是自听。

【任务】

核从 49 拍压到 36 拍这件事本身写在 `2026-10-22_drc_loop_ii.md`。
今天的活是**验收**:三档延迟复测、确认声学段还能不能沿用、按演示同配置跑 600 秒,
然后决定演示默认用哪一档。

【提示词】

- 【之前不是测过耳机的延迟了吗,不能直接用吗】
- 【开始测600ms吧】
- 【这个低延迟档是多少ms】
- 【所以演示版本改成这个16.2ms的版本没有任何问题吗】
- 【所以还是31ms的演示效果最好吗】
- 【那使用16.2版本,我最想演示的就是实时功能。……我怎么才能展示实时功能呢,就是能录下我实时说话的产出。】

【模型回答】

**第一轮:三档数字延迟。** 改 `perf_probe.py` 的配置表,把 10-22 那四档
(含不可用的 L=240 / 120)换成出货的三档,每档 20 秒、`LIVE_SRC=wav`,与 10-22 同口径。
测前按 10-22 的教训先停网页服务。

| 档位 | L | NBUF | 10-22(49 拍) | 10-23(36 拍) |
|---|---|---|---|---|
| 稳定 | 480 | 3 | 29.80 ms | **29.80 ms** |
| 中间 | 480 | 2 | 19.86 ms | **19.86 ms** |
| 低延迟 | 360 | 2 | 14.96 ms | **14.92 ms** |

三档自检都通过(960000 / 960000 逐位相同)。

数字延迟由 `NBUF × L / 48000` 决定,卡在块缓冲这一层。核每采样快 13 拍,
一块 480 采样省 62.4 µs,摊到 10 ms 的块上不到 1%;而且交块时刻由队列按块长
节拍定,不是算完就交。**16.7× 和「延迟更低」是两件事,不能捆在一起说。**

**第二轮:声学段沿用。** 一开始我说「声学法要等你在,耳机贴话筒那一步」,
理由是 PLAN 里的待办。被问「之前不是测过耳机的延迟了吗」之后核对原始记录:
`R = 1.23 ms` 量的是 DAC → 耳机 → 空气 → 话筒 → 抗混叠 → ADC,这次改的 49 → 36 拍
落在 ADC 缓冲与 DAC 缓冲**之间**,模拟端一个零件没换。10-22 那次三档满量程
(1% / 3% / 10%)互相关主峰落在同一个采样(第 59 个)、主峰/次峰约 5.8,证据够硬。

| 配置 | 数字延迟 | + R | 嘴 → 耳 |
|---|---|---|---|
| L=480, NBUF=3 | 29.80 ms | 1.23 ms | **31.0 ms** |
| L=480, NBUF=2 | 19.86 ms | 1.23 ms | **21.1 ms** |
| L=360, NBUF=2 | 14.92 ms | 1.23 ms | **16.2 ms** |

边界的算法:就算退一步假设 FIR 核也在声学回环里,13 拍 @100 MHz = 0.13 µs,
而 48 kHz 一个采样 20.8 µs,只占 0.6%,远小于互相关能分辨的一个采样。

**第三轮:两趟 600 秒。** 演示同配置 —— 网页和服务开着、headless Chrome 真实拉页面、
麦克风源,每臂起跑对齐到板子 `uptime % 30`。

| 项 | L=480 / NBUF=3 | L=360 / NBUF=2 |
|---|---|---|
| 处理块数 | 60192 | 80103 |
| **丢块** | **0** | **0** |
| 最大块间空档 | 3.683 ms | 3.846 ms |
| dsp 线程 p90 | 1.33 ms | 1.27 ms |
| 自检 | 960000/960000 | 960120/960120 |

两块读数当场说明:缺口 −182.4 ms/60 s 是负数,表示板子按 I2S 时钟采出来的音频
比主机墙钟略快,不是欠账;低延迟档那两个 `lost: 1` 事件出现在起跑 2.8 s 和 7.2 s,
是瞬时积压,整趟 `lost_total = 0`。

**第四轮:演示档。** 第一版建议是「换成 16.2,再留一条回退命令」,理由是余量够、
数字更接近助听器的临床参考线。被问「还是 31 ms 的演示效果最好吗」之后重算:
15 ms 的差在放音乐、听外放、A/B 对比频段增益这些场景里听不出来,
唯一能感觉到的是**自己戴耳机听自己说话**。而代价是块间余量从 3.68/10 ms(37%)
压到 3.85/7.49 ms(51%),离已知会丢块的 L=300 只差 60 个采样(1.25 ms)。

所以建议改成「默认保持 31.0,低延迟做成可切换」。**最后是用户定的:本次演示的核心
动作就是自听**,16.2 的体验优势在这个场景里是真的,那就值得换,回退路线照样留。

【哪里错了】

**AI 的问题:照着待办清单念,没确认前提还在不在。**
「声学法要等你在」这句话是从 PLAN 抄下来的,那句写于核改成 36 拍之前。
一句追问就把这条推翻了。**待办清单记录的是当时的事实,不是现在的事实。**
这和「报『还没做 / 要重测』之前先翻自己的记录」是同一个毛病的两面。

**AI 的问题:演示档的第一版建议只算了收益,没把代价折成同一个单位。**
「换过去数字更好看」是真的,但当时没算余量:3.68 → 3.85 ms 的最大停顿在两档
占块预算的比例从 37% 涨到 51%,而且离已知失败的配置从 240 采样缩到 60 采样。
用户一问「还是 31 ms 最好吗」,这笔账才翻出来。**建议里如果只有一个收益
(数字好看),先把代价折算成同一把尺子再比。**

**AI 的问题:接口能力没查手册就下了结论。**
讨论演示接法时我说 Line-in「只认三段式插头」。被要求去翻板子手册之后才纠正:
那口只接了左、右、地三根线,第 4 段(话筒)根本没有通路 —— 三段四段都一样;
而且没有偏置、没有话放,驻极体麦接上去也听不见。
**同一天更早那条「买分线器」的建议也一并作废**:分线器把话筒拆到一根三段插头上,
板子那颗 U41 只在插入沿检测,认不出有话筒。

**AI 的问题:转接线的公母方向写反了。**
二合一的方向是「两个三段母 → 一个四段公」,插板子那头是公头。
我那张对照表把两种线写拧了,用户按实际接法反问才发现。
判别只需要看商品图:**一公两母 = 对,一母两公 = 买反了。**

**环境的坑:耳机没插到底。**
用户发来一段 2.78 秒的录音问「核或程序是不是坏了」。数字很清楚:峰值 32768,
26% 的采样卡在满幅,RMS −2.5 dBFS,基频 55.7 Hz 带一整串谐波,不说话也一直在响。
我按「输入悬空」和「声反馈」两个方向分析了一圈,最后发现是**插头半插** ——
话筒触点接触不良,高增益输入悬空,拾到了那团嗡声。
**先问一句「插到底了吗」,比先看频谱便宜。**

【沉淀】

1. **加速比和延迟是两条线。** 核算得快,只影响吞吐和 CPU 余量;延迟由块缓冲层数决定。
   验收一个「更快」的改动,要报的是三样:延迟(应该不变)、余量(应该变宽)、
   稳定性(不能变差)。
2. **改完再测一次「和改之前一样」,是有效的结论,不是没测出来。**
   它的价值在于把「快 = 延迟低」这个默认联想切断。
3. **建议里只有一个收益时,先把代价折算成同一个单位。** 数字好看 vs 余量从 37%
   压到 51%,这两者只有在同一把尺子上才能比。
4. **产品手册里的接口能力,以手册和实测为准,不以常识为准。** 3.5 mm 口接法有
   TRS / TRRS、CTIA / OMTP 几种,名字相近,方向还相反。

## 验证边界

- 三档延迟各 20 秒,`LIVE_SRC=wav`;没有更长窗口。
- 600 秒两趟是演示同配置(网页 + 服务 + 麦克风源),各跑一次。
- `R = 1.23 ms` 沿用 10-22 的实测,当天**没有**重测;模拟段未改动是沿用的前提。
- 「16.2 ms 档 600 秒 0 丢块」是当天凌晨的结论。**当天深夜同一档 41 秒丢了 4 块,
  31.0 ms 档 60 秒也丢了 5 块** —— 两档在同一个晚上同时丢,和上午的长跑矛盾。
  这一条当天没查清,第二天才定案,见 `2026-10-24_dropout_was_the_probe.md`。
