# 2026-10-24 丢块是探针自己造成的:同一档位,开着插桩丢 19 块,关掉丢 0 块

> 结论先写:**10-23 深夜那几块丢块不是核、不是调度,是探针的插桩。**
> `drop_probe.py` 每块多做 3 次 `perf_counter()`、1 次 `time.time()`、2 次 list 追加,
> 让块周期从 7.483 ms 涨到 7.505 ms —— 每块 15~25 µs。
> 16.2 ms 档每块的全部余量也就十几微秒,正好被压过线。
> 关掉插桩:600 秒、80188 块、**0 丢块**。演示档维持 16.2 ms。
>
> 附带定案:**跑测期间从主机 SSH 进板子也会丢块**(5 分钟积累 58 ms 缺口)。

【任务】

10-23 深夜 16.2 ms 档 41 秒丢了 4 块而且还在涨,31.0 ms 档 60 秒丢了 5 块。
但同一天上午按演示同配置跑的 600 秒两趟,两档都是 0 丢块。
同一个位流、同一台板子、同一份 `fir_live.py`,白天不丢、晚上丢。
判据:16.2 ms 档 60 秒 0 丢块;做不到就退回 31.0 ms 档。

【提示词】

 【16.2 档 41 秒丢了 4 块，还在涨；31 档 60 秒丢 5 块。但同一天上午按演示配置跑 600 秒，两趟都是 0 丢块。
   同一个位流、同一台板子、同一份 fir_live.py，白天不丢晚上丢。 查清楚是回归还是别的原因】

【模型回答】

**第一步:把「改了什么」和「没改什么」分开。** 白天到晚上之间,位流没换、
`fir_live.py` 的 md5 没换、网页服务没换配置。唯一确定变了的,是晚上**用探针
`drop_probe.py` 跑的那几趟** —— 它默认给子进程打开 `DROP_TRACE` 和 `GAP_TRACE`。

**第二步:同一个配置,只换插桩,跑对照。** 每臂 60 秒,起跑对齐 `uptime % 30`。

| 臂 | 插桩 | 网页 | 块数 | 每块周期 | 缺口 ms/60 s | 末态 lost |
|---|---|---|---|---|---|---|
| ctl16_nopage | 开 | 关 | 8013 | 7.5041 ms | **+126.2** | 19 |
| page16_trace_repeat | 开 | 开 | 8009 | 7.5066 ms | **+142.2** | 20 |
| ctl16_notrace | 关 | 关 | 8008 | 7.4925 ms | −26.0 | **0** |
| page16_notrace | 关 | 开 | 8023 | 7.4872 ms | −38.5 | **0** |

网页开关几乎没影响(两次复现都是);插桩一开就丢,一关就 0。

**第三步:加长跑。** 关插桩、网页开着:180 秒 24027 块 0 丢块;
600 秒 80188 块 0 丢块,缺口 −135.2 ms/60 s。中间还有一趟 300 秒的
(`demo16_300`)积压了 9 块 —— 那一趟是因为跑的过程中从主机 SSH 进板子查了
`df`、`ps`、读状态文件。同一时长、同一页面、不去碰它,复跑 0 块。

**第四步:算插桩的价。** 开关两组的块周期差 0.25~0.30%,60 秒折 150~180 ms,
约 20 块。花在哪:两个 list 各长到八千条,分配和 GC 都落在搬样线程上;
而 `duplex_block` 每块要 7.404 ms、块周期 7.49 ms,**留给 Python 的只有几百微秒**。
块长 10 ms 那档同样开着插桩跑 600 秒是 0 块 —— 块越长,同样的开销占比越小。

【哪里错了】

**AI 的问题:把「600 秒 0 丢块」当成了配置的属性,没记录那趟是开着插桩的。**
10-23 凌晨那趟 16.2 ms 长跑的**插桩也是开着的**,而且恰好比今天快了 14 µs/块
(7.4904 vs 7.504/7.483),于是没丢。我拿着这个结果说「演示档稳」,
却从没把测量工具本身的开销算进块预算。
**同一个配置在不同起跑状态下的余量会差十几微秒 —— 而这档的余量就是十几微秒。**

**AI 的问题:把 `lost_blocks` 读成了累计数。**
`events` 里有 33 条 `delta: 1`,末态却只有 19,我一度当成日志写错了。
实际定义是 `int(max(0, 墙钟 − n × 块长) / 块长)` —— **瞬时积压**,
积压追平就归零,所以它会涨也会落。判据只有两个:`缺口 ms/60 s` 和 `lost_total`。

**AI 的问题:缺口是负数被当成欠账。**
−182.4 ms/60 s 的意思是板子按 I2S 时钟采出来的音频比主机墙钟**略快**
(60192 × 480 / 48000 = 601.92 s 音频 / 600.02 s 墙钟),是两边晶振的相对偏差。
**在这个口径下,负数是更健康的那一边。**

**AI 的问题:一边跑一边从主机 SSH 进板子查状态,自己制造了丢块。**
`demo16_300` 那趟 5 分钟积累 58 ms 缺口(0.02%),末态积压 9 块。
差一点就把这次自己造成的积压,当成「丢块复现了」。
**测量动作本身必须在被测系统的账上。**

**环境的坑:片上 `python3` 不是 PYNQ 那个环境。**
后台起任务必须走 `/usr/local/share/pynq-venv/bin/python3` 加
`XILINX_XRT=/usr`,写成 `sudo env ... /usr/local/.../python3`。
漏了就是一句 `ModuleNotFoundError: No module named 'pynq'`,而且报错落在后台日志里。

**环境的坑:探针在第一个采样周期会崩。**
线程表和进程族在同一循环里第一次被发现时 `dt_s` 是 0,`pct()` 除零。
改成 `now > th_prev_t` 才做除法。

【怎么修正】

1. `drop_probe.py` 加 `--no-trace`:**短配置一律用它**,不给子进程开
   `DROP_TRACE` / `GAP_TRACE`。
2. 补两处除零保护。
3. 演示和跑测的规矩写进 `demo_video_script.md` 和 `live_dropout_recheck_20261024.md`:
   **跑起来之后不要从主机 SSH 进板子**;页面自己 150/250 ms 拉一次状态不算,
   Jupyter 在 CPU1 上也不碍事(CPU1 只用 64%)。要查就等跑完。
4. 判据统一成 `缺口 ms/60 s` + `lost_total`,不再看 `events` 条数。

【沉淀】

1. **测量工具要计入被测量的预算。** 余量只剩十几微秒时,先做「插桩开 / 关」
   这一组对照,再谈其他变量 —— 否则所有参数实验都是在测探针。
2. **「同样的配置昨天不丢」不是反证。** 先确认两次的起跑状态和观测手段一样;
   这一档的余量在十微秒量级,快慢由起跑时的状态决定。
3. **瞬时值和累计值要分清。** `lost_blocks` 会回落,`lost_total` 只增不减;
   一个会回落的数不能拿来当「丢了几个」。
4. **缺口是负数时,先看口径再判断。** 时钟偏差、块长换算、采样率,三样都可能让它变号。

## 验证边界

- 每臂 60 秒,长跑 180 / 300 / 600 秒;全部 `LIVE_SRC=wav` 或默认麦克风源,
  网页开着、服务开着,条件与演示同配置。
- 16.2 ms 档 600 秒只跑了**一趟**;同一档在 300 秒那趟出现过 9 块积压,
  归因于跑测期间的主机 SSH,没有单独做「SSH 开 / 关」的计数对照。
- 插桩代价是用块周期差估的(0.25~0.30%),没有直接测 `perf_counter()` 本身的开销。
- 当天没有重跑 49 拍那版核做对照;结论成立的前提是位流与 `fir_live.py` 的 md5
  在整个对照期间没有变过(每臂跑前都核过)。
