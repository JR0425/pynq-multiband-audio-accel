# 2026-10-22 每采样 49 拍压到 18~71:一个猜错的机制、贴错的 pragma,和一次被自己的重构拖慢

> 结论先写:**II=4 的原因不是乘法器不够,是 `env` 数组的假携带依赖。**
> 显式展开四段之后,DRC 那一圈消失了,整核从 49 拍掉到 **19~33**(函数写法)
> 或 **18~71**(宏写法)。**但没有一版能直接出货**:
> 函数写法要 **215/220 个 DSP**,宏写法的最坏路径 **71 拍比原来的 49 还慢**。
> 另外两条教训是这一次真正的收获:
> **`#pragma HLS UNROLL` 贴错了两次循环,而且不报错**;
> **把这段抽成 `static inline` 函数、逻辑一字没改,II 从 4 被推到 14。**

【任务】

出货核 `v21_wdrc` 每采样 49 拍,csynth 里能看出还有一处没榨干:

```
VITIS_LOOP_425_6   三路低通      11 拍
VITIS_LOOP_517_11  四段压缩+WDRC 30 拍, iteration latency 17, II=4, trip 4
```

那一圈目标是 II=1、实际是 4。压到 1 的话整核约 36 拍,加速比 12.5 × → 17 ×。
任务就是搞清 II=4 是"依赖"还是"资源",以及值不值得改。

【提示词】

【这一圈 II=4 的根因,到底是「依赖」(如 `env` 数组上的假携带依赖)还是「资源」(如 DSP 不够)?】
【如果值得改,给出具体改法和预期收益,并说清风险(DSP 占用会不会顶到 220、最坏路径拍数会怎样】

【模型回答】

**第一轮,先给机制(错的)。** 我说 II=4 最可能是**乘法器分配不足**:
DSP 已经用了 200/220,四段并行要做 16 个乘法实例,HLS 只能复用。
顺着这个机制,建议"加 UNROLL、看能不能挤出并行度,不够就限流"。

**第二轮,读 csynth 日志。** 日志里已经写清楚了,而我第一轮没去读:

```
WARNING: [HLS 200-880] ... 'atenv_V_0_write' ... 'env_V_0_load' ... distance = 1
```

也就是 `static drc_t env[N_BANDS]` 上的**假携带依赖**:循环里 `i` 是变量下标,
不展开的话 HLS 证明不了"第 i+1 次写"不会碰到"第 i 次读"的那一格,
于是保守地给出一条 distance=1 的依赖,把这一圈钉在 II=4。
**和乘法器数量无关。**

**第三轮,两个 pragma 都贴错。** `factor=4` 贴在那一圈上,综合结果和基线**逐项相同**
(49 拍、II=4、200 DSP)—— 说明它根本没起作用;
换成 `factor=2`,结果变成 **141 拍、392 DSP、FF 24560**,整个 FIR 被复制了两遍 ——
它展开的是**外层采样循环**,不是目标那一圈。

**第四轮,改成显式展开。** 先用"抽函数"的办法减少重复,结果见下。

【哪里错了】

**AI 的问题:先给机制,后读日志。**
HLS 200-880 那条警告一直在 csynth 日志里,第一句话之前就能看到。
我却先凭"资源紧张"这个印象编了一个机制,再拿它安排实验。
**"资源不够"和"有假依赖"这两类问题,在 HLS 里的表现是一样的(都是 II 达标不了),
但验证方式完全相反**:前者加资源会变好,后者加资源一点不变。
分不清的时候,正确动作是**先去读 warning 和 dependence 那一段**,不是先加 pragma。

**AI 的问题:pragma 贴错循环,两次。**
`#pragma HLS UNROLL` 是贴在**紧跟着的那一个循环**上的。
我把它贴在四段循环里面,实际作用在它外层的结构上;
`factor=2` 那次甚至展开的是 `for (n = 0; n < length; n++)` —— 那是采样循环,
展开等于把整个 FIR 复制两份。**这个错不报错,只表现为"pareto 变差"**,
只有对着 `VITIS_LOOP_<行号>_<序号>` 逐个核才能发现。

**AI 的问题:把代码抽成 `static inline` 函数,逻辑一字没改,却慢了 40%。**
为了在"展开"和"不展开"两条路之间共用代码,我把单段处理抽成了

```c
static inline drc_t band_proc(acc_t bandv, gain_t g, ...)
```

并且声明"默认路径行为逐位不变"。**综合结果否掉了这个声明:**

| 标签 | 做法 | 拍/采样 | II | DSP | FF | LUT |
|---|---|---|---|---|---|---|
| `v21_wdrc` | 出货版,循环内联 | **49** | 4 | 200 | 14985 | 11370 |
| `v23_drc_u0` | 同一段抽成 `static inline` 函数,默认走循环 | **88**（合段循环 69） | **14** | 200 | 15989 | 11498 |

> **2026-10-23 补**:这一行当时抄的是合段循环的延迟 69,不是整核 88,差了 19 拍 ——
> 后面"49 → 69"这种说法都偏高估。同一个报告里 `VITIS_LOOP_390_4` 那行(前面是 `-`)
> 才是整核的拍数,`+` 开头的只是它里面那一圈。详见 `data/results/impl_metrics.md`
> 同一处的更正。

日志里多出一个 `grp_band_proc_fu_3656`:延迟 12、II=1 —— **它没有被内联**,
变成了每圈调一次的共享单元。
**"结构上等价"在 HLS 里不等于"综合结果等价",而"逐位不变"只保证了数值,没保证拍数。**
更糟的是,如果没跑这一版,出货基线和"对照"两个东西会同时失效,后面的数全不可信。


**环境的坑:Vitis HLS 2020.2 每次综合约 2 分钟,但两个变体串行才能比较。**
并行跑会抢 CPU,而且`run_synth.tcl` 的 `HLS_LABEL` 决定输出目录,
两个标签并行本身没问题,但机器只有两三个核,综合时间会互相拖长。
**比较实验就串行跑,别为了省时间把两个变体搅在一起。**

【怎么修正】

1. **默认分支改回 v21 原文**,不再共用代码。展开分支单独用一个宏:

   ```c
   #define BAND_STEP(i) do { ... } while (0)   /* 文本替换,一定内联 */
   ```

   展开路径给字面量下标 `BAND_STEP(0..3)` —— 字面量才能让 HLS 看出四次写入
   落在不同的 `env` 元素上,假依赖自然消失。
2. 用 `FIR_DRC_UNROLL` 编译开关切换,默认 0 = v21 原文。
3. 重新综合两版做对照,结果如下 —— **默认路径确实修回来了**:

   | 标签 | 拍/采样 | II | DSP | FF | LUT |
   |---|---|---|---|---|---|
   | `v24_drc_u0`(默认) | **49** | 4 | 200 | 14985 | 11370 |
   | `v24_drc_u1`(宏展开) | **18~71** | — | 203 | 14442 | 12021 |

   默认那行和 `v21_wdrc` **逐项相同**(49 / 200 / 14985 / 11370) ——
   `FIR_DRC_UNROLL=0` 现在真的等于出货版。
4. 但展开那一版**两种写法都不理想**:

   | 写法 | 拍/采样 | DSP |
   |---|---|---|
   | 函数(`v23_drc_u1`) | 19~33 | **215** |
   | 宏(`v24_drc_u1`) | **18~71** | **203** |

   - 函数写法:最坏 33 拍比原来好,但 DSP 215 折到整机就贴着 220,
     大概率塞不进或者把 +0.251 ns 的时序余量吃光。
   - 宏写法:DSP 和面积反而降了(203 / 14442 / 12021),但**最坏 71 拍比原来的 49 还差**。
     宏展开出 16 份乘法实例之后,HLS 在 `drc` / `wdrc` 两条分支之间复用了它们,
     把分支路径拉长了。

   **结论:拍数和 DSP 这两关,目前没有一版同时过。** 这一项能不能出货,
   10/23 要单独决定(试实现 / 改结构 / 放弃),不能当成"已经做完了"。

【沉淀】

1. **HLS 里"II 达不到目标"有两类原因,先读 dependence 段再动手。**
   日志里 `carried dependence ... distance = 1` 出现 = 假依赖,加资源不会变;
   只有"资源"类才会因为加 DSP 变快。
2. **`#pragma HLS UNROLL` 作用在紧跟其后的那个循环上,并且错的循环不报错。**
   验证方法只有一条:看 `VITIS_LOOP_<行号>_<序号>` 的拍数变没变。
3. **在 HLS 里,"把代码抽成函数"是一个会改变综合结果的改动,不是重构。**
   `static inline` 不保证内联;要用就显式加 `#pragma HLS INLINE`,或者直接写宏。
4. **改任何性能相关代码之前,先重跑一次基线。** 不是为了防止"改坏",
   而是因为一旦中间版本被误当成基线,后面所有"提升多少"都会算错,
   而且这种错不会报错,只会让数字虚高。

## 验证边界

- 这里的拍数是 **csynth 调度估算**,不是布局布线后的实测;
  真正能报的拍数要等实现和上板。
- `v23_drc_u0` 是**中间版本**,不会出货;它的价值是证明"抽函数会改调度"这件事。
- `v24_drc_u0` / `v24_drc_u1` 是修好之后的对照:`u0` 与 `v21_wdrc` 逐项相同,
  `u1` 是宏写法。**两版都还没做布局布线和上板**,DSP 能不能放进 220 要等实现报告。
- 区间下限/上限分别对应不启用 WDRC(`attack=release=0`,走 `drc`)和启用(走 `wdrc`);
  两个分支的电路长度不同,所以 csynth 给的是区间而不是单值。
- DSP 是 **csynth 估算**,整机还要叠加音频 IP 和互连(v21 的 200 在整机里是 205)。
