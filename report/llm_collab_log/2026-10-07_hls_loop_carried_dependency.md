【任务】

上一轮量出来一个对不上的数：综合报告里每个采样 **449 拍**，上板实测 **4.6 µs**
（10 ns 约束 = 100 MHz，449 拍本来就该是 4.49 µs，两边是自洽的）。
所以问题不是"实测比报告慢"，是**449 拍本身就太多**——48 kHz 下每个采样有
20.83 µs 的预算，4.6 µs 只剩 4.6 倍余量。这一轮要把这 449 拍拆开、压下去，
再上板复量。

要的是一个**能站住的数**，不是"感觉快了不少"。

【提示词】

「综合报告说每个采样 449 拍，占掉预算的 22%。这 449 拍到底花在哪，能不能压下来？」

【模型回答】

AI 头两轮给的方向都不对，而且都被后面的数据否掉了，记在这里：

- **加 `#pragma HLS PIPELINE` 把外循环流水化。** 理由是"拍数多 = 流水线不够"。
  实测加完**纹丝不动**：只加 PIPELINE 那一版（`t6_pipe_nofull`）还是 **449 拍**，
  两份综合报告逐行 diff 只差日期和行号。官方文档那句"外层加了 PIPELINE，
  编译器会自动展开移位循环"**在我们这份代码上不复现**。
- **限乘法器数量、或者把时钟降下来。** 这是更早一轮试过的路（`v15`，限到 64 个
  乘法器），结果是 LUT 从 3962 涨到 10443 才勉强在 80 MHz 过时序——**方向相反**，
  更慢更贵。

真正有用的信息在 `csynth` 报告的**循环表**里，AI 是在被叫去看那张表之后才找对的。

【哪里错了】

· **AI 的问题：把"拍数多"默认成"流水线不深"，先想到加 PIPELINE 指令。**

  实测加了没用（449 → 449）。原因看循环表就明白：

  | 循环 | 干的事 | 迭代 | II | 延迟 |
  |---|---|---|---|---|
  | `VITIS_LOOP_312_4` | 延迟线整体移位 `hist[k]=hist[k-1]` | 194 | **2** | **398** |
  | `VITIS_LOOP_324_5` | 乘加那几个 | 10 | 1 | 11 |
  | `VITIS_LOOP_270_3` | 每采样一遍（外层） | — | — | **449** |

  **88%（398/449）的拍数花在"把延迟线整体挪一格"这个纯搬运上，真正的乘法只占 11 拍。**
  202 个 DSP 铺在片子上，97% 的时间是空着的——它根本不缺算力，它在搬东西。

  给一个搬运循环加流水线指令，等于给一条已经开到最快的传送带再加一节，
  瓶颈不在那儿。（把 `hist` **完全拆进寄存器**确实有改善——224 拍，见下表——
  但那也只是把 398 拍换成 195 拍，量级没变。）

· **AI 的问题：第一反应是"换环形缓冲区"，那是 C 层的大改。**

  环形缓冲（读下标跟着转、每采样零搬运）是这个问题的标准解法，方向没错。
  但它要改数据结构、改三个低通的取值方式，改完**整套数值要重验一遍**——
  而这个设计的数值对齐是花了好几天钉住的。

  真正需要的只是**换一种写法，让编译器自己把它展开成移位寄存器**：

      hist[k] = hist[k-1]                       ← 有环依赖（距离 1）

  这行的依赖距离是 1，C 语义要求严格按顺序执行，所以编译器**必须拒绝展开**
  （日志里那句 `II Violation ... carried dependence constraint`）。
  它只能一拍一格地跑：194 次移位 = 194 拍。

  改成把值串在一根**标量临时变量**上，语义完全一样（`hist[k]` 一律取旧的
  `hist[k-1]`），但依赖只落在那个标量上，展平之后就是**一根根的线**，
  零逻辑、零拍数：

      data_t prev = samp_in(in[n]);
      for (int k = 0; k < N_TAPS_ALLOC; k++) {
          data_t old = hist[k];
          hist[k] = prev;
          prev = old;
      }

  **改的是一个开关，不是电路。**

· **环境的坑：新 bit 传上板这一步——脚本传上去了、bit 忘了传。**

  第一次上板跑出来的是 10-01 17:30:56 的那份旧 bit，而**六项功能自检一项都
  分辨不出来**：这一版改的是结构、算法一个字没动，csim 输出两边 `cmp -s`
  逐字节相同。所以"功能全过"这句话在这里**不构成"新 bit 上板了"的证据**。

  分开新旧只能读 `.bit` 文件头里 Vivado 自己写进去的构建日期：

      a  fir_wrapper;UserID=0XFFFFFFFF;Version=2020.2
      b  7z020clg400
      c  2026/10/07      d  19:59:48        ← 电脑上这份
      板上那份是 2026/10/01  17:30:56

  文件名和时间戳都靠不住——这次就是因为只比了文件名，两边都叫 `fir.bit`。

【怎么修正】

在 `src/hls/fir_multiband.cpp` 里加一个编译开关 `FIR_SHIFT_CHAIN`
（**默认 0，所以默认路径和改之前逐字节相同**），1 的时候走上面那种串接写法。

前提是延迟线必须全在寄存器里（配 `-DFIR_HIST_FULL`），否则展出来的"线"还是
落回 BRAM 上，等于没改。

整条路径上每一版都走了同一套流程（同脚本、同努力度、OOC、100 MHz），
逐版对照在 `build/hls/reports/`：

| 版本 | 改了什么 | 拍/采样 | LUT | FF |
|---|---|---|---|---|
| `t0_ctrl` / `t0b_recheck` | 原样 | 449 | 9246 | 12916 |
| `t2_cyc13` | `hist` 循环拆 13 路 | 437 | 9324 | 12891 |
| `t6_pipe_nofull` | **只加外循环 PIPELINE 指令** | **449** | 9246 | 12916 |
| `t1_histfull` | `hist` 完全拆分进寄存器 | 224 | 9715 | 12480 |
| `t5_pipe_histfull` | 完全拆分 + PIPELINE 指令 | 224 | 9715 | 12480 |
| **`t4_shift_cyc5`** | **只加 `-DFIR_SHIFT_CHAIN=1`** | **28** | **8619** | **12454** |
| **`t3_shiftchain`** | 完全拆分 + 移位改写 | **28** | **8619** | **12454** |

三个值得记的点：

- **`t4` 和 `t3` 逐位相同** —— 说明最小改动就是那**一个编译开关**，
  `ARRAY_PARTITION complete` 是多余的。**"改的是一个开关，不是电路"，这句有据。**
- **`cyclic factor=13` 完全没用**（449 → 437）。194 不能被 13 整除，
  跨 RAM 边界还是要串行。官方文档那句"II 达不到时会报错"在这里**不成立**——
  它不报错，只是默默慢着。
- **"一个开关换十几倍"是这个坑的正常收益量级。** Xilinx 官方
  `Vitis_Accel_Examples` 的 `shift_register` 例子在同一个坑上拿到 U250 上 72 倍、
  U200 上 7.1 倍。所以这不是综合器抽风。

数值验证：csim 用 `-DFIR_SHIFT_CHAIN=1` 跑出来的输出，和改之前的输出 `cmp -s`
**逐字节相同**，直通检验仍是"最佳位移 96，错配 0 / 800"。

【数据】

**整机（in-context）逐项对照，`v18` → `v19_shift_chain`：**

| | v18 | v19 | |
|---|---|---|---|
| 拍/采样 | 450 | **28** | 16.1 倍 |
| LUT | 6422 | **6127** | −295，不涨反降 |
| FF | 9416 | 9427 | +11，等于没动 |
| DSP | 202 | **200** | −2 |
| BRAM | 54.5 | **52** | −2.5 |
| WNS @10 ns | +0.256 | **+1.283** | +1.027，失败端点仍 0 |

**除了触发器多 11 个，其余每一项都更好。** 时序松了 1 纳秒也说得通：那条
398 拍的移位链本身就是又长又绕的组合链，拆掉它等于同时给面积和时序松绑。

**上板复量**（`board/scripts/fir_selftest.py`，新旧两版 bit 同一套六项检查）：

| | 旧 bit（450 拍） | 新 bit（28 拍） |
|---|---|---|
| 1000 个采样耗时 | 0.0046 s | **0.0004 s** |
| 单采样 | 4.6 µs | **0.4 µs** |
| 实时余量 | 4.6 倍 | **55.6 倍** |

**11.5 倍，不是 16 倍。** 差的那部分就是每块固定的 Python 开销被抬起来了，
两个数对得上：

    核省下：450 − 28 = 422 拍 = 4.220 µs/采样 × 1000 = 4220 µs
    实测省：4600 − 400 = 4200 µs          （差 20 µs，在一位有效数字的精度内）

反推每块固定开销（这是当时唯一的瓶颈项）：

    新核理论  28 拍 × 1000 ÷ 100 MHz = 280 µs
    实测                              400 µs
    差                                120 µs   ← 占实测的 30%

顺带把延迟线搬到寄存器之后 BRAM 反而少了 2.5 个——**代码里"省事"的写法
（每采样搬 194 个数）在硬件上是最贵的那一种。**

【沉淀】

- **拍数多要先看循环表，别先加流水线指令。** 那张表会直接告诉你哪一段占了多少拍；
  这次的答案是"88% 花在搬运上"，加 PIPELINE 当然不动。
- **有环依赖的循环，编译器展开不了——这是语言规定的，不是优化不够。**
  `hist[k] = hist[k-1]` 换成标量串接，语义不变、展开得了。
  遇到"这段明明很简单却慢"的地方，先看依赖距离。
- **改结构不改算法时，"功能自检全过"不能证明新 bit 上板了。**
  验证手段必须能分辨两版——读文件头里的构建日期，别读文件名。
- **拿两个数相减推固定开销，比直接量更容易发现口径问题。**
  450→28 是 16 倍，实测是 11.5 倍，差的那 4.5 倍就是被掩盖掉的固定开销。
- **同一个写法在软件里"省事"、在硬件里最贵**（整体移位 vs 寄存器链）。
  这类地方只有读综合报告才看得见。
