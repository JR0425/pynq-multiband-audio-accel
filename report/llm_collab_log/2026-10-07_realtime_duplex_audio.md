【任务】

把音频通路从"录一段 → 算 → 放一段"改成**边录边放**：对着麦克风说话，
耳机里立刻听到经过四段压缩处理的声音，而且要**连续跑不断续**。

验收标准定死了三条，缺一条这件事就没做成：

1. 实时倍率 ≥ 1.00（墙钟不比音频长）
2. 逐位自检通过（分线程跑出来的结果 == 原来离线那条路的结果）
3. 能连续跑几十秒不成片丢音

【提示词】

「核现在有余量 55.6 倍，能不能不重跑 Vivado，就做成真的实时——
对着麦克风说话，耳机里立刻听到处理过的自己的声音？」

【模型回答】

AI 的判断是对的：核只占预算的 1.8%，这件事**不用改 PL**，瓶颈全在 PS 侧
怎么喂数据。但这个判断之下给的**具体方向，前两个都是错的**，而且都被实测否掉了：

- **怀疑 Python 线程切换间隔太小**（GIL 每 0.5 ms 被强制交出去一次）。
- **建议把两条线程提成 `SCHED_FIFO` 实时优先级**。

两个方向都不是靠推理排除的，是靠扫参数和量化掉的（见下）。

【哪里错了】

· **AI 的问题：先怀疑 GIL 争用，扫了四档线程切换间隔 —— 完全没动。**

  `sys.setswitchinterval` 依次取 0.0005 / 0.005 / 0.02 / 0.1 秒，实时倍率一直在
  0.98~0.99。四档都一样，说明这一项不是变量。（搬样那个 C 调用是 cffi 的 ABI
  模式，本来就释放 GIL，不靠这个间隔让路。）

· **AI 的问题：接着提实时优先级 —— 压小了尖峰，一块都没少丢。**

  两条线程提成 `SCHED_FIFO`（搬样 20、过核 10）之后：

      最大尖峰   20.04 ms → 11.48 ms
      8 秒丢的块      12 块 → 8 块

  尖峰压下去一半、丢块数几乎不变 —— 说明亏损**不是被谁抢占**，是每块都会发生的
  固定开销。这个结果直接排掉了整条"调调度参数"的路。

· **环境的坑：第一次跑实时，`sudo` 漏了。**

  脚本一开 `/dev/uio0` 就退出，前几秒的输出全是误导性的。板上跑这个脚本必须
  `echo xilinx | sudo -S sh -c "..."`，而且 `sudo -S` 和 heredoc 会打架，
  得先把命令写进文件。

---

**真正的原因有三个，没有一个在核上。**

**坑一：原版 `play()` 每调一次白花 3.3 ms。**

第一次跑只有 **0.65 倍**（每块 10 ms 要花 15.5 ms），核只占 214 µs。拆开量：

    play(L)     13.31 ms
    record(L)    9.94 ms
    差           3.31 ms

拟合出来 `play_ms = 3.47 + 0.0205·L`——**截距是每次调用的固定开销，和块长无关**。
所以块长再怎么调也摊不掉：每播 1 秒音频要花 `1 + 166/L` 秒，**永远到不了 1**。

源头在驱动的 C 源码里：`play()` 每调一次都给 codec 写 **8 次 I2C**
（开头 4 次"开声"、结尾 4 次"静音"）。用一个 `nsamples=0` 的对照把它钉死了：

    play(nsamples=0)     3.447 ms
    record(nsamples=0)   0.119 ms
    差                   3.329 ms   ← 8 次 I2C 写，每次约 416 µs

顺带一个副作用：按当时的块长算，每秒把 DAC 静音再开声 100 次——那本来就该有咔声。

**坑二：两个方向搬样要占两个核，而板子只有两个核。**

换完驱动还是 **0.85~0.88 倍**，而且 10 秒的麦克风音频里**丢了 1.5 秒**。

原因不是"慢"，是**没地方站**：这个 IP 没有 DMA，`capture_block` 和 `stream_block`
各自都在**空转轮询**状态寄存器，各自把一个核吃到 100%。只跑这两个方向、什么都
不算的对照：

    录 200 块 ‖ 播 200 块：墙钟 1.974 s（实时 1.01x）
                            烧掉 CPU 3.930 s = **平均占 1.99 个核**

两个核全满，中间那点 Python（过核、转格式）被挤来挤去——谁抢到 CPU 就要把某个
空转线程挤开零点几毫秒，被挤开的那一头当场丢几个采样。

**坑三：搬样那条线程上多写一行 Python，就是丢音。**

把两个方向合起来之后还是 **0.81 倍**。把那条线程的每一段拆开量：

    ① cout→24 位（摆成 C 要的那份）    1.66 ms   17%
    ② 搬样 C 调用                      9.87 ms   99%   ← 这就是 I2S 时钟本身
    ③ 收到的 → int16                   0.08 ms    1%
    ④ 算 rms + 入队                    0.57 ms    6%
    io 整圈                           12.20 ms  122%

②是**一点余量都没有**的：它按设计就等于一个块的长度（48000 Hz、480 采样 = 10 ms）。
所以①③④加起来那 2.3 ms 全是净亏。

关键在于**它不是"慢"，是"不在"**：那段时间里没人来取 I2S 的数据，硬件 FIFO 只有
几个采样的深度，超了就被后到的覆盖——**直接丢**，而且听不出是哪一块丢的，
只是隔一会儿"咔"一下。

【怎么修正】

**一、把"一次一块"拆成"一个会话 + 很多块"**（`board/scripts/audio_stream.cpp`）：

    stream_begin()   mmap + 开 i2c + **开声一次**
    stream_block()   只搬数据，一次 I2C 都不写      ← 可以每 10 ms 调一次
    stream_end()     **静音一次** + munmap + close

实测 `stream_block(L)` 相对理论值超出 **−0.18 ms**（在噪声里，等于零）。
算法一个字没动，PL 不用重跑。

顺带修掉一个泄漏：驱动里 `setUIO()` 只 `open()` 不 `close()`，每调一次漏一个文件
描述符，按每秒 100 次调用算就是每秒漏 100 个。

**二、收和放合进一次调用**（`duplex_block()`）：

收和放本来就是**同一个 I2S、同一个采样时钟、同一个状态寄存器**，所以能在一次
状态脉冲里同时做完（驱动自己的 `bypass()` 就是这么写的，顺序照抄它：等 status →
应答 → 读 RX → 写 TX）。合起来之后，**整个搬样只占一个核**，另一个核空出来给 Python。

**三、搬样那条线程上只留那一次 C 调用**：

①③④全挪到过核那条线程上——它每块只用 2.4 ms，预算 10 ms。

【数据】

    实时倍率    0.65 → 0.85~0.88 → 0.81 → **1.00x**
    io 整圈     12.20 ms → 9.86 ms
    10 秒麦克风音频丢失   1.5 秒 → **0**

连续跑三档（8 秒 / 10 秒 / 24 秒）全部 1.00x。24 秒那一档：

    跑完 2401 块，24.01 秒音频，墙钟 24.05 秒
    逐位自检：960000 / 960000 个采样相同

**"960000/960000 逐位相同"是这个脚本唯一硬的那条判据**——它证明分线程没有让块
错位、`reset` 只给了一次、缓冲没有被踩。好不好听只能靠耳朵。

【沉淀】

- **空转等待的线程，CPU 占用再高也不代表有余量。**
  余量 = 它有没有权利晚一点。搬样那条线程占着 99% 的 CPU、看起来"很忙"，
  但它的中位耗时**就是**一个块的长度——它本身就是 I2S 时钟，一点都晚不得。
  判断一个线程有没有余量，看的是它的耗时离它的**截止时间**多远，不是看它忙不忙。

- **固定开销要拟合成截距看，不然会一直去调错的那个参数。**
  `play_ms = 3.47 + 0.0205·L`——截距是每次调用的固定成本，和块长无关。
  看不出这一点，就会一直在块长上打转（0.65 倍就是这么来的）。

- **先把每一段的耗时拆到能对上预算，再决定改哪里。**
  "io 整圈 122%" 这一行是整件事的转折点：它把"哪一段超了"从猜测变成读数，
  也直接指出了"这条线程上一点余量都没有"。

- **改架构的收益远大于调参数。**
  调线程切换间隔（四档）、调实时优先级，两个方向加起来几乎没用；
  改成"一次调用做两个方向"一步就从 0.85 到 1.00 的前一半。

- **试过没用的路要写进注释里。**
  那两个被否掉的方向如果不记，下一轮还会再试一遍。

- **硬件 FIFO 浅的地方，"晚一点"不是变慢，是丢数据。**
  这是实时的通路和批处理的通路最本质的区别：批处理丢掉的是时间，
  实时丢掉的是采样，而且丢得无声无息。
