# 2026-10-16 板子死机:六轮对照实验,一个机制查清了、它的因果被我自己的实验推翻,真凶还没找到

> ⚠️ **本篇的结论在收尾时仍然是"未结案"。** 已经知道的是 **panic 是怎么发生的**
> (两份完整转储互相复现),**不知道的是板子为什么会挂**。
> 「关掉实时就能救」这条在本文写完之前就被我自己推翻,别按它去改代码。
> 原始读数在 `data/results/board_hang_evidence_20261016.md`,
> 两份转储原文在同目录 `board_hang_rcu_stall_dump_20261016*.txt`。

【任务】

接着 10-15 那条线索往下查:实时通路跑起来会挂,挂的样子有两种 ——
一种是 RCU stall 之后自己 panic 重启,另一种是**静默硬死**(串口一个字不吐、
连 panic 都没有、要人按电源)。目标有两个:

1. 拿到卡住那颗核的调用栈 —— 之前录到 5 次 panic,**0 次栈**
2. 分辨"是管线把板子弄死的"还是"板子自己在坏"

同时在收尾时回答用户的一个问题:每次挂了直接断电,是不是把 SD 卡弄坏了。

【提示词】

- 「我重新上电，现在开始你注意监控
- 「你不是怀疑我每次直接断电损坏了sd卡吗?现在有结果了吗」

【模型回答】

这一轮最大的收获和最大的教训是同一件事:**转储解释得非常漂亮,漂亮到我直接把它
当成了结论。**

**第一步:找到那条还能拿到栈的路。**
AI 先前判过"这台板子上没有任何能拿到栈的路" —— hung_task、softlockup、
sysrq(BREAK)、ftrace、`/proc/<pid>/stack` 全都没有编(查过 `/proc/config.gz`)。
这次去读了 panic 那条路径的实现顺序,才发现问题出在顺序上:
`panic_on_rcu_stall=1` 是在 `rcu_dump_cpu_stacks()` **之前** panic 的,
所以卡住那颗核的栈永远打不出来。而 `panic_print` 走的是 panic 处理**早期**的
`panic_print_sys_info()`,不受那条顺序影响。

```sh
sudo sysctl -w kernel.panic_print=31     # 位0=任务状态+内核栈(等价 sysrq-t)
```

一次性打出 **1468 行 / 633 个栈帧**(转储正文的行数),两份独立复现。**这条路以前判"死"了,是判错了。**

**第二步:从转储里读出的机制。**

| 转储里的行 | 读出来的东西 |
|---|---|
| `ksoftirqd/0  R running task` 栈停在 `__schedule` | CPU0 的软中断线程"可运行却一直轮不上" |
| `ksoftirqd/1  S` | CPU1 的同一个线程正常睡着 —— **两颗核不一样** |
| `python3` pid 922,CPSR 低 5 位 `0x10` | 搬样线程被 tick 打断时在**用户态** |
| CPU0 的 `kworker`(含两个 `mmc_complete`)也全是 `R` | 不是只有软中断被饿死 |
| `0-....: (999 ticks this GP) ... softirq=10908/10908 fqs=500` | 整个宽限期里 CPU0 **一个 RCU 软中断都没跑过** |
| `panic_on_rcu_stall+0x1c` 直接进 `panic` | 这就是"5 次 panic、0 次栈"的原因 |

配上板上探针:`sched_rt_runtime_us=950000`/`sched_rt_period_us=1000000`(默认值),
`ksoftirqd/kworker` 全是 `TS` 普通类。于是机制是:

> `fir_live.py` 把搬样线程设成 `SCHED_FIFO` 20 且永不阻塞(零余量轮询 PL 状态寄存器)、
> 钉在 CPU0;`ksoftirqd`/`kworker` 是普通 CFS 类,任何 RT 线程都压得过它们。
> 唯一的护栏是 RT 限流,每秒留给非 RT 的 5% 被 nice -20 的 mmc/块层 worker 吃光
> (CFS 权重 88761 : 1024 ≈ 99 : 1),nice 0 的 `ksoftirqd/0` 抢到的≈0 →
> CPU0 的 RCU 静默态报不上去 → 60 秒后 stall → panic。

**CPU1 永远不 stall 是关键对照**:板上每个设备中断(xuartps 26 / eth0 28 / mmc0 29)
都落在 CPU0,CPU1 那列恒 0,所以 CPU1 没有 nice -20 的竞争者。

**第三步:半小时后,我自己把这个结论推翻了。**
按上面那条,正确做法显然是"关掉实时"。同一轮的第二臂就把它关掉
(`LIVE_RT_IO=0 LIVE_RT_DSP=0`)—— **照样挂**,而且换了一种死法:

| | 串口 | panic | `arp -a` 里有板子吗 | 网口链路 | 怎么回来 |
|---|---|---|---|---|---|
| 实时开着(`N_short`) | 有完整转储 | 有 | 有 | 1 Gbps | 60 秒后自己重启 |
| 实时关掉(`R_rtoff`) | **一个字都没有** | **没有** | **条目都没有** | 1 Gbps | 3 分钟不回来,**要人按电源** |

`arp -a` 里连条目都没有这一条很关键:ARP 是内核答的,不是用户态 ——
**内核整个停了**。而网口 PHY 链路还在(自协商不靠 Zynq),所以是死机不是断电。

⇒ RT 饿死是一个**真 bug,但只是"挂的方式之一"**,不是(或不只是)挂的成因。
静默硬死那种还没有解释,唯一不矛盾的猜想是"PL/AXI 读不返回,两核一起卡在总线访问上"
—— 那样连报 stall 的内核线程自己都跑不上,所以串口全静。**这只是猜想,没有任何证据。**

**第四步:那一轮的两臂根本不可比,所以"实时关掉也挂"这个判断当时还不能算数 ——
但下一句是,"它不可比"这件事本身就是我的责任。** 第二臂起跑时开机才 44 秒
(systemd/journald 还在猛写 SD),第一臂是开机 526 秒。我自己的工具里**本来就有**
一个 `NEXT_SETTLE` 专门对齐每臂的起跑 uptime,当天忘了设。

**第五步:SD 卡那条问题。** 用户问的"每次直接断电是不是把卡弄坏了" ——
查下来**没有证据支持,而且因果是反的**:板子先硬死,断电是被迫的。

| 读到的 | 值 |
|---|---|
| `tune2fs` 的 `Filesystem state` | **clean** |
| `Errors behavior` | Continue(真出错也不会 remount-rw,只会记一笔) |
| dmesg 里 mmc / ext4 / I/O 错 | **一条都没有** |
| 每次开机的 `EXT4-fs (mmcblk0p2): recovery complete` | 是日志回放**成功**,不是失败 |
| `Mount count` / `Last checked` | 63 次 / 停在 **2021-11-18**(创建那天),从没 fsck 过 |
| 卡的产品名 | **`asdfg`** |
| 写入速度 | 开机 51.8 秒时 `wr_sect=18784`(9.6 MB)/`wr_ms=48148`(48.1 秒)⇒ **约 200 KB/s** |

`asdfg`、63 次从没 fsck、200 KB/s 这三条是**旁证,不是证据**。结论是没坏。

【哪里错了】

· **AI 的问题:判"这台板子上抓不到栈"判错了。**

  只查了"这些调试设施没编",没去读 panic 那条路径的实现顺序。一个"没有路可走"
  的否定判断,只要还有一条路的实现细节没读,就是没查完。结果:这条路一开就打出
  1468 行,而前面已经为此绕了好几天。

· **AI 的问题:把"能解释 panic 的机制"当成了"挂的成因"。**

  这是本篇最贵的一条。转储把机制解释得很完整,我一读完就写进了给用户看的状态栏,
  还说"关掉实时就能救"。推翻它的对照实验半小时就做完了。
  **转储回答的是"怎么死的",不是"为什么死"。** 先跑对照、再下结论,就不会白写一版,
  也不会把一条错的改法交到用户手上。

· **AI 的问题:忘了用自己造的护栏。**

  `NEXT_SETTLE` 是我自己为"每臂起跑状态要一致"写的,当天却忘了设,导致一整轮实验作废。
  **写进工具的东西,不写进流程就还是没用。**

· **AI 的问题:在一条已经死掉的板子上跑出了假结论。**

  settle 那段把 `uptime() < 0`(板子死了连不上)当成"等到了",于是继续往下跑,
  记了一次假 HANG。挂了之后正确做法是 `wait_up` 等它回来,等不到就收工,而不是硬跑。

· **AI 的问题:一度把 SD 卡当头号嫌疑犯,方向反了。**

  当时的推理是"挂得越多 → 脏关机越多 → 文件系统越坏"这个正反馈。
  但账本读下来是干净的,而且因果顺序是"板子先硬死、断电是被迫的"。
  反话当时也写了("CPU0 一死 mmc0 中断就没人收了,所以 SD 看起来卡住也可能是结果"),
  但两条方向都说得通的时候,应该去读账本,而不是继续列旁证。

· **环境的坑:Windows 控制台默认 GBK,打印含 `⇒`(U+21D2)的日志会抛
  `UnicodeEncodeError: 'gbk' codec`。**

  加 `PYTHONIOENCODING=utf-8` 就好。排查看起来像"脚本坏了",其实是输出编码。

· **环境的坑:板上 `kill -0 $PID` 不加 `sudo` 永远返回"没权限"。**

  `fir_live.py` 是 root 跑的,所以这个存活判断以前**永远报 `alive=n`** ——
  那一行日志看着像"进程没起来",其实什么也没测到。已改成 `sudo kill -0`。

· **环境的坑:板子上两个串口程序不能同时开。**

  `pynq_serial_capture.py` 和 `pynq_console_cmd.py` 会抢 COM6 那一句柄,
  第二个直接报错。要发命令就得先停录制。

【怎么修正】

1. **`DUMP=1` 常开。** 它只改"panic 时打什么",不改任何行为,所以做 A/B 的每一臂都可以带着 ——
   顺手给下一次死亡留现场。同理**串口录制常开**,否则打出来也没人接。
2. **`NEXT_SETTLE` 每一轮都设。** 每臂起跑前等到板子开机满 N 秒(这一轮用的 180),
   把"关某项设置"和"当时板子刚开机正忙"这两件事分开。
3. **判据用"能撑多久",不用"挂了几次"。** 配置表里加了 `Z_idle` ——
   一个**什么都不跑**的对照组(`IDLE=1 IDLE_S=300`,连 overlay 都不加载);
   它活而管线挂,就锁定在管线/PL 这条路;它也挂,就跟我们一行代码都无关。
4. **每臂起跑前把设置记到主机侧**(`next_round.py` 的 `pre_probe()`):
   板子一挂,板上那份日志跟着没,`panic_print`/`rcu_panic` 之类的设置就永远读不到了
   (round7 的 `R_rtoff` 就是这样)。同时补了三条从没读过的 SD 计数:
   SDHCI 的 `err_stats`、ext4 的 `errors_count`、`lifetime_write_kbytes`。
5. **判"断电"还是"死机",看两个信号一起**:电脑侧网口 Disconnected + COM6 消失 = 断电;
   PHY 链路在 + 串口静默 = 死机;再加 `arp -a` 里连条目都没有 = 内核整个停了。

【沉淀】

1. 一份转储能解释"怎么死的",不等于能解释"为什么会死"。**先做对照实验,再写结论。**
2. 凡是要比两个配置,先把两边的起跑状态对齐;对不齐就明写"这一轮判不了",别硬判。
3. "没有路可走"这种否定判断,要顺着实现读一遍再下。实现细节没读完,"没有"就只是"没找到"。
4. 写进工具里的护栏,要同时写进流程,否则等于没写。
5. 板子上一旦挂了,先在主机侧等它自己回来;等不到就收工,**别拿着一条死板子把后面的
   配置一个个"跑"成假 HANG** —— 那种记录会把账算歪。
6. 界面上"拖滑杆没反应"这类症状,先确认板子还活着再当第二个 bug 查。
   (10-16 之前的记录里就有一次:滑杆那条链路本身是好的,`gain_applied_db` 从
   `[0,0,0,0]` 变成了 `[-20,-10,10,20]`,用户看到的"没反应"是板子已经死了的症状。)
