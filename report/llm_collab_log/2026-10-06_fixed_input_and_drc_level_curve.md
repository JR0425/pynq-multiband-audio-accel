【任务】

把上一轮留下的那条悬案收掉：**"压缩前后听不出区别"**。

上一轮把通路接通了、参数改成运行期可写、A/B 也改成了等响度三遍，
但最后那句结论是空的——"① 和 ③ 听感对比要等下一次上板才能确认"。这一轮要把它变成
一个**报告里能站住的说法**，而不是一句"我觉得差不多"。

拆成三件事：

1. **把板子的输入固定下来。** 原来每次跑都现场对麦克风念一段，
   同一次运行里所有参数用的是同一段录音，但换一次运行就换一段声音——
   参数组之间根本没法比。
2. **把"到底压窄了多少 dB"量出来。** 耳朵分不出 1 dB 上下的差别，
   选型和汇报都不能靠听。
3. **补一个压缩器的标准表征：输入-输出电平曲线。** 这是这个器件的行业通用测法。

【提示词】

「我队友也觉得差距不明显，要我录一个音调变化的版本再试试吗？」

【模型回答】

AI 第一次给的方向是**"重录一段起伏更大的素材"**——理由是真实语音的音量起伏太平，
压缩器没有可压的东西。这个方向后来被自己的测量推翻了（见下）。

第二个方向错在实验设计上：板子上原本让听的人在**六个候选参数组**里挑"几号最好听"。
而板子同时打印的选型指标是"峰均比"——这六组的峰均比只差 0.3 dB。
让人在六个几乎一样的里面挑，等于让人猜。

第三轮才改成：A/B 只比**「原声」和「扫描里最狠的一档」**，
再加一段**电平台阶**把压缩量直接量出来。

【哪里错了】

· **AI 的问题：板子上用整段峰均比当选型指标，而这个指标在六个候选之间是平的。**

  板子 4c 那张扫描表最后一列是整段峰均比：5.04 / 5.26 / 5.34 / 5.07 / 5.02 / 5.07
  —— 六组差 **0.3 dB**。拿它选型等于没选。

  真正能分辨参数组的是**帧级动态范围**（20 ms 一帧，取 95 分位比 5 分位）。
  离线复算 `data/audio/board_input_48k.wav`（归一到满量程 15%）：

  | 参数组 | 阈值 / 压缩比 | 帧级动态范围 | 压窄 | 整段峰均比 |
  |---|---|---|---|---|
  | 直通 | — | 22.1 dB | — | 5.56 |
  | 1 号 | 0.100 / 0.70 | 20.3 dB | 1.9 dB | 5.04 |
  | 2 号 | 0.050 / 0.70 | 19.4 dB | 2.7 dB | 5.26 |
  | 3 号 | 0.030 / 0.70 | 19.2 dB | 3.0 dB | 5.34 |
  | 4 号 | 0.030 / 0.50 | 17.1 dB | 5.0 dB | 5.07 |
  | 5 号 | 0.020 / 0.40 | 16.0 dB | 6.2 dB | 5.02 |
  | 6 号 | 0.010 / 0.30 | 15.6 dB | **6.5 dB** | 5.08 |

  同一张表里，帧级动态范围跨了 **1.9～6.5 dB**，峰均比只跨 0.3 dB。
  指标选错，后面所有"听哪个好"的问法就都建立在沙子上。

· **AI 的问题：把"听不出区别"归因到素材，建议重录。**

  把素材的包络**人为**扩张后再算（`build/drc_diag.py` 第二节）：

  | 起伏放大 | 素材动态范围 | 4 号压窄 | 6 号压窄 |
  |---|---|---|---|
  | 原样 | 22.1 dB | 5.0 dB | 6.5 dB |
  | ±6 dB | 24.2 dB | 4.9 dB | 7.0 dB |
  | ±12 dB | 28.0 dB | 5.4 dB | 8.5 dB |
  | ±20 dB | 33.1 dB | 5.2 dB | 9.1 dB |

  一段"起伏大一点"的真人录音顶多相当于 ±6 dB 那一行 —— 6 号从 6.5 到 7.0 dB，
  **多 0.5 dB**。真正能拉开的是 ±20 dB，但那是把正常语音改成机器声，不是"语调变化"。
  重录不是那个杠杆，这条建议撤回。

· **AI 的问题："固定输入"的增益在 int16 域算、却乘到 ±1.0 的浮点上。**

  `src/python/export_board_input.py` 里 `TARGET_RMS = 0.15 × 32767`（是 int16 的数），
  但乘的对象是归一化后的浮点信号，等于**多乘了一个 32768**。

  症状不是报错，是数字离谱：**有效值 32764（满量程 99.99%）、峰均比 1.00**。
  峰均比 1.00 在物理上不可能（那意味着整段是方波），是从这个常识看出来的。
  改成在浮点域算增益（`TARGET_RMS / 32768.0 / rms`），两边等价。

· **AI 的问题：`scipy.io.wavfile.read` 的返回顺序写反了。**

  它是 `(采样率, 数据)`，写成了 `(数据, 采样率)`，直接
  `AttributeError: 'int' object has no attribute 'astype'`。

· **AI 的问题：电平台阶那一节的判据是恒真的。**

  原来写的是 `abs(lifts[0]) < 1.0`——"最响那一档基本没动"。
  可是 `lifts` 是按最响档归一化出来的，`lifts[0]` **按定义就是 0**，这条永远过。

  换成两条有可能失败的：**输入跨度减输出跨度 > 2 dB**、
  **越轻的档抬得越多（单调）且最轻档 > 2 dB**。

· **AI 的问题：画图脚本把已经是 dB 的列又过了一遍 `log10`。**

  台阶表第五列本来就是"相对直通多少 dB"，再取对数就是 `log10(0) = -inf`。
  补了两个自检把这类错挡住：**直通列必须等于输入列**、
  **升量列必须等于「压缩后 − 直通」**——对不上就不画。

· **AI 的问题：量频谱变化时，选了一个在这个滤波器组上不成立的量。**

  第一版算的是"每个频段占整体能量的百分之几"，拿它前后对比。
  可这套分频是**相减式**的，相邻段的过渡带互相抵消，四段信号加起来才等于输入——
  四段确实还原得回输入（延迟 96 拍后最大差 `4.4e-16`），
  **但它们的有效值不按功率相加**：四段有效值的平方和只有输入的 0.66 倍。

  于是那张表里出现了"175.4%""107.3%"这种数——**一个占比超过 100% 的表**。
  这个异常比它看起来更早就能发现：四段占比加起来 140.8%，本身就说明这个量没定义好。

  改成直接看**压缩器对每一段施加了多少 dB 增益**。这个量不需要任何归一化，
  四段的差值就是频谱倾斜。

· **环境的坑：Jupyter 里 `!` 开头的行有缩进就 `IndentationError`。**

  `%cd` 容忍缩进，shell escape 不容忍。贴在 cell 里的命令必须**顶格**。

· **环境的坑：stdout 被 `tee` 接走时按块缓冲，界面上一片空白。**

  看着像卡死，其实在跑。要 `PYTHONUNBUFFERED=1` 加 `python3 -u`，
  或者另开一个 cell 去 `tail` 日志文件。

· **环境的坑：连点多次 Run，Jupyter 会把多余的执行排队。**

  结果是**多个进程同时播同一段音频**——耳机一直循环响，
  而且并发生成的那几份 wav 是坏的，得重跑一遍。清干净：
  `pkill -f '[f]ir_audio_loop'`，再用 `ps aux | grep '[f]ir_audio_loop'` 确认。

· **环境的坑：Git Bash 会把命令行里的 `/tmp` 重写掉。**

  传给 Python 的 `/tmp` 被换成 Windows 临时目录，而 Python 那边自己解析成 `D:\tmp`,
  两边不是同一个地方——测试夹具放进去，脚本说"没找到文件"。
  夹具要放在仓库里，别放 `/tmp`。

· **环境的坑：从板子整包下载，上一次存下来的是 Jupyter 首页的 HTML。**

  不用打开就知道：`loop_*.wav` 的字节数应该是
  **1728044 = 288000 采样 × 6 字节（24 位双声道）+ 44 字节头**，对不上就是页面。

【怎么修正】

1. **固定输入。** 新增 `src/python/export_board_input.py`，从 `data/audio/real_voice.wav`
   生成 `data/audio/board_input_48k.wav`（48 kHz、单声道 int16、截第 2.0～8.0 秒）。
   条件路径和 `src/python/multiband_baseline.py` 完全一致——混声道相加、去直流、
   `resample_poly` 到 48 kHz——重采样后 **507905 个采样**，和
   `data/results/baseline_metrics.md` 对得上，说明两边的输入是同一串比特。

2. **增益匹配做成幂等。** 生成脚本和板子脚本用**同一个公式**（一个在浮点域、
   一个在 int16 域，等价）。文件已经归一化过，所以板子上算出来正好是 **1.0000 倍**——
   这个数变成"加载对了文件"的对账点，偏了就报警。

3. **板子脚本读固定文件。** `board/scripts/fir_audio_loop.py` 加 `load_wav16()`：
   文件在就用它，不在就退回现场录音。采样率不对直接退出，**不在这里悄悄重采样**
   —— 那会让"板子的输入"和软件基线的输入对不上。

4. **A/B 换成最狠的一档**（阈值 0.010、压缩比 0.30），存 `loop_5_过核_压缩_最狠.wav`。

5. **新增第 9 节电平台阶。** 6 档 × 1 秒、每档降 8 dB，每档是四个正弦相加
   （250 / 700 / 1400 / 4000 Hz，固定相位）。过一遍核，
   量出每一档的有效值，并补回等响度后存成 wav。

6. **把台阶表画成图。** `src/python/plot_drc_curve.py` 从 run 记录里读那 6 行
   （不重算，重算是仿真不是板上的成绩），画输入-输出曲线，
   输出 `data/figures/drc_transfer_curve.png`。

7. **把几段拼成一个文件。** `src/python/make_ab_medley.py` 加 `--files` 模式，
   按给定顺序拼、每段前面加提示音、响度统一对到第一段。
   分开的 wav 让人来回切，音量、设备、注意力都在变，比不出东西。

8. **顺手量了频谱变化。** `build/drc_band_tilt.py`。这条通路是**逐频段**压缩的，
   四段被压的程度不一样，所以频谱平衡也会动。这不是副产品——
   "每个频段各自压"正是这个结构存在的理由，频谱怎么动是它该回答的问题。

**实测数据**（2026-10-06，PYNQ-Z2，固定输入 `board_input_48k.wav`）

第 9 节电平台阶（阈值 0.010、压缩比 0.30，压缩后已补回等响度）：

| 档位 | 输入 | 直通 | 压缩后 | 相对直通 |
|---|---|---|---|---|
| +0 dB | 6554 | 6554 | 6554 | +0.0 dB |
| −8 dB | 2609 | 2609 | 3323 | +2.1 dB |
| −16 dB | 1039 | 1039 | 2000 | +5.7 dB |
| −24 dB | 414 | 414 | 1131 | +8.7 dB |
| −32 dB | 165 | 165 | 450 | +8.7 dB |
| −40 dB | 66 | 66 | 179 | +8.7 dB |

**输入跨 40.0 dB，输出只跨 31.3 dB —— 压窄 8.7 dB。**
最下面三档数值一样是硬拐点压缩器的正常形状：落到门限以下就一点不动了。

别的几条：

| 项目 | 结果 |
|---|---|
| 固定输入电平 | 有效值 4915（满量程 15.0%）、峰值 27346（83.5%）、峰均比 5.56 |
| 板子上算出的增益 | **1.0000 倍**（幂等，说明加载的是对的文件） |
| 旁路逐位校验 | 0 / 288000 个采样不匹配，切了 36 块 |
| 压缩真的改了数据 | 287910 / 288000 个采样和直通不同（100.0%） |
| 处理速度 | 直通 4.51 µs/采样 ｜ 压缩 4.51 µs/采样 |
| 帧级动态范围（真实语音） | 22.1 dB → 6 号压到 15.6 dB |

台阶上量到 8.7 dB、真实语音上量到 6.5 dB 两个数不矛盾：台阶一直降到 −40 dB，
比真实语音的起伏深得多。**报告里两个都要写**，只写 8.7 会显得挑好看的说。

各频段被压的程度（压缩器对每一段施加的增益；参数取 6 号）：

| 频段 | 直通 | 压缩后 | 压缩器增益 | 补回等响度后净变化 |
|---|---|---|---|---|
| 0–500 Hz | 0.1009 | 0.0352 | −9.15 dB | −0.41 dB |
| 500–1000 Hz | 0.0563 | 0.0215 | −8.36 dB | +0.38 dB |
| 1000–2000 Hz | 0.0228 | 0.0107 | −6.60 dB | +2.14 dB |
| 2000–24000 Hz | 0.0311 | 0.0136 | −7.22 dB | +1.51 dB |

低频段被压得最狠、1–2 kHz 最轻（差 2.55 dB；4 号是 2.04 dB）。
补回等响度之后低频基本回到原位，中频抬起来 —— 净效果是**往亮处偏约 1.7～1.9 dB**。

**说明一处边界**：这一轮把"压窄多少"量清楚了，但**没有解决"要不要为听感重新选参数"**。
六组里挑哪一组是设计取向问题（压得狠 = 效果明显但改了声底，压得轻 = 自然但看不出）。
这一轮只做到"给出选择的依据"，选择本身还没定。

还有一条**没有对上**、留给下一次的：试听时反馈的是「明显放大、低音亮」，
而上面量出来的方向是**低频被压得最狠、平衡往亮处偏**。
两个说法不一致。要确认的是听的是哪两段——板子第 6 节放三段
（① 原声 ② 压缩后（比原声轻 8.7 dB）③ 压缩后补回等响度），
只有 ① 和 ③ 之间才该等响度；拿 ② 去比，听到的就是音量差。

几条能搬去别的项目的：

- **拿耳朵选参数之前，先量一下几个候选到底差多少。** 差 0.3 dB 就别问了，
  问出来的答案是噪声。这次是板子自己打印的选型指标（整段峰均比）就是那个分辨不出的量。
- **选型指标要选"能分辨候选的那个量"。** 同一个器件，整段峰均比差 0.3 dB、
  帧级动态范围差 4.6 dB——指标选错，扫描白扫。
- **听感实验三件套**：固定输入、等响度、拼成一个文件顺序播。
  缺一样，听出来的就是音量差或者顺序差。
- **"效果听不出来"要先分成两种**：没生效，和生效了但小。
  这次是后者（6.5 dB）。分不清这两种，就会去改不该改的地方。
- **写 `check()` 之前先问一句"这条有没有可能失败"。**
  按定义恒真的判据比不写还坏——它会让人以为验过了。
- **同一个公式写两个地方，就把其中一个的输出做成对账点**（这里是"1.0000 倍"）。
  两边不一致时不用查，它自己会喊。
