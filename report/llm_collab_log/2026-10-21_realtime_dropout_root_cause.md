# 2026-10-21 实时通路丢块:每块之间停 196 µs,以及每 30 秒一次的 SD 卡写入

> 结论先写:丢块不是 CPU 不够。**搬样线程每块之间要在 Python 里停 196 µs**
> (`queue.Queue` 的锁和 `Condition` 在 Python 层),而 I2S 只吸得下一百来微秒,
> L=480 时每块漏一点,60 秒丢 70 块。换成 `queue.SimpleQueue`(等待和锁在 C 里)
> 后空档降到 81 µs,同样 60 秒丢 0 块。
>
> 修完队列后 600 秒能跑完、总数也达标(丢 4 块),但 trace 里还有**每 30 秒一次**
> 的 5~80 ms 停顿:一个 systemd timer 每 30.24 秒拉起一次内核线程提权脚本,
> systemd 自己往 journal 写四行,journald 落在 SD 卡上,刷卡的 `kworker/0:1H-mmc_complete`
> 是 FIFO 50,在 CPU0 上直接抢搬样线程(FIFO 20)。换成常驻静默进程后,
> 空闲 45 秒 journal 零写入。
>
> 最终按演示配置跑 600 秒:60066 块、**丢块 0**、自检通过、最大空档 3.91 ms。

【任务】

性能线的第一项:演示同配置下 600 秒丢块 ≤5 块。演示同配置
= 网页开着、服务开着、L=480、NBUF=3、默认麦克风通路。

起点不好看:此前最好的成绩是"无界面 0.20 块/秒",带 SSH 拉取器 0.90 块/秒,
网页开着时更高。而 SSH 轮询本身就会制造丢块,所以这次探针必须在板内读状态。

【提示词】

- 【演示同配置下 600 秒丢块 ≤5。不要从 PC 侧轮询，探针在板内读状态。】
  【先排查 CPU 竞争，若排除不了就在 fir_live.py 块间路径按代码位置插桩量时间，再用 A/B 只换一个变量来确定原因，或者你有更好的想法】

【模型回答】

**第一步:先把"是不是 CPU 被别的进程抢了"这件事排除掉。**
按上一轮的怀疑方向排了 12 臂矩阵,每臂 60 秒,网页开关 × 钉 CPU1 × NBUF 3/4 ×
L 480/960/1920,外加一臂把 GIL 切换间隔降到 0.1 ms。每一臂起跑都对齐到
`uptime % 30`,避免上一臂的定时器落在下一臂开头。

结果:

| 变量 | 效果 |
|---|---|
| 网页开关 | 差 3%,在噪声里 |
| 非音频进程逐线程钉 CPU1 | 没有可测收益 |
| NBUF 3 → 4 | 69 → 58 块/60 s,不是余量问题 |
| GIL 切换间隔 5 ms → 0.1 ms | 64 vs 67,没有 |
| L 480 → 960 → 1920 | **480 稳定丢,960 以上稳定 0** |

块长是唯一的强变量。这一点把方向指到了"每块固定要交多少开销",而不是
"CPU 有没有空",但矩阵本身还没量到 Python 里那段时间。

**第二步:把两块之间按代码位置切开量。**
在 `fir_live.py` 里加 `GAP_TRACE`,记五个时刻:等槽位开始、等到槽位、
进 C 之前、出 C、qput 完。四段相加就是"这块到下一块之间没有人在搬样"的时间。

| 队列实现 | 等 dsp 槽位 | 进 C 之前 | 出 C 到 qput 完 | 下一轮开头 | 合计 |
|---|---|---|---|---|---|
| `queue.Queue` | 67.6 | 7.7 | 108.9 | 11.8 | **196 µs** |
| `queue.SimpleQueue` | 22.1 | 7.3 | 39.9 | 12.8 | **81 µs** |

`queue.Queue` 的 `get`/`put` 各要拿一次 `threading.Lock` 和 `Condition`,
都在 Python 层;`SimpleQueue` 的等待和锁在 C 的 `_queue` 模块里。同样的两步,
176 µs 变成 62 µs。

**第三步:A/B 只换队列,别的都不动。**
L=480、NBUF=3、网页开着:

| 队列 | 60 秒丢块 | 块到块周期 | 自检 |
|---|---|---|---|
| `queue.SimpleQueue` | **0**(6021 块) | 9.993 ms | 通过 |
| `queue.Queue` | 73(5932 块) | 10.125 ms | 通过 |

块周期差 0.125 ms,正好是 1.25%,和 60 秒丢 75 块对得上。queue.Queue 的每一块
都慢一点点,累积成 1.25% 的音频缺口;SimpleQueue 的周期略小于 10 ms,偶发的
Python 停顿时还能靠硬件缓冲追回来。

默认改成 `SimpleQueue`,L=480、NBUF=3 保持不变,所以端到端延迟公式不变:
`3×480/48000 + 2 ms = 32 ms`。

**第四步:600 秒跑完,但开始看分布,而不只看总数。**
这一趟 60009 块、丢 4 块、实时 0.9999x、自检通过,按判据算过了。
但 trace 里 60008 个块间空档中有 28 个超过 5 ms,而且每隔 30 秒一簇,最大 80.2 ms。

把每一簇换成开机秒数(探针记了起跑时的 `/proc/uptime`,加上块内相对时刻),
周期是 **30.24 秒**,第一簇正好等于 `45 + 366 × 30.24`,最大那一簇等于
`45 + 371 × 30.24`。`ksoftirqd-rt-refresh.timer` 的配置正是 `OnBootSec=45`、
`OnUnitActiveSec=30`,实测每次比配置多出 0.24 秒。

**第五步:把链条补全。**
timer 每唤醒一次,systemd 自己要写 Starting / Succeeded / Finished 四行 journal。
journald 把日志落在 SD 卡上,写卡完成的中断由 `kworker/0:1H-mmc_complete` 处理,
它是 FIFO 50;搬样线程是 FIFO 20,同在 CPU0,于是写卡期间搬样直接停摆。

**第六步:两次失败的修法,然后换掉机制本身。**
先试了两条:把 timer 的服务钉到 CPU1、给服务加 `LogLevelMax=warning`。
停顿没有消失。原因分别是:钉 CPU 移不走 CPU0 上完成的 mmc 中断;`LogLevelMax`
过滤的是服务自己打的东西,systemd 给 unit 写的 Starting/Finished 不受它管。

改法是把"周期执行"这个机制整个换掉:删掉 timer 和它调的 shell,换成一个常驻
Python 进程,每 30 秒扫一遍 `/proc`,对 ksoftirqd 和 `kworker/[01]:*` 调
`sched_setscheduler`。只读内存,不 fork、不写日志、不碰磁盘。开机那一次仍由
`ksoftirqd-rt.service` 调原来的 shell,脚本改成只在失败时记一条 warning。

验证:

- 空闲 45 秒,journal 里除 ssh 会话以外的行数 = 0(旧版每 30 秒 4 行);
- 60 秒臂:6017 个块间空档,最大 0.363 ms,没有一个超过 0.5 ms,丢块 0;
- 600 秒臂:60066 块,丢块 0,最大空档 3.91 ms,超过 0.5 ms 的 17 次且不再有
  30 秒周期。

【哪里错了】

**AI 的问题:第一轮矩阵里没有一条能量"Python 自己花了多久"。**
12 臂是按上一轮留下的怀疑方向(CPU 竞争、网页负载、缓冲深度)排的。矩阵没白做,
它确实把网页、钉核、NBUF 都排除了,但它回答不了真问题。真正定案的 `GAP_TRACE`
是后来才加的。**"排假设"不能代替"按代码位置量时间"**;当所有假设都属于同一类
(CPU 够不够)时,再做一百臂也跳不出这一类。

**AI 的问题:拿 `lost_blocks` 横向比不同的块长。**
`lost_blocks` 是按本档块长算的:L=480 一块 10 ms、L=960 一块 20 ms,
同样丢一块,丢掉的音频差一倍。第一轮表格如果只看这个数,会得出"960 比 480 好",
其实只是尺子变了。后来补了 `audio_rate` 和"缺口 ms/60 s"两个统一尺子。

**AI 的问题:把"总数达标"当成了"完成"。**
600 秒那趟丢 4 块、`ok=true`,按判据是过的。我差点就此收工,是看 trace 分布时
才发现 28 个 5~80 ms 的停顿。**一个能过的总数可以藏一个周期性的缺陷**;
判据里只有总数的时候,要另外看一次分布。

**AI 的问题:先写了"停顿对在 timer 上",之后才算相位。**
这个结论方向是对的,但第一版只是肉眼把时间戳和日志摆在一起,没算周期、没算
命中率。补算之后才能写成"30.24 秒周期、`45 + 366 × 30.24` 命中到 0.1 秒"。
**先给结论后补证据,即使结论最后是对的,这个顺序也不该有。**

**AI 的问题:结果文档里把最大空档写成了 215 ms,原始 trace 是 80.2 ms。**
两个数都是我这次会话里写下的,215 没有出处。是回查 json 时对上的。
报数字之前要回到原始文件核一遍,尤其这种"顺手写下的最大值"。

**AI 的问题:加了个 `phase30` 指标,算的是"到最近 30 秒整数倍的偏差"。**
它在"每 30 秒一簇"的数据上会给出漂亮的低值,但在均匀分布上也会给出中等低值,
分辨不出这两种情况。换成把事件按 `dt % 30` 分到 10 个 3 秒格子看直方图。

**环境的坑:`/dev/shm` 开了 `fs.protected_regular=2`。**
sticky 目录里,root 用 `"wb"` 打开别人建的普通文件会 `EACCES`,只有新建才行。
探针的日志、trace 全是上一臂留下的同名文件,第一趟直接报 `PermissionError`。
修法是开跑前先 `unlink`,删不掉就退到带 pid 的文件名。

**环境的坑:Windows 上用 `os.path.join` 拼远程路径。**
paramiko 的 SFTP 收到的是 `C:\...` 风格的反斜杠路径,文件推到了一个奇怪的名字下,
板上执行时找不到。全部改成 `"%s/%s" % (目录, 文件名)`,并在推完后核对字节数。

**环境的坑:探针用 `xilinx` 身份跑,子进程起不来。**
`fir_live.py` 要 `Overlay(BIT)` 和 SLCR 的 mmap,非 root 直接
`OSError: Root permissions required`。矩阵里所有臂改成 `sudo` 起。

**环境的坑:`LogLevelMax=warning` 不过滤 systemd 给 unit 写的行。**
它只作用于服务进程自己的输出。这条是试了才知道的。

**环境的坑:`OnUnitActiveSec=30` 实测周期是 30.24 秒。**
拿 30.0 去对相位会对不上,越到后面偏得越多(600 秒里从相位 12.8 漂到 17.5)。
周期为什么多 0.24 秒没有细查。

**环境的坑:板子的系统时间停在 4 月 10 日。**
所有"看日志时间戳"的做法都得先换算成开机秒数,否则和 audio trace 对不上。

【怎么修正】

1. `fir_live.py` 的两条队列改成 `queue.SimpleQueue`(`LIVE_QUEUE=queue` 可退回旧实现对照)。
2. 保留 `GAP_TRACE`(环境变量打开),以后查实时问题直接开,不要再从"CPU 够不够"开始猜。
3. ksoftirqd/kworker 的周期重扫从 systemd timer 改成常驻进程 `ksoftirqd_rt_watch.py`。
4. `ksoftirqd_rt.sh` 只在失败时记 warning;成功一次都不写。
5. 安装脚本顺手删掉旧的 timer 文件,避免升级后它继续每 30 秒写 journal。
6. 探针、矩阵、钉核三个工具落到 `tools/board_debug/`,一次推板、一条命令跑一臂。

【沉淀】

1. **周期性卡顿先看周期和相位,不要看总数。** 总数会把"每次 80 ms、每 30 秒一次"
   平均成"看起来还行"。
2. **横向比性能数之前,先确认两边的尺子一样。** 块长不同时,丢块数不能直接比。
3. **"通过"的判据不能只有一个总数。** 至少有:总数、分布、最坏一次。
4. **实时通路里,Python 每块的开销要和硬件缓冲放在一起看。** 196 µs 对 100 µs
   就是丢,81 µs 就是不丢;这两个数差一倍,现象却是"丢 70 块"和"丢 0 块"。
5. **排实时障碍时按"谁在 CPU0 上、优先级多少"查,不要按"哪个服务"查。**
   真正抢 CPU 的不是那个服务进程,是它引起的内核线程。
6. **root 也不是什么都能写。** `protected_regular=2` 下,sticky 目录里打开别人的文件要
   先删。
7. **系统的时间和你的时间不是一回事。** 板子时钟停在四个月前,周期和相位只能从
   `/proc/uptime` 算。

## 验证边界

- 12 臂矩阵每臂 60 秒;600 秒只跑过两次(旧 timer 一次、新 daemon 一次),
  各 1 次,没有重复。
- 两次 600 秒都是"网页用 headless Chrome 真实打开",但**没有模拟人手在页面上
  拖动滑杆、点按钮**;那种负载没有量过。
- 最终那一趟仍有 17 次 0.5~3.9 ms 的空档,间隔 12~63 秒,越往后越大,
  来源没有定位(不是 30 秒周期)。没有造成丢块,报告里不能写"零停顿"。
- `deficit_ms_per_60s` 为负(-46 / -111 / -425)不是"多处理了音频",是
  `time.time()` 与音频时钟零点的偏差,看丢块终值。
- 结论只覆盖 L=480、NBUF=3、默认麦克风通路、网页与服务同时开着这一种配置。
- 板子的系统时间不对,所有周期和相位结论用的是 `/proc/uptime` 的差值。
