# 2026-10-25 自研 RTL 三颗位流上板：核 3 拍/采样，错都在读数和写报告

> 结论先写：**基准档五条判据全过，连续流版也上了板。** 块模式 14407 拍、
> DMA 版 14408 拍，两版输出逐位相同（最大 0 LSB）；4800 点整块墙钟 2.17 → 0.90 ms；
> 65535 点连发 25.7 M 采样/秒（约 536 倍实时）。第三颗抓取位流抓到握手时序：
> 块头输入握手间隔 100% 是 3 拍。
> 当天写错的东西没有一条在电路里，全在**怎么读数、怎么写报告**：
> 把 96 采样群延迟当成拍数、把自己的软件耗时算进硬件吞吐、
> 绕过了驱动唯一的超长提示、没查 IP 的总线接口就先连 ILA。

【任务】

把手写 RTL 前端（3 低通 + 相减 + 4 段综合 + DRC）从「仿真逐位对」推到「板上跑对」，
按三档交付：基准（独立 overlay + 周期计数器 + 逐位对拍 + 块往返）、
连续流（AXI DMA + AXI-Stream）、拔高（两版并排 + valid 时序图）。
约束：不替换出货的 `fir.bit`；图更硬，但数字一律用不带监视器的那版位流。

【提示词】

「先完成基准档最后部分，再继续做dma版，拔高档」

【模型回答】

**第一步：判据 ⑤ 从传递论证补成并排对拍。** 两个 overlay 放进同一进程先后加载，
跑同一份 `in_q15.mem`：RTL 前端 vs 出货 `fir.bit` 的
`FirMultiband.run(..., bypass=True)`，4800 点 0 点不同、最大 0 LSB。
两侧各自也先和 xsim 黄金核过（0/0），不是「两边一起错」。

**第二步：DMA 版。** `axi_dma` 的 MM2S 直接读 DDR、S2MM 直接写回，外壳只做
valid/ready。4800 点 14408 拍（bypass）/ 14418（DRC），和块模式只差 1 拍，
逐位相同。65535 点连发十次，每块 2.55 ms = 核内 1.97 + DMA/驱动 0.58，
折 25.7 M 采样/秒；核内上限 33.3 M。

**第三步：抓时序。** ILA 6.2 只有 JTAG 口、PS 够不着，`system_ila` 的寄存器映射
在 IP-XACT 里没有字段，所以写了一个 1024 拍深的抓取器：每拍一条 32 位，
输入输出各一块 BRAM，PS 经 AXI BRAM 控制器读回。板上结果：块头 342 次输入握手，
相邻间隔全部 3 拍；块尾输入 TLAST 与输出 TLAST 差 8 拍；前 96 个输出采样全 0。

【哪里错了】

**AI 的问题：把 96 采样群延迟当成拍数读。**
第一次抓到输出握手在第 10 拍，第一反应是「接错了」，还按 96×3=288 拍去算
「输出该晚 288 拍」，差一点把这句话写进报告。回头读 `fir_stream_shell.v`
的模块头才看到原文：每块开头复位延迟线，前 96 个输出就是 0，
**延迟在数值里，不在个数里**。改成检查前 96 个输出是否全 0，板上实测正好 96 个。
读数的前提没确认，后面所有判断都是错的。

**AI 的问题：绕过驱动唯一的提示。**
4800 点只回来 704 个采样，根因是 `axi_dma` 的 LENGTH 只有 14 位
（`c_sg_length_width` 默认），19200 字节被截成 2816 字节，IP 不报错。
PYNQ 驱动本来按 `2^14-1` 卡住并给了提示，却先把 `ch._max_size` 改成 `2^26-1`
绕过去，等于拆掉了唯一的报警。正确做法是在 tcl 里把 `c_sg_length_width`
设成 26 重编，驱动一个字不动。

**AI 的问题：把自己的软件耗时算进硬件吞吐。**
持续吞吐第一次量出 15.6 ms/块（86 倍），和单次对不上。分阶段计时才看清：
Cortex-A9 上那几句 numpy 整块校验就占 5.7 ms，比一次传输还长；
`wait` 前那 1 ms 宽限循环也原样进了墙钟。改成 O(1) 状态检查 + 50 µs 宽限、
把逐点校验移出计时区间，才是 2.55 ms。

**AI 的问题：没查接口就先连 ILA。**
按「BRAM 控制器能挂 AXI 互连」的经验去连 `ila_0/S_AXI`，Vivado 报
`No interface pins matched`。翻 `component.xml` 才确认 ila 6.2 根本没有
AXI4-Lite 从口。IP 有没有某个接口，看 `component.xml`，不看框图经验。

**AI 的问题：报告里三处归因写错。**
① 把 `fir_rtl_dma.bit` 的 WNS / LUT / 端点数量写成了「这颗抓取位流」的，
两者不是同一颗；② 图注写成「TLAST 与输出排空」，块尾不是排空，
是输入与输出的 TLAST 对齐；③ 给 1 拍差异编了一个「流外壳把 TLAST 那拍也算进去」
的原因，读了两边的计数器才发现真因是块模式停在前端 `dout_vld`、
流式要等这一拍进了 FIFO 并被 DMA 收走，而 FIFO 输出是寄存的。

**环境的坑：BD 里的静默错误，validate 和出声都拦不住。**

- `axi_bram_ctrl` 的 `SINGLE_PORT_BRAM` 填 0，控制器改从没接线的 B 口回读，
  整片恒为 `0x00000008`（和 wrapper 里绑的常量一字不差）。
- A 口地址被截成 13 位，字节地址当成字地址用，2048 点之后回卷。
- `blk_mem_gen` 的 `clka` / `clkb` 漏接：BD 照 validate 过、位流照出、`done` 照置，
  但 PS 写不进也读不回。
- B 口只拉高 `enb` 不驱动 `web`，写不进去；`web` 是 1 位，接 4 位会被截成最低位。
- `xlconcat` 的 In0 是最低位，`done` 接到 In1，板上读成 `0x80000000`。

**环境的坑：综合把整颗 FIR 当死存储删掉。**
输出 BRAM 的写数据就是 FIR 输出、A 口只有 AXI 从机在读，被判成可删存储，
网表里 DSP = 0 / RAMB = 0，util 只剩 PS7 + AXI。加 `DONT_TOUCH` 后 197 个 DSP；
现在综合后 `$s_dsp < 100` 直接报错，不再静默出空壳位流。

**环境的坑：Vivado 2020.2 会随机读不到自己的 tcl。**
`create_bd_design` 报 `couldn't read file "...bd.tcl": No error` 或
`Failed to load feature 'ipintegrator'`，连挂四轮，第五轮自己过。
同样的文件手动读 200 次 0 失败。判断依据是报错里出现的是工具内部文件名，
不是自己的文件。

【怎么修正】

1. 判据从「输出比输入晚 288 拍」改成「前 96 个输出采样是否为 0」，
   写进探针和报告。
2. `c_sg_length_width` 改成 26 重编；驱动里的长度上限不动。
3. 吞吐测量：O(1) 状态检查、50 µs 宽限、逐点校验移出计时区间。
4. ILA 换成自写抓取器，寄存器地址自己定，不再猜官方 IP 的 hwh。
5. BD 侧：单口参数按语义填、地址取 `[14:2]`、BRAM 两个时钟都接、`web` 驱动、
   `xlconcat` 低位先接；抓取器先用 `0xDEADBEEF` 自检通路，再谈位序。
6. 报告里的归因逐条对回原始报告文件，每个数字标明属于哪颗位流。

【沉淀】

1. **延迟可能藏在数值里，不在拍数里。** 判断时序对不对之前，先确认这条通路的
   延迟以什么形式存在；模块头通常写着。
2. **测量里凡是 O(n) 的软件工作都要挪出计时区间**，否则量的是 Python 不是硬件。
3. **工具给的限制提示不要绕过。** 绕过之后，错误会从「报错」变成「数少了一截」。
4. **IP 的接口看 `component.xml` / hwh，不看框图经验。**
5. **BD 的静默错误只能靠自检数据暴露**：先写已知值再读回，先验通路再验位序。

## 验证边界

- 三颗位流各自单独加载；拍数与吞吐一律引 `fir_rtl_dma.bit`，
  抓取位流只出图不出数（监视器让组合路径多一级）。
- 4800 点单次墙钟含 PYNQ 驱动的起停开销；536× 是 65535 点连发十次的平均，
  不是单块数，也不能和块模式的 46× 并列。
- 逐位对拍覆盖 4800 点单块与连跑两块；更长的块只验了不溢出和可复跑，
  没有做全量对拍。
- DRC 通路仍只对 Python 模型，没和 v25 逐位比：v25 的起停是运行时寄存器，
  RTL 的是编译期参数，两边参数来源不同。
- 收工时间 2026-10-25；三颗位流（每颗约 3.9 MB）、构建脚本、探针和图都随本篇一起入库。
