# 2026-10-22 延迟能压到多低:块长扫到 7.5 ms,以及一个被自己的测量推翻的机制

> 结论先写:**块长的下限是 7.5 ms,不是文档里一直写的 10 ms。**
> L=360、NBUF=2 跑 120 秒,实时倍率 1.00×、延迟中位 14.96 ms,
> 超过 25 ms 的块 0 个(旧的 21.1 ms 那档是 8 个)。嘴到耳 **16.2 ms**。
> 再往下(6.25 ms)开始丢块,而卡住的原因**不是** Python、也不是调度,
> 是音频 IP 那条逐采样的 I2S 握手。

【任务】

延迟这一项原来报的是 31.0 ms(稳定档)和 21.1 ms(NBUF=2)。
目标是尽量往下压,并且要知道**压到哪儿就压不动了、为什么**。

【提示词】

- 【python的处理速度是不是比C慢，换成C能改善延迟吗？你测试一下或者提出更好的方案】

【模型回答】

**第一轮:先确认机制,再安排测量。** 我肯定"10 ms 块以下跑不动,是因为每块固定的
Python 开销(队列、格式转换、状态文件)摊到每个采样上太多的想法",并建议把格式转换
挪进 C 库,以此换更短的块长。

**第二轮:被要求直接测,于是扫块长。** 七档一次扫完(`LIVE_SRC=wav`、NBUF=2,
每档 25–30 秒):

| L | 块长 | 搬样中位 | 占预算 | 实时倍率 | 结果 |
|---|---|---|---|---|---|
| 960 | 20 ms | 19.72 ms | 99% | 1.01× | 稳 |
| 480 | 10 ms | 9.87 ms | 99% | 1.00× | 稳 |
| 360 | 7.5 ms | 7.41 ms | 99% | 1.00× | 稳 |
| 300 | 6.25 ms | 6.18 ms | 99% | 0.98× | 丢 64 / 3950 块 |
| 264 | 5.5 ms | 5.83 ms | 106% | 0.91× | 丢 389 / 4176 块 |
| 240 | 5 ms | 5.93 ms | 119% | 0.83× | 丢 1053 / 4985 块 |
| 120 | 2.5 ms | 3.09 ms | 124% | 0.42× | 严重丢块 |

**第三轮:归因。** 三个证据把"每块固定开销"这个说法否掉:

1. `GAP_TRACE` 把每块切成四段(L=240):等槽 0.023 ms、`duplex_block` 5.93 ms、
   放回队列 0.019 ms、块间空转 0.013 ms。除了那一次 C 调用,其余全在 20 µs 量级。
2. dsp 侧一直只占预算的 18–25%,队列里始终有算好的槽。
3. 把搬样线程的实时优先级从 20 提到 60(高于 CPU0 上全部内核线程):5.92 vs 5.93 ms,没变。

**第四轮:L=360 补 120 秒。** 16050 块、音频 120.38 秒 / 墙钟 120.12 秒 = 1.00×,
延迟中位 14.96、p99 15.30、最大 20.77。

【哪里错了】

**AI 的问题:先给机制,后做测量。**
"每块固定开销来自 Python 转换"这句话是在**没有任何分项计时**的情况下写出来的,
而且已经写进了设计报告正文。真正定案的 `GAP_TRACE` 是后来才加的。
**结构性的怀疑(CPU 够不够、Python 快不快)可以先排,但机制结论不能先写。**
这两个说法听起来都像"性能问题",区别是前者能靠加参数验证,后者只能靠按代码位置切时间。

**AI 的问题:设计报告里那句错结论是我自己写进去的。**
原句是"Getting below 10 ms requires moving the sample transport out of Python
(C thread or DMA), which is an architectural change"。测量之后这句被推翻:
换 C 线程没有用,因为瓶颈在那次 C 调用**内部**。
已改成"the remaining gap to 10 ms is the per-sample I2S handshake"。
**报告里的机制句和测量结论必须来自同一次实验。**

**AI 的问题:拿 20 秒的数当结论,还跨条件横向比。**
`performance_profile` §1.2 里 L=240 记的是"0.99×、丢 45 块",那是 **20 秒、麦克风音源**。
今天同配置跑三次(25–30 秒、wav 源)全是 **0.83×**。20 秒那趟把起跑阶段算进去了,偏乐观。
这正好是 10-21 那条教训的同一类:**块长不同、窗口不同时,丢块数不能直接比。**

**AI 的问题:只测了 L=480 一档就下了"10 ms 是下限"的结论。**
真正扫完七档才知道下限是 7.5 ms —— 中间还隔着 300 / 264 两档。
**"下限"这个词只有在扫过它两侧的时候才成立。**

**环境的坑:板上的 `python3` 不是 PYNQ 那个环境。**
直接跑会 `ModuleNotFoundError: No module named 'pynq'`,必须用
`/usr/local/share/pynq-venv/bin/python3`。用 `sudo sh -c '... env XILINX_XRT=/usr ...'`
起后台任务时,这一条最容易漏。

**环境的坑:rc=0 不等于文件对。**
把 643 KB 的 json 从板上拉回主机时走 base64,传完必须比 md5;
同一天已经踩过一次"命令回了 0、板上还是旧文件"。

**环境的坑:测量期间网页服务开着,板子静默硬死过一次。**
网口还在、COM6 在、串口一个字没有,等 100 秒没自愈,手按电源。
第二次先停网页服务、开串口录 + `panic_print=31`,跑完正常。
**只有一次对照,不能下结论,但以后测之前先停它。**

   并把原来 §1.2 里 L=240 那行标注为"偏乐观,以 §1.5 为准"。
2. 设计报告里那句错结论改掉,换成"剩下的差距在逐采样 I2S 握手"。
3. 新增低延迟配置 L=360 / NBUF=2:120 秒实测写进报告和性能画像,
   时刻戳原始文件 `data/results/latency_n2_l360_20261022.json`(16050 块)。

【沉淀】

1. **扫参数找下限时,必须扫过下限两侧**,而且每档至少 25 秒 ——
   20 秒会把起跑阶段算进去,给出偏乐观的倍率。
2. **怀疑"某段代码慢"时,按代码位置切时间,不要按"CPU 够不够"排假设。**
   `GAP_TRACE` 那种四段打点是唯一能分清"调用内"和"调用外"的做法。
3. **实时通路里的时间,几乎总落在那一次 C 调用上。**
   这个 IP 没有 DMA,搬样就是 I2S 时钟本身,它跑多快不由块长决定。
4. **报告里的机制句和测量结论要同源。** 先写机制、后做实验,写出来的大概率是错的,
   而且它会顺着被引用到别的文档里。

## 验证边界

- L=360 只跑了 120 秒(16050 块),没有 600 秒。
- L=480 / L=300 / L=264 / L=240 / L=120 那几档各跑 1 次,25–30 秒。
- 全部测量是 `LIVE_SRC=wav`;麦克风源只对 L=480 那一组做过对照。
- 丢块数按本档块长计,不同块长之间不直接比,只比实时倍率。
