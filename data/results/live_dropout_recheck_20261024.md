# 16.2 ms 档丢块复查（2026-10-24）

PLAN §11.14 §3.5 的那件事：10-23 深夜 16.2 ms 和 31.0 ms **两档同时在丢**，
定为 10/24 第一件事。今天查完。

## 结论

**1. 丢块是探针自己造成的。** `drop_probe.py` 默认给 `fir_live.py` 打开
`DROP_TRACE` 和 `GAP_TRACE`：这两样在搬样线程上**每块**多做 3 次
`perf_counter()`、1 次 `time.time()`、2 次 list 追加。实测让每块周期从
7.49 ms 涨到 7.505 ms。16.2 ms 档每块的全部余量正好也就十几微秒，
所以这十几微秒刚好把它压过线。

**2. 关掉插桩，16.2 ms 档 600 秒 0 丢块**（80188 块，缺口 −135.2 ms/60 s）。
判据「60 秒 0 丢块」达成，**演示档维持 16.2 ms**。

**3. 31.0 ms 档 10-23 深夜那 5 块今天没复现**：开着插桩跑 60 秒 0 块，
10-23 那趟 600 秒也是 0 块。所以「两档同时丢」没有可重复的证据 ——
它和 16.2 ms 那几块是同一类：搬样线程被额外的东西打扰了。

## 插桩的代价

| | 每块周期 | 缺口 ms/60s | 实时倍率 |
|---|---|---|---|
| 插桩开 | 7.504 ~ 7.507 ms | +126 ~ +142 | 0.9976 ~ 0.9979 |
| 插桩关 | 7.482 ~ 7.499 ms | −26 ~ −135 | 1.0004 ~ 1.0023 |

差值 0.25~0.30%，60 秒 150~180 ms，折 20 来块 7.5 ms。**每块多花 15~25 µs。**

这十几微秒花在哪：`DROP_TRACE` 每块一次 `time.time()` + 一个四元组 + 一次
list 追加；`GAP_TRACE` 每块三次 `perf_counter()` + 一个六元组 + 一次追加。
两个 list 都长到八千条，分配和 GC 都落在搬样线程上。而 `duplex_block`
每块要 7.404 ms，块周期 7.49 ms —— **余下给 Python 的就这几百微秒，
插桩占掉十几微秒就够越线。**

10 ms 一档（L=480）同一套插桩跑 600 秒 0 块：块越长，同样的开销占比越小。
这也是 21.1 ms 档当备用的理由。

## 两个读数，别看成故障

**1. `lost_blocks` 是瞬时积压，不是累计数。** 定义是
`int(max(0, 墙钟 − n×块长) / 块长)`，积压追平就归零。所以它会涨也会落，
`events` 里 33 条 `delta: 1` 而末态只有 19，不是数错。
**只看 `缺口 ms/60s`（= 1 − 音频秒数/墙钟秒数）和 `lost_total`。**

**2. 缺口是负数 ≠ 欠账。** 负数表示板子按 I2S 时钟采出来的音频比主机墙钟
略快（600 秒那趟：80188 × 360 / 48000 = 601.41 s 音频 / 600.01 s 墙钟）。
这是晶振相对偏差，不是丢块。

## 16.2 ms 档的边界

`demo16_300` 那一趟，我在它跑的时候从主机 SSH 进板子查了几次状态（`df`、
`ps`、读状态文件）。5 分钟累积了 58 ms 缺口（0.02%），末态积压 9 块。
干净复跑（`demo16_300b`）同一时长、同一页面，0 块、缺口 −48.8。

**所以：跑测和演示时，别从主机 SSH 进板子折腾。** 页面自己 150/250 ms 拉一次
不算（`page16_*` 几趟都干净），Jupyter 在 CPU1 上也不碍事（CPU1 只用了 64%）。
要查就等跑完再查。

## 改了什么

`tools/board_debug/drop_probe.py`：

1. 加 `--no-trace`：不给子进程开 `DROP_TRACE`/`GAP_TRACE`。**短配置一律用它。**
2. 两处除零保护：线程表和进程族在同一个循环周期里第一次被发现时，
   `dt_s` 会是 0，`pct()` 会崩。现在 `now > th_prev_t` 才除。
