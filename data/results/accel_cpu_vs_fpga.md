# 加速比：同一块板子上，ARM 核 vs PL 里的核

这是 §2.2 第 ③ 步那条验收判据「加速比可测」的答案。
**核的计时更新于 2026-10-07（核已从 450 拍砍到 28 拍）。**
**加速比那一次对照测于 2026-10-01、脚本是 `board/scripts/compare_cpu_fpga.py`；⛔ 加速比现已过期 —— 脚本改过但还没在板上重跑，下面的 1.4 倍不再有效。**

原始输出两份，**结论用第二份**：

| 文件 | 是什么 |
|---|---|
| `compare_cpu_fpga_run_20261001.txt` | 第一版。CPU 那边跑的是"4 段各自滤波"，**和核不是一个形状**，加速比虚高 |
| `compare_cpu_fpga_run_20261001_fix.txt` | 修正版。CPU 也改成 3 个低通 + 相减，**以这份为准** |

## 为什么必须在这块板子上测

在这之前手上有两个数，不能相除：

| 从哪来的 | 单采样 | 实时倍率 |
|---|---|---|
| 桌面 x86（3 GHz，扛 SIMD） | 0.140 µs | 149× |
| PYNQ 板子上的核（100 MHz FPGA） | 0.28 µs（理论）／板上 0.311~0.4 µs | 55.6×（长块约 67×） |

这两个数不能直接相除 —— 一个是 3 GHz 的通用 CPU，一个是 100 MHz 的专用硬件。
拿它们相除只说明单核时钟差，说明不了"用 FPGA 值不值"。

有意义的对照是**同一颗芯片里的两种做法**：Zynq 里的 ARM 核（PS）和 PL 里的核。
那才是"软件跑不动，所以上硬件"这句话的账。

## 测量条件

- **同一块板子**（PYNQ-Z2 / Zynq-7020），同一段时间，同一串输入。
- **输入**：144000 个采样（3.0 秒 @ 48 kHz），11 根谱线铺在 100 Hz~4 kHz + 底噪。
  故意不用单音 —— 单音在频域只占一根线，压不到什么，两边都不吃力。
- CPU 侧：float64 + `scipy.signal.lfilter`（C 实现），跑 3 次取最快。
- 核侧：Q1.15 定点 int16，跑 3 次取最快，每块 8000 点。

### 「同一套算法」得落实到乘加次数上

只是"结构一样"不够，两边的**乘法次数**必须对得上，否则加速比里混着"核少干了一半活"。

核每采样跑 **3 遍** 193 抽头低通（`for (int b = 0; b < N_LP; b++)`，N_LP=3），
第 4 段靠 `hist[D]` 白拿。所以 CPU 这边也必须是 3 遍低通再加两次减法。

第一版脚本里 CPU 那边写的是"4 段各自一个 193 抽头滤波器"，等于让 CPU 多干 1/3 的活。
修正版两种都跑、都打出来：

    3 低通 + 相减（和核同一个形状）：0.881 秒，6.116 µs/采样   ← 用这个
    4 段各自滤波（旧形状，仅作对照）：1.041 秒，7.232 µs/采样  比上面慢 18%

两条路算出来的输出数值相同（float64 舍入级，实测最大差 3.3e-16），所以换形状不影响别的结论。

## 结果

| | 单采样 | 实时倍率（预算 20.83 µs） |
|---|---|---|
| **ARM 核**（float64，scipy） | **6.116 µs** | 3.41× |
| **PL 里的核**（Q1.15，AXI4-Master） | **0.28 µs**（理论，板上 0.311~0.4 µs） | 55.6×（长块约 67×） |
| **加速比** | ⛔ 过期，`compare_cpu_fpga.py` 尚未在板上重跑 | |

核的实测值和理论吞吐对得上，说明测量干净：

    28 拍 @ 100 MHz = 0.28 µs/采样（理论）
    板上实测          长块 0.311 µs、1000 采样 0.4 µs

也就是说 **Python 写寄存器 + cache 维护的开销很小**，
0.3 µs 上下基本就是硬件本身的吞吐。

两边结果也对得上（精度不同，不能逐位比，只查是不是同一件事）：

    输入有效值 0.10706 ｜ CPU 输出 0.10659（1.00 倍）
    CPU 峰值   0.28627 ｜ 核峰值   0.28625

## 引用这个数必须带上的四条

否则加速比会虚高，而且虚得没有道理：

1. **两边精度不同。** CPU 是 float64 双精度，核是 Q1.15 定点 16 位。
   核做的是**更粗**的活 —— 快的一部分是这一条换来的。这是定点设计的取舍，
   不是 FPGA 白得的便宜。
2. **CPU 那边是 scipy 的 C 实现**，属于「优化过的软件」，不是随便写的 Python 循环。
   但也不是极限 —— 见下面的「这个数还能再压」。
3. **核的耗时里含 Python 写寄存器 + cache 维护**，从上面对得上的理论/实测看它很小。
4. **两边的工作量是对等的**，都是每采样 **579 次有效乘法**（核那边是
   3 × 195 = 585，含 6 次补零）。
   ⚠️ 这条**以前写错过**：原文说"核借了对称性把 193 抽头折叠成 97 对，
   每采样只有 291 次乘法，核比 CPU 少做一半的乘法"。**那是错的。**
   出货那一版 `FIR_FOLD` 是 0（关着的），v13/v18 的编译开关里没有 `-DFIR_FOLD=1`。
   三条证据：
     · csynth 实例表里乘法单元 67 + 67 + 61 = **195 个**，正好每抽头一个；
     · 裸核 DSP = 202 ≈ 195 + 2，折叠的话只要约 99 个；
     · 全仓搜 `FIR_FOLD` 只出现在 v4_* 那批**浮点时代**的旧指令文件里，
       出货路径上一个都没有。
   错的方向是**把公平的对比写成了"我们占了便宜"** —— 改过来之后，
   两边的乘法量确实对等，加速比才有意义（旧的 1.4 倍已过期，见上文）。

## 当初为什么只有 1.4 倍（历史记录 —— 已修好）

> **已修好。** 下表的 450 拍 / 88% 移位是 v13/v18 的**历史**记录：核现在已砍到 **28 拍**
> （编译开关 `-DFIR_SHIFT_CHAIN=1`，默认关、默认路径逐字节不变，**算法一个字没改**），
> 实时余量涨到 55.6 倍（见上文）。下面这一段过程描述保留作历史。

看 csynth 报告的循环表。v13 和 v18 两版**三个数一模一样**：

| 循环 | 在哪 | 迭代 | achieved II | 拍数 |
|---|---|---|---|---|
| `VITIS_LOOP_270_4` | **延迟线整体移位** | 194 | **2** | **398** |
| `VITIS_LOOP_281_5` | 3 个低通 | 3 | 1 | 11 |
| `VITIS_LOOP_356_10` | 4 段压缩 | 4 | 1 | 12 |
| `VITIS_LOOP_263_3` | 每采样一遍 | — | — | **450** |

**398 / 450 = 88% 的拍数花在"把延迟线整体挪一格"上**，而真正的乘法只占 11 拍。

源码里对这一段写的假设是"展开之后 192 次移动变成同一拍的 192 组线，从 192 拍降到 1 拍"
—— **这个假设是错的**，`#pragma HLS UNROLL` 确实在，但 achieved II 还是 2。
原因：`hist` 同时挂着 `ARRAY_PARTITION cyclic factor=5`，被拆进 5 个 RAM 里，
跨 RAM 边界搬数据没法一拍做完。

**所以：这个核不是"算得慢"，是"搬得多"。** 202 个 DSP 铺在片子上，
每采样 450 拍里只有 11 拍在算乘法，乘法器 97% 的时间空着。
（这是 v13/v18 的历史情况 —— 移位那 398 拍后来靠 `-DFIR_SHIFT_CHAIN=1` 去掉了。）

> 这一条是**从综合报告直接读出来的**，不是推测。v13/v18 两版报告可以复现：
> `build/hls/sol_v13_sub_n193/syn/report/fir_multiband_csynth.rpt`（同样四行）。

### 修得掉吗 —— 已经修了

标准做法是**环形缓冲区 + 转动的读下标**：数据不动，每采样只把读指针转一格。
按上面这张表，移位那 398 拍基本可以去掉，每采样会掉到 60~70 拍量级。

**实际是：没改结构，只加了个编译开关就修掉了。** 用 `-DFIR_SHIFT_CHAIN=1`
把延迟线改成移位链，拍数从 450 直接降到 **28**（理论 0.28 µs，板上 0.311~0.4 µs），
**算法一个字没改**，默认关、默认路径逐字节不变。

> 这一段（含"没做"的取舍）留作**历史记录**：当时判断要重跑 csynth/P&R/上板验证，
> 代价不对称；后来发现用编译开关就能拿到同样的效果。

## 这个数还能再压（诚实起见）

CPU 那边**不是极限软件实现**。`scipy.signal.lfilter` 是通用的直接 II 型转置结构，
内层循环没有向量化。手写一版 NEON float32 的 FIR，在 Cortex-A9 上大概能快 3~5 倍
（估计值，**没试过**）。真那样的话加速比会明显缩小。

**所以加速比这个数该怎么用（等 `compare_cpu_fpga.py` 在板上重跑出结果之后）**：

- 可以说：「同一颗芯片上，硬件通路比 scipy 参考实现快 N 倍」——N 必须来自重跑，别沿用旧的 1.4 倍。
- **不能**说：「FPGA 比 CPU 快 N 倍」，更不能说「FPGA 只能快这么点」。

## 板子上的账不在吞吐上

两边的实时倍率是 3.41× 和 55.6×（长块约 67×） —— **都够实时**（预算 20.83 µs/采样）。
光看吞吐，这件事在 ARM 上也能做。

真正拉开差距的是另外三条：

- **确定性。** 核永远是 0.3 µs 上下，不随负载变。ARM 那个 6.1 µs 是"空机器上跑这一件事"
  的数 —— 一旦同时要录音、写文件、跑界面、跑 Jupyter，就会被抢占、被换页，
  延迟尾巴甩出去。助听器最怕的不是平均慢，是**偶尔卡一下**。
- **CPU 腾不出来。** ARM 上跑这一套要吃掉一个核（Zynq-7020 只有 2 个核）。
  核搬到 PL 之后，那两个核能去干别的（音频搬运、压缩参数的自适应调节、界面）。
- **功耗和体积。** 这是助听器场景的硬约束，通用 CPU 顶不住。

这三条才是"上硬件"的理由 —— 报告里该这么写。
