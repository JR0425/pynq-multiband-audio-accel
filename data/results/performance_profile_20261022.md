# 性能线实测（2026-10-22）

四件事：延迟、CPU 占用、功耗、输出质量。全部有产物落在 `data/results/`，
每条都能照命令重跑。

先说结论：

- 稳定档（L=480、NBUF=3）数字延迟 **29.8 ms**，和公式 32 ms 差的那 2 ms
  就是公式里给 codec 留的余量。
- 中间档（L=480、NBUF=2）数字延迟 **19.9 ms**。
- 低延迟档（L=360、NBUF=2）数字延迟 **14.96 ms**、嘴到耳 **16.2 ms**，
  120 秒跑满 1.00×、没有一块超过 25 ms —— 见 §1.5。这是能跑的最短块长；
  再短到 6.25 ms 就开始丢块。
- 压不下去的原因不是 Python 也不是调度，是逐采样的 I2S 握手本身（§1.5）。
- CPU 侧 io 线程吃满一个核（100.3%），dsp 线程 45%；**核本身几乎不占 CPU**。
- PL 动态功耗估算 0.746 W，48 kHz 下 15.5 µJ/采样，但置信度 Low，只能当估算。
- 压缩器关掉时 THD+N 在 −6 dBFS 下 −89.7 dB；四段合成频响全频段 0.0 dB。

## 1. 延迟

### 1.1 怎么量的

不敲 click、不用话筒，直接读流水线自己的时刻戳。

`fir_live.py` 设 `LAT_TRACE=路径` 后，每块记两个时刻：

- io 线程调用 `duplex_block()` 的**开始时刻** —— 这一块被采到的时刻；
- 同一个槽被 io 线程取去播放时的**同一个调用开始时刻** —— 这一块交给 codec 的时刻。

两次都取同一次 `duplex_block` 调用的起点，所以块里每个采样的数字延迟**完全相同**。
差出来的就是这块音频从"进 ADC 缓冲"到"出 DAC 缓冲"真正经过的时间，
不含 codec 模拟端、不含耳机。

```bash
python tools/board_debug/perf_probe.py latency 20
```

每跑完一个配置，`fir_live.py` 的自检会照常跑一遍（`[OK ] 960000 / 960000`
逐位相同），也就是说这些延迟数字是在**结果正确**的同一趟里量出来的。

### 1.2 四个配置

| 配置 | L | NBUF | 公式 ms | 采样块 | 中位 ms | p90 | min | max |
|---|---|---|---|---|---|---|---|---|
| n3_l480 | 480 | 3 | 32 | 2019 | **29.80** | 29.87 | 29.71 | 31.40 |
| n2_l480 | 480 | 2 | 22 | 2022 | **19.86** | 19.92 | 19.78 | 23.00 |
| n2_l240 | 240 | 2 | 12 | 3997 | 9.99 | 10.13 | 9.93 | 17.34 |
| n2_l120 | 120 | 2 | 7 | 6608 | 5.78 | 6.58 | 5.33 | 15.69 |

数字延迟 ≈ `NBUF × L / 48000` 减去本块已经走过的零头，公式里那 2 ms
是给 codec 留的余量，这里的量法不含它。

**后两行不能当稳定档用。** 同一批测量里它们的丢块情况：

| 配置 | 音源 | 20 秒内 |
|---|---|---|
| n2_l240 | 麦克风 | 丢 45 块（0.23 秒），实时倍率 0.99x（**偏乐观，见 §1.5**） |
| n2_l120 | 麦克风 | 实时倍率 **0.60x**，跑了 12.21 秒音频用了 20.24 秒墙钟 |

块长越小，每块固定的开销（队列、`duplex_block` 进出、状态文件）摊到每个采样上
越多。10-21 那轮已经记过 `LIVE_L=8` 时每采样 7.93 µs，就是这个效应。
所以 10 ms 块是这套通路的实际下限附近，想再压只能上 DMA / PL 内闭环，
不是改参数的事。

n2_l480 的 20 秒那趟不足以证明稳定，当晚又补了一趟 120 秒（见 §1.4）。
仍然**没有 600 秒的证据**；10-26 那趟复测如果要换配置，得先按 600 秒跑一遍再说。

### 1.3 声学延迟（10-22 晚补测）

数字法量的是 ADC 缓冲 → DAC 缓冲。从嘴到耳朵之间还有 codec 的 AD/DA 转换与滤波、
耳机、空气、话筒、抗混叠滤波，这一段用声学回环补。

做法（`board/scripts/acoustic_lat.py`）：耳机耳塞贴住板上话筒孔，放一段
500–6000 Hz 线性扫频，**每档连发 6 次、对齐后同步平均**再和模板互相关。
随机房间噪声按 √6 衰减，回波相干相加，所以房间不安静也能测；要求的只是
两次扫频之间别挪动耳塞。三档幅度用来避开削顶和小信号。

```bash
cd /home/xilinx/jupyter_notebooks
echo xilinx | sudo -S env XILINX_XRT=/usr \
    /usr/local/share/pynq-venv/bin/python3 -u acoustic_lat.py
```

| 档位（满量程） | 回波峰值 | 互相关主峰/底噪 | R |
|---|---|---|---|
| 1% | 2065 | 60.8 | 1.23 ms |
| 3% | 1661 | 100.3 | 1.23 ms |
| 10% | 5133 | 102.3 | 1.23 ms |

三档都落在**同一个采样**（第 59 个），主峰/次峰约 5.8。原始波形在
`data/results/acoustic_lat_20261022.npz`。

**怎么确认 1.23 ms 不是别的峰**：扫频自相关在 ±0.29 ms 处有 32% 的旁瓣，
实测在 −0.29 ms 有一个 58% 的峰；主峰仍然是最高且三档一致，1 ms 以前
没有独立峰（0.15 ms 处只有主峰的 2%），所以不是电串扰。1.23 ms 也比
"数字直通串扰"该有的近零延迟大一个量级。

**结论：**

| 配置 | 数字延迟 | + R | 嘴 → 耳 |
|---|---|---|---|
| L=480, NBUF=3（稳定档） | 29.80 ms | 1.23 ms | **31.0 ms** |
| L=480, NBUF=2 | 19.86 ms | 1.23 ms | **21.1 ms** |
| L=360, NBUF=2（低延迟档） | 14.96 ms | 1.23 ms | **16.2 ms** |

嘴到耳分别是 **31.0 / 21.1 / 16.2 ms**，模拟端这 1.2 ms 是实测的，不再是估算。
最后一行是 120 秒实测（§1.5）。600 秒长稳后来补了：稳定档和低延迟档各一趟，
都 0 丢块，见 `soak600_20261023.md` 和 `live_dropout_recheck_20261024.md`；
n2_l480（21.1 ms）这一档仍只有 120 秒。

所以同一套配置再跑 120 秒：块数、实时倍率、丢块、延迟分布一次都记下来。

| 块数 | 2022 | **12071** |
| 音频 / 墙钟 | 20.13 s / 20.13 s | **120.71 s / 120.24 s** |

延迟分布两次一致，说明 19.9 ms 不是一次侥幸。120.71 秒音频在 120.24 秒墙钟里跑完，
没有成片丢音；那 8 块是**单块多等了几毫秒**，不是丢块。

每段的耗时（块长 10 ms 就是预算）：

| 段 | 中位 | 最大 | 占预算 |
|---|---|---|---|
| ① 搬样（io 线程全部） | 9.87 ms | 12.62 ms | 99% |
| ② 过核 + 格式转换 | 1.40 ms | 2.71 ms | 14% |
| ② 里的过核本身 | 0.30 ms | 1.28 ms | 3% |

两条线程绑在两个核上，所以①和②可以同时跑。**瓶颈仍然是搬样**：中位 99%，
最大那一块 12.62 ms 已经越过 10 ms 预算 —— 这就是那 8 块延迟尖峰的形状。
搬样是空转轮询（这个 IP 没有 DMA），它本身就是 I2S 时钟，压不下去。

`data/results/latency_n2_l480_retest_20261022.json`。

**这只能说明"两分钟没问题"。** 低延迟档（L=360 / NBUF=2）的 600 秒长稳在 10-23 补上了，
页面开着、0 丢块（`soak600_20261023.md`），10-24 又复查一次（`live_dropout_recheck_20261024.md`）。
L=480 / NBUF=2 这一档的 600 秒还没有。

### 1.5 块长能压到多短（10-22 深夜）

原来判断"10 ms 块是这套通路的实际下限"，是拿 L=240 的 0.99× 推出来的。
把七档一次扫下来，结论要改：**下限在 7.5 ms，不是 10 ms。** 每档 25–30 秒，
`LIVE_SRC=wav`、`NBUF=2`：

| L | 块长 | ①搬样中位 | 占预算 | 实时倍率 | 结果 |
|---|---|---|---|---|---|
| 960 | 20 ms | 19.72 ms | 99% | 1.01× | 稳 |
| 480 | 10 ms | 9.87 ms | 99% | 1.00× | 稳 |
| **360** | **7.5 ms** | **7.41 ms** | **99%** | **1.00×** | **稳（120 秒复测见下）** |
| 300 | 6.25 ms | 6.18 ms | 99% | 0.98× | 丢 64 / 3950 块 |
| 264 | 5.5 ms | 5.83 ms | 106% | 0.91× | 丢 389 / 4176 块 |
| 240 | 5 ms | 5.93 ms | 119% | 0.83× | 丢 1053 / 4985 块 |
| 120 | 2.5 ms | 3.09 ms | 124% | 0.42× | 严重丢块 |

L=360 的 120 秒复测（`latency_n2_l360_20261022.json`，16050 块）：
音频 120.38 秒 / 墙钟 120.12 秒 = **1.00×**，延迟中位 **14.96 ms**、
p95 15.04、p99 15.30、最大 20.77，**超过 25 ms 的 0 块**（L=480 那档是 8 块）。
自检通过。

**这 0.83× 从哪来 —— 不是 Python，也不是被内核线程抢。** 三个证据：

1. 把每块四个时刻拆开记（`GAP_TRACE`，L=240）：①等槽 0.023 ms、
   ②`duplex_block` 5.93 ms、③放回队列 0.019 ms、④块间空转 0.013 ms。
   **除了那一次 C 调用，其余全在 20 µs 量级。**
2. dsp 那侧一直只占预算的 18–25%，队列里始终有算好的槽 —— 它没拖后腿。
3. CPU0 上有 8 个 `SCHED_FIFO 50` 的内核线程（`ksoftirqd/0` 和一堆 `kworker`），
   搬样线程是 20。把搬样提到 **60**（高于全部内核线程重跑）：5.92 vs 5.93 ms，**没变**。

所以卡在 `duplex_block` 那个逐采样 I2S 握手本身：块长掉到 6 ms 以下时，
它按 I2S 时钟取数的节奏维持不住。要再往下压，得动音频 IP（加深 FIFO 或加 DMA），
是 PL 的活，不是调参数和改 Python 能到的。

> **这条同时更正了 §1.2 里的一行。** 那里写着 L=240「丢 45 块、实时倍率 0.99x」，
> 是 20 秒、麦克风音源那趟的量。今天同样配置跑三次（25–30 秒，wav 源）
> 都是 **0.83×**。20 秒那趟把起跑阶段的块算进去了，偏乐观。引用以本节的数为准。

### 1.6 测的时候踩到的两个坑

- **两个测量脚本漏了 `audio.select_microphone()`**，只调 `configure()`。结果 ADC
  抓的是线路输入，电平恒为 0.7 LSB，看起来像"话筒坏了/U41 没锁上"。补上这一句
  之后本底立刻变成 50–70 LSB（说话几百到上千）。`fir_live.py` 里一直有这句，
  新写脚本时容易漏。
- 第一次跑 `acoustic_lat.py`（网页服务也在跑）把板子**静默硬死**：3 分钟无返回、
  ping 全丢、ARP 无条目、网口仍 Up 1 Gbps、COM6 在，等 100 秒没自愈，手按电源。
  第二次先停网页服务、开串口录 + `panic_print=31`，跑完正常、串口无任何输出。
  **两次差别是网页服务在不在**，但只跑过一次对照，不能下结论；以后测之前先停它。

## 2. CPU 占用

```bash
python tools/board_debug/perf_probe.py cpu 60
```

板上跑 60 秒实时（麦克风音源、稳定档），每秒采一次 `/proc/stat` 和进程/线程
的 jiffies，跳过前 6 秒（还在下 overlay），取 55.3 秒稳态：

| 项 | 占单核 |
|---|---|
| 整机 idle（双核合计） | 27.1% |
| fir_live 进程 | **145.3%**（整机 72.6%） |
| └ io 线程（钉 CPU0，SCHED_FIFO 20） | **100.3%** |
| └ dsp 线程（钉 CPU1，SCHED_FIFO 10） | **45.0%** |
| └ 其余（主线程等） | 0.1% |

怎么读这张表：

- **io 线程吃满一个核是设计使然，不是 bug。** 它整段都在 `duplex_block` 里
  自旋等 I2S，中间不插任何 Python。10-14 的实测是：这一条线程上多 0.09 ms
  的 Python，8 秒就丢 8 块。所以宁可烧掉一个核，也不让调度器在采样中间插进来。
- **dsp 线程的 45% 里，过核只占很小一部分**，大头是 numpy 的 24 位→int16 转换
  （每块 1.4 ms/10 ms）和 Python 层的队列、状态文件。这套转换是可以继续往下
  挪的（比如挪进 C 库），但那要重编 `libaudio_stream.so`。
- **核本身不占 CPU。** 49 cycles/sample @ 100 MHz，480 点一块 = 235 µs 的 PL 时间，
  占 10 ms 块的 2.35%；折成 CPU 侧等价工作量约 0.2% 单核。
  也就是说：加速器把算术拿走了，剩下的 CPU 开销全在通路上，不在计算上。

这个结论和"上 FPGA 是为了省 CPU"的说法要对齐口径：省的是**计算**，
搬运和格式转换仍然要 CPU，而且因为不能被打断，代价是一个核。

## 4. 输出质量

### 4.1 THD+N

走的是和核逐位相同的整数模型（`tools/ref_model_wdrc.py`，csim 对拍 1000/1000）。
相干采样，1 kHz × 0.5 s = 24 个整周期，不加窗。

```bash
python tools/quality_metrics.py --csv data/results/four_band_response_20261022.csv
```

| 条件 | 输入 | THD+N (dB) | 基波 (dBFS) | 最大谐波 (dBc) |
|---|---|---|---|---|
| 压缩器关闭 | 1 kHz −6 dBFS | **−89.7** | −6.0 | −98.8 |
| 压缩器关闭 | 1 kHz −20 dBFS | −77.4 | −20.0 | −82.8 |
| 压缩器关闭 | 1 kHz −40 dBFS | −57.0 | −40.0 | −66.6 |
| 默认无记忆压缩 | 1 kHz −6 dBFS | −26.1 | −7.4 | −26.7 |
| 默认无记忆压缩 | 1 kHz −30 dBFS | −67.0 | −30.0 | −76.6 |
| 默认 WDRC 5/100 ms | 1 kHz −6 dBFS | −20.1 | −7.9 | −22.0 |
| 默认 WDRC 5/100 ms | 1 kHz −30 dBFS | −67.0 | −30.0 | −76.6 |

读法：

- **标准 THD 要用压缩器关闭那一行**（−89.7 dB @ −6 dBFS）。后两组的数字不是
  失真，是压缩器本身在做的时变非线性 —— 它在 −6 dBFS 输入时把电平压到 −7.4/−7.9 dBFS，
  输出当然不再是纯正弦。
- −40 dBFS 那行 −57 dB 是量化底。Q1.15 单采样信噪比上限约 96 dB，但这里
  量的是"所有非基波分量"，低电平输入下噪声占比自然变大。
- −30 dBFS 低于默认阈值（−20 dBFS），压缩器不动作，所以两条都是 −67.0 dB，
  证明阈值以下完全不动作。

交叉验证过这不是分频点造成的：300 / 800 / 1000 / 1600 / 3000 Hz 同一条件
给出 −26~−30 dB（无记忆）和 −17~−20 dB（WDRC），和 1 kHz 一致。
1600 Hz 的 WDRC 输出谱里 3 次谐波 −18.5 dBc、5 次 −23.6、7 次 −27.7，
奇次谐波序列，来源是包络的纹波（attack 时间常数 5 ms，对 1.6 kHz 的半周期
0.625 ms 来说太慢，增益跟着波形抖）。

### 4.2 四段频响

由**核实际用的那张 Q1.17 系数表**算复数响应，不是按浮点设计系数画图。
完整表在 `data/results/four_band_response_20261022.csv`（31 个 1/3 倍频点）。

| Hz | 段0 <500 | 段1 500–1k | 段2 1k–2k | 段3 >2k | 合成 |
|---|---|---|---|---|---|
| 20 | −0.0 | −68.0 | −85.9 | −80.4 | 0.0 |
| 500 | −6.1 | −5.9 | −49.1 | −82.7 | 0.0 |
| 1000 | −50.2 | −6.0 | −6.0 | −81.0 | 0.0 |
| 2000 | −69.7 | −70.8 | −6.0 | −6.0 | 0.0 |
| 10000 | −89.1 | −88.3 | −79.3 | −0.0 | 0.0 |
| 20000 | −99.5 | −83.7 | −89.8 | −0.0 | 0.0 |

- 合成一列**每个点都是 0.0 dB**：相减式分频的幅度重建是精确的，
  分频点 −6 dB 的正确约定也成立。
- 段0 从 20 Hz 起就是平的，段3 到 20 kHz 还是平到 −0.001 dB。
- 段间抑制在分频点附近 40–70 dB，越往高频串得越多（段3 是 96 采样延迟线，
  不是滤波器，上限到 Nyquist 也没衰减）。

**口径：这是核/模型的输出，不是模拟端。** DAC、功放、耳机、ADC 的频响
和失真都不在里面。
