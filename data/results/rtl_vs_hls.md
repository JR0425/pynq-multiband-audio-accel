# 自研 RTL（`src/rtl/`）：和 HLS 那版逐位对拍

这里记的是**自己写的 Verilog 低通 FIR**，以及它跟 HLS 那版核的数值关系。
对照的 HLS 侧数据在 `impl_metrics.md`，软件基线在 `accel_cpu_vs_fpga.md`。

范围说明：文件分三块。第 3~4 节是**单个低通**（`fir_lp.v`），
第 5 节是**多频段前端**（`fir_mb_fe.v`：3 个低通 + 相减 + 4 段综合），
第 9 节是补上 DRC、块模式外壳和 DMA 流式外壳之后的三颗位流上板结果。
第 3~5 节里这两块都没有 DRC、没有每段增益、没有 AXI 外壳 —— 这是刻意的，数值对齐
要一步一步钉，先把算法本身对到逐位，再往上加东西。

---

## 1. 为什么要做，以及为什么第一步求"对"不求"快"

HLS 那版核的瓶颈在"它做不到的事"（延迟线整体移位，449 拍里有 398 拍花在这上面，
见 `impl_metrics.md`）。那个坑已经用一个编译开关绕过去了，但绕过去之后
仍然值得回答一个问题：**同一件事自己写 RTL 能到什么程度。**

但第一步的目标**不是快，是逐位等于参考**。理由是：

> 一个 193 抽头 FIR 的 RTL，最快的失败方式是"跑起来了、数差一点点"，
> 然后花两天找不出差在哪。

所以这一版的验收标准是 **RTL 的输出和参考模型完全一致**，不是"SNR 够高"。

---

## 2. 数值契约（这是整件事的地基）

### 2.1 系数怎么量化 —— 实测反推出来的，不是猜的

拿 HLS 综合出来的系数 ROM（`solution1/syn/verilog/fir_multiband_FIR_LP_V_rom.dat`）
当"标准答案"反推。结论：

    q = round_half_away_from_zero( x * 2^17 )      # 有符号 Q1.17，18 位

**全量验证：579 个系数（3 个滤波器 × 193），不符 0 个。**

两个容易读错的地方：

- 那个 `.dat` 里的数是**有符号 15 位二补数**，不是 16 位。
  `7FFE` 按 16 位无符号读是 32766，按 15 位有符号读才是 **−2**（= `round(−1.7517e-5 × 2^17)`）。
  原因是 HLS 对 `const` 数组做了常量值域裁剪 —— 这批系数实际只落到
  `[-2210, +10943]`，15 位装得下。
  按 16 位读，579 个里有 **305 个对不上**；按 15 位读，**0 个**。
- **正数两种读法一样**（`+32` 在两种读法下都是 `0x0020`）。
  所以只抽几个数、或者只抽正数手工验一验，会以为规则对了。
  要全量比对才暴露得出来。

量化用的舍入是"远离零"，**不是** Python 内置 `round()` 的银行家舍入 ——
后者在 `.5` 的地方会差 1。脚本里用 `Decimal` 的 `ROUND_HALF_UP`（语义就是远离零）。

定点之后三个滤波器的系数和：

    LP500   0.999984741
    LP1000  1.000068665
    LP2000  1.000038147
    （浮点版本都是精确的 1.000000000）

这就是"DC 增益不是精确 1"的来源。

### 2.2 为什么 RTL 可以随便摆加法树

定点 FIR 里**每一步都没有舍入**：

    乘积   16 位 × 18 位 → 34 位有符号。**精确**，一个位不丢。
           而且和 HLS 的 `ap_fixed<34,2>` 完全一致（2 个整数位 + 32 个小数位）。
    累加   全部都是 32 位小数的整数相加，加法本身不舍入。
           溢出检查：|乘积| 最大 32768 × 10943 = 3.59e8，
           195 项求和上界 6.99e10 < 2^39 = 5.50e11，装得进 40 位有符号。
           → **不会溢出**，加法精确，而且**与顺序无关**。
    输出   `acc >>> 17`，再饱和到 16 位有符号。
           `17 = 32（累加器小数位）− 15（输出小数位）`；
           算术右移 = 向下取整，对应 `ap_fixed` 的 `AP_TRN`；饱和对应 `AP_SAT`。

**"顺序无关"这条是支点**：HLS 把乘加拆成 5 路部分和（`FIR_PARTIAL=5`），
RTL 想怎么摆加法树都行，**不需要**去模仿 HLS 的加法顺序。

实测累加器峰值 `|acc| = 1.70e9`，40 位上限 `5.50e11`，**余量 324 倍**。

## 3. 验证链：三段，每段能独立定位问题

    ① 系数规则   RTL 用的表  ←→  HLS 综合出的 ROM        579/0 全中
    ② 参考模型   整数模型    ←→  浮点卷积               SNR 72.5 / 76.3 / 78.2 dB
    ③ RTL 本身   xsim 输出   ←→  整数模型               **1000/1000 逐位相同**

第 ② 段的 SNR 和 `baseline_metrics.md` 里记的整机 75.4 dB 是同一档，说明模型没跑偏。

第 ③ 段的实测结果（1000 个采样，三个滤波器各跑一遍）：

| 滤波器 | 累加器（40 位） | 输出（int16） |
|---|---|---|
| LP500  | 1000/1000 逐位相同 | 1000/1000 逐位相同 |
| LP1000 | 1000/1000 逐位相同 | 1000/1000 逐位相同 |
| LP2000 | 1000/1000 逐位相同 | 1000/1000 逐位相同 |

### 为什么先比累加器、再比输出

输出是"右移 17 + 饱和"之后的结果，会把低 17 位的信息**全部扔掉**。
只比输出的话，"乘法算错一点点"和"移位量写错了"长得一模一样。
先比累加器，错在哪一步就是确定的：

    累加器就不对          → 乘法 / 加法树 / 抽头下标 的事
    累加器对、输出不对     → 只剩移位量和饱和这两行

这也是 RTL 把 `acc_raw` 单独引出来的原因 —— 它**不是给板子用的**，是给这一步用的。

### 饱和规则已经对实了

输出截断/饱和（`acc >>> 17` 再饱和）原来只有 `ap_fixed` 的 `AP_TRN`/`AP_SAT`
文档依据。2026-10-20 用 `sim/model/ref_model_mb.py` 把它做实了：整数模型的输出
和 HLS csim 的 bypass 通路（`data/results/hw_transparent_i16.txt`）逐位比，
**1000/1000 相同**。这条规则不再是"照文档猜的"。

压缩路径（DRC）的定点语义还没对 —— 前端还没加 DRC，加上了再对。

## 4. RTL 结构（`src/rtl/fir_lp.v`）

    拍 0     din_vld 拉高，抽头延迟线 sr 整体挪一格（硬件里就是寄存器间接线）
    拍 0→1   195 个乘法各算各的，每个一个 DSP48，打一拍存下来
    拍 1→2   40 位平衡加法树（8 层），再打一拍 → acc_raw / dout

延迟 2 拍，**II = 1**（源源不断时每拍出一个采样）。
对照 HLS 那版是每采样 **31~49 拍**（历史记录：v19 是 31、v20_gain 含每段增益是 35、
v21_wdrc 加包络是 49；**当前出货的 v25_env_indep 是 36**，见 `impl_metrics.md`）——
同样的 DSP 数，吞吐差 **三十几倍**，
因为 HLS 的 195 个乘法器是被 5 路部分和分批喂的，这里每个乘法器每拍都在干活。

几个刻意的选择：

- **加法树补零到 256 项**（实际只用 195 项）。多出来的 61 项是常数 0，
  会被综合折掉一部分，但确实多花加法器（255 个 vs 理论最少 194 个）。
  第一版先求"对"，非 2 的幂的树后面再说。
- **乘积用 40 位接收**：两个操作数都被符号扩展到 40 位再相乘，取低 40 位。
  因为真积只占 34 位，低 40 位就是它的符号扩展，**精确**。
- **乘法器显式挂 `(* use_dsp = "yes" *)`**。AMD 论坛上有实测：
  常量系数 FIR 会被综合成 LUT 里的 CSD 移位加法，**一个 DSP 都不占**。
  板上只有 220 个 DSP，这条路跑偏了面积会很难看。
  ⚠️ 这只是按经验挂了属性，**还没综合过，没实测**。
- **饱和判据不写死位宽**：右移后高 `(ACCW-15)` 位必须"全 0"（正）或"全 1"（负），
  否则就是超出 16 位有符号的表示范围。抽头数/位宽改了不用改这里。

## 5. 多频段前端（`src/rtl/fir_mb_fe.v`）

3 个低通 + 相减 + 4 段综合，全在同一个模块里。这是"3 拍/采样"这个数字的来源。

### 5.1 它做的运算

    y0 = LP500(x)       b0 = y0
    y1 = LP1000(x)      b1 = y1 - y0
    y2 = LP2000(x)      b2 = y2 - y1
                        b3 = x[D] - y2          D = 96

输出 = b0+b1+b2+b3。定点下相减是精确的，所以 Σb 恒等于 x[D]：不压缩时
输出就是延迟 96 拍的输入。直通检验、以及和 HLS bypass 通路逐位对上，靠的都是这一条。

三个结构上的决定：

- **只有一套 195 个乘法器**，三张系数表按相位轮着喂（P0/P1/P2），不是 585 个。
  板上只有 220 个 DSP，585 个根本放不下 —— 这不是"优化选项"，是唯一能落地的做法。
- **加法树也只有一棵**，三组共用。每拍树上躺着三个不同采样的部分和，互不打架。
- **每个采样 3 拍**。这个数是仿真日志里数出来的，不是从结构推的：
  `[tb] cycles: first=11 last=3008 span=2997 over 999 samples -> 3000/1000 per sample`。

### 5.2 和 HLS 同功能那版的条件对比

对照物是 `v19_shift_chain`（同样是 3 低通 + 相减 + 4 段，没有增益和 DRC），
器件、时钟 10 ns、OOC 都一致；综合和布线各比各的，不跨阶段混比。

| | 自研 RTL 前端 | HLS `v19_shift_chain` |
|---|---|---|
| 每采样拍数 | **3** | 31（OOC 那次记 28） |
| DSP48 | 189 / 220 | 200 / 220 |
| LUT（综合 → 布线） | 6108 → 4559 | 3874 → 3670 |
| FF（综合 → 布线） | 3138 → 3138 | 5540 → 5547 |
| BRAM（综合 → 布线） | 0 → 0 | 49 → 49 |
| WNS @ 10 ns（综合 → 布线） | +3.675 → **+0.585** | +2.441 → **+1.832** |

布线后（place & route，同一份 OOC）：WNS **+0.585**，LUT 4559（4366 逻辑 + 193 移位寄存器），
FF 3138，DSP 189，0 条失败端点。两份报告：
`data/results/rtl_fe_{util,timing}.rpt`（综合）、`rtl_fe_impl_{util,timing}.rpt`（布线）。

DSP 是 189 而不是 195：有几个抽头的三组系数正好都是 0 或 2 的幂，
综合器把这几个乘法折进了 LUT。

**这张表只能和 `v19` 比。** 现在出货的 `v25_env_indep` 是每采样 36 拍，
因为它多了每段增益和峰值包络（v21_wdrc 时是 49 拍，v25 去掉合段循环的假依赖后
降到 36，功能没变）—— 拿 3 拍去比 36 拍等于虚报加速比。

拍数这一项的差距来自结构：HLS 那版要把延迟线一拍一格地搬，195 个乘法器
被 5 路部分和分批喂；这里延迟线整体移位只是寄存器间接线（零逻辑、零拍），
195 个乘法器每拍都在干活。资源上的代价是 LUT 多 2400 个（平衡加法树 + 流水寄存器），
换回来的是 FF 少 2400 个、BRAM 从 49 降到 0。

### 5.3 时序是怎么磨出来的（四轮，每轮只动同一个东西）

    ① 8 层加法树全组合     综合 -4.926 ns   单条组合路 14.6 ns
    ② 树分三段 3+3+2       综合 -2.460 ns   综合器把乘法器和树拼成 DSP 级联，
                                            一拍串 5 个 DSP，11.0 ns
    ③ 同上 + 树禁 DSP      综合 +3.215 ns   布线后只剩 +0.070：每级 3 层
                                            40 位加法，走线占 6 ns
    ④ 树分四段 2+2+2+2     综合 +3.675 ns   布线后 +0.585

第 ② 轮最容易被误读：`report_timing` 里 5 个 DSP48E1 串成一条链，看着像
"乘法器有问题"，实际是综合器把常系数乘法、加法树的几层、以及流水寄存器
一起塞进了 DSP 自带的加法通路（synth 日志里成片的
`register ... is absorbed into DSP`）。给树的加法器挂上 `(* use_dsp = "no" *)`
之后才回到进位链上。

第 ④ 轮之后最差路径换了地方：相位译码 → 195 个 DSP 的系数选择端，
纯走线约 5 ns。把选择信号提前一拍存进寄存器、再挂 `max_fanout` 复制，
也只从 5.03 压到 4.95 ns —— 189 个 DSP 铺满了整片器件，任何全局控制信号
都得走这么远。这是时分复用的固有代价。

### 5.4 改这个模块时最容易踩的两处（都踩过）

- **valid 流水必须跟着流水级数一起改。** 数据全对、只是整体晚一个采样，
  现象是 `rtl[i] == ref[i-1]`，第一眼像"少了一个采样"，其实是 `dout_vld`
  选错了移位位。改流水改了三次，每次都差这一位。
- **x[D] 不能在出数那一拍直接从延迟线读。** 延迟线只在有输入时移位，
  最后一个采样之后不再移，`sr[D+2]` 永远到不了那个采样 —— 最后 2 个采样的
  第 4 段就差了一个 LSB（51，正好是 x 的一个最低位）。改成在移位那一拍抓
  `sr[D]`、走 4 拍流水，排空阶段也能正常流出来。

### 5.5 怎么跑

    bash sim/rtl_sim/run_xsim_mb.sh                          # 仿真 + 9 路逐位对拍
    vivado -mode batch -source sim/rtl_sim/synth_mb.tcl      # OOC 综合
    vivado -mode batch -source sim/rtl_sim/impl_mb.tcl       # OOC 综合 + 布局布线

第 3 条要几分钟。前两条各十几秒/一分钟。

9 路逐位对拍（1000 个采样）：三个低通累加器、四个频段、四段之和、最终 int16，
**全部 1000/1000 位相同**。定位顺序写在 `sim/rtl_sim/check_mb.py` 的输出里：
低通就不对 → 乘法/树/抽头下标；低通对但某一段不对 → 只剩那一减法；
四段对但总和对 → 综合那一级；总和对但输出不对 → 右移量/饱和。

## 7. 工具链上的坑（都是环境的，不是设计的）

**给 xsim 传 plusarg，Windows 上两条路都堵：**

- 走 `bin/xsim.bat` + `cmd /c`：cmd 会把整串参数**重新解析一遍引号**，
  `-testplusarg "IN=D:\...\in_q15.mem"` 到 xsim 手里变成裸的
  `D:\...\in_q15.mem`，报错 `Expected a switch but found D`，
  看着像参数名拼错了。
- 直接起 `bin/unwrapped/win64.o/xsim.exe`：引号是保住了，但缺
  `libxsimverific.dll`（那个 DLL 是靠 `.bat` 设 PATH 才找得到的），起不来。

→ **结论：命令行上不要传路径。** 运行脚本把要用的文件复制成固定名字
（`in_q15.mem` / `coeffs.mem`），模块和测试台只认相对名。
代价是模块不能同时例化三份（会抢同一个 `coeffs.mem`）—— 现在一次跑一个，正好不需要。

**`MSYS_NO_PATHCONV=1` 和 `cmd //c` 不能一起用。**
加了那个环境变量，`//c` 不再被转成 `/c`，cmd 当成"没有参数"直接进交互模式，
日志里只留一行 cmd 横幅，看起来像"命令跑过了"。

**`$fwrite(..., "%0d", dout)` 默认按无符号打印**，负数会变成 65535 这种数。
必须写 `$signed(dout)`。这条不报错，只是对拍时显示成"到处都不对"。

**测试台里的计数器坏过一次**：`got = 0` 放在了喂数循环**之后**，
而 `dout_vld` 是 `din_vld` 延两拍，喂数一开始它就在计数 ——
那 996 个被清零冲掉，只留下排空那几拍，打印
`collected 4 outputs (expected 1000)`。**而输出文件本身是好的**，
所以逐位比对那边同时报 1000/1000 全同。两个数字互相矛盾，
第一反应是"比对脚本读错文件了"，实际是计数器在说谎。
**一个会说谎的诊断数字比没有更费时间。**

## 8. 还剩什么

- `fir_mb_fe` 的输出截断/饱和规则已经和 HLS csim 的 **bypass** 输出逐位对上；
  压缩路径由 `fir_drc4` 补上（见 §9），和 HLS 同一套定点规则，但**黄金值来自
  Python 模型，不是 HLS 自己吐的**。
- 块模式外壳、DMA 流式外壳、抓取位流都已上板（§9、§9.7）。块模式那张 46× 的表
  大头是 PS 逐字 MMIO；换 DMA 后 25.7 M 采样/秒（约 536×），核内上限 33.3 M。
- "3 拍/采样"是核内的数，上板实测整块 3.002 拍/采样（4800 点 14407 拍），
  DMA 版 14408 拍 —— 外壳的 LOAD 段没有额外暴露成墙钟。
- DRC 通路没有和 v25 逐位比（参数来源不同），原因见 §9.6；和 v25 并排对拍的是 bypass 通路。
- 单低通那版（`fir_lp.v`）已经是历史版本，前端取代了它；
  它的验证脚本留着，因为逐抽头对系数表那一环还在用。

## 9. DRC 与 AXI 外壳（2026-10-25）

前端补上压缩路径、套上块模式外壳之后，RTL 这一线才算和出货 v25 同功能。

- `src/rtl/fir_drc4.v`：四段各一套「验配增益 + 包络压缩」。定点契约照
  `src/hls/fir_types.h`：`acc_t` Q8.32、`drc_t` Q2.22、`gain_t` Q7.8，
  每次赋给窄类型都是向负无穷取整再饱和（AP_TRN + AP_SAT）。
  出厂参数写成模块参数（thr=419456 / ratio=2936064 / atk=17408 /
  rel=896 / gain=256），四段可各自不同。
  代码注释里记了一条踩过的事：`drc_t × gain_t` 收回 Q2.22 是右移 **8** 位，
  不是 `FRAC_DRC-8`；写错时输出整体小 64 倍，不报错，只是数不对。
- `fir_rtl_shell.v` 的 `ctrl[17]` 选路：0 = 只过前端（= v25 bypass），
  1 = 整条压缩路径。`drc_en` 在 start 上升沿锁存，一块之内不切换。
- 外壳是 AXI-Lite + BRAM 的块模式（LOAD / RUN / DRAIN 三段），
  不是 PLAN §11.14 §4 首选的 DMA + Stream —— 没有板子，那条链一次没跑过。

**跑法：**

    bash sim/rtl_sim/run_xsim_shell.sh                   # 1000 点，bypass
    bash sim/rtl_sim/run_xsim_long.sh 4800               # 4800 点，bypass，出黄金对
    DRC=1 bash sim/rtl_sim/run_xsim_long.sh 4800         # 4800 点，压缩路径
    bash sim/rtl_sim/run_xsim_drc4.sh                    # 只测 DRC 单元

`run_xsim_long.sh` 的第 4 个参数是黄金目录后缀，用来并存不同音源。
例如 `DRC=1 bash run_xsim_long.sh 4800 <abs>/ab_board_in.wav 62131 _loud`
写进 `golden_n4800_drc_loud/`。音源路径必须给绝对路径 —— 脚本会先 cd 进工作目录。

**结果（n=4800，100 MHz）：**

| | bypass | DRC |
|---|---|---|
| 拍/采样 | 3.002（14407 拍） | 3.004（14417 拍） |
| 和 xsim 前端逐位 | 0/4800 | 0/4800（两份音源） |
| 连跑两块 | 0/4800 | 0/4800 |

DRC 多 10 拍是压缩器流水延迟（9 级 + 1 拍写回），吞吐不变。

`golden_n4800_drc_quiet/`（noisy_voice）里**压缩器没有启动**：包络最高 205844，阈值
419456。逐位相同只说明直通没弄坏、定点取整对。要证明压缩器在动得看
`golden_n4800_drc_loud/`：47% 的段-采样衰减量 > 0，rms 降 1.77 dB，峰值
26088 → 24544，和 PLAN §3.2 记的「出厂设置压 1.6~2.1 dB」一致。
**写对拍结论时先确认包络真的进了门限**，否则测的是空集 —— 这条和 §3.2
那个「门限以下判据一直在测空集」是同一类错。

这不是空话：把 DRC 改成 8 级流水时写错了两处（见 §9.1），**1000 点那份单元 tb
照样 1000/1000 全对**，因为那份音源的包络根本没进门限。只有 `_loud` 那份才
把错误显出来。

### 9.1 8 级流水踩的两个坑

`fir_drc4.v` 第一版是 4 级、全程 64 位，xsim 全对但实现后 **WNS = −11.397 ns**
（最差路径 40 级逻辑、20.7 ns）。改成 8 级、按需留位宽之后又踩了两个：

- **拼接是无符号的。** `{{8{band[39]}}, band} >>> 10` 里的 `>>>` 实际是逻辑
  右移：−532 变成 +274877906943，直流偏置一下子顶到饱和。要先把拼接落到
  `wire signed` 上再移位。
- **`ATK` 不能截成 15 位。** `localparam signed [14:0] ATK15 = ATK[14:0]`，
  15 位有符号上限 16383，ATK=17408 截完是 −15360，包络每步都在减、永远停在 0。
  现象是"压缩一点都没动"，和阈值设太高完全一样。

两个错都只在"压缩器真的启动"时才表现出来，也就是必须用 `_loud` 那份对拍。

### 9.2 综合里的一个坑：整颗 FIR 被当死存储删掉

BD 综合日志里 191 行 "Generating DSP"、初步映射表也对得上，最后网表里
DSP48 = 0、RAMB = 0，`wr_en`/`wr_idx`/`dout_reg`/系数 ROM 全不见，util 只剩
PS7 + AXI 骨架；而单独综合同一份 RTL 是 197 个 DSP。
根因是输出那块 BRAM 的 B 口写数据就是 FIR 输出，A 口那侧只有 AXI 从机在读，
综合判成可删的存储，写口整条反向剪到 `f_dout`。
给两块 BRAM 加 `DONT_TOUCH` 后 DSP = 197、RAMB = 20。
这条约束由 `board/overlay/build_rtl.tcl` 自动生成，并且综合后
`$s_dsp < 100` 会直接报错，不再静默出一颗空壳位流。

### 9.3 整机时序：拆开 DRC 最后一级之后 WNS = +0.151 ns

§5.2 那个 **+0.585 ns 是裸核 OOC** 的数，和整机不是一回事。把 PS7、axi_interconnect、
两块 axi_bram_ctrl、两个 axi_gpio、外壳、前端、DRC 塞进同一个工程重新布局布线。
第一次整机 WNS = −0.140（44 个失败端点全在 DRC 的 `p_gr_reg`），把
`gr_p >>> FRAC_DRC` 单独打一拍（流水 8 → 9，total_cycles 14416 → 14417）后：

| | 裸核 OOC | 整机（9 级） |
|---|---|---|
| WNS | +0.585 | **+0.151** |
| TNS / 失败端点 | 0 | 0.000 / **0**（共 20180） |
| WHS / 失败端点 | — | +0.057 / 0 |
| WPWS | — | +4.020 |
| DSP48 | 189 | 197（89.55%） |
| Slice LUT | 4559 | 7734（14.54%） |
| Slice FF | 3138 | 5663（5.32%） |
| BRAM Tile | 0 | 19（13.57%） |

**那 44 条失败路径一次清干净了。** 最差一条从 `p_gr_reg` 换成了复位扇出：

    u_shell/fe_rst_reg/C → u_fe/sr_reg[153][14]/R
    9.236 ns = 逻辑 0.456 + 走线 8.780，0 级逻辑

全是走线，说明剩下的余量问题不是逻辑深度，是 `fe_rst` 这一个高扇出复位网横穿整片
的布线延迟。现在 +0.151 已经过，不必再动；真要再收，办法是给复位加
`MAX_FANOUT` 复制，而不是继续拆流水。

前端侧从第一次整机起就干净：`u_fe` 起见最差 +0.496，top-400 里 0 条起点在 `u_fe`。
所以"189 个 DSP 铺满、控制信号纯走线 5 ns"不是整机的主要矛盾。

现出的 `board/overlay/fir_rtl.bit`（md5 `0dc44bc49bdfed9cc5376b43f547112e`，
hwh `30f8175ebf8463dfd7f56cb4053c2f17`）就是这份工程，**合时序**。

报告文件：`board/overlay/fir_rtl_timing.rpt`、`fir_rtl_util.rpt`
（都从 `impl_1/fir_rtl_wrapper_routed.dcp` 重新 report 出来的）。

### 9.4 AXI-Lite 外壳上板才暴露的两个错

位流加载正常、外壳算得对（14417 拍、n_out=1000、无溢出），但两块 BRAM 读回来
恒为 `0x00000008`，写进去的值一个都读不回。同一轮里 `axi_gpio` 读写完全正常，
所以问题只在 BRAM 那条路。两个错都不在 RTL 里，在 BD 里，xsim 也看不到
—— xsim 跑的是 RTL 源文件，根本不过 BD。

**① `axi_bram_ctrl` 的 `SINGLE_PORT_BRAM` 填了 0。** 填 0 时控制器认为 BRAM 两个口
都归它用：写走 A 口，**读走 B 口**。而本项目 B 口预留给自研外壳，控制器那侧的
`bram_rddata_b` 没人接，Vivado 就把它绑成常量。生成的 wrapper 里能直接读到：

    .bram_rddata_b({1'b0,...(28 more)...,1'b1,1'b0,1'b0,1'b0}),   // = 32'h00000008

和板上读回来的 `0x00000008` 一字不差。改成 `SINGLE_PORT_BRAM {1}` 后回读走
`bram_rddata_a`，接的是 BRAM 的 `douta`。

**② A 口地址被当字地址接。** `axi_bram_ctrl` 的 `bram_addr_a` 是 15 位**字节**地址，
`blk_mem_gen` 的 `addra` 是 13 位**字**地址。用 `connect_bd_intf_net` 接 `BRAM_PORTA`
接口时，Vivado 报 `[BD 41-2384] Width mismatch` 后只连低 13 位：

    .addra(in_pa_ADDR[12:0])

等于拿字节地址当字地址用：采样 k 落到第 4k 个字，2048 点之后回卷。改成一根根
连普通引脚 + `xlslice` 取 `[14:2]`。顺带一个名字坑：控制器的写数据脚叫
`bram_wrdata_a`，不是 `bram_din_a`（`get_bd_pins` 匹配不到会直接
`[BD 41-701] connect_bd_net requires at least two pins`）。

`bram_we_a` 是 4 位而 `blk_mem_gen` 的 `wea` 是 1 位（`Use_Byte_Write_Enable`
没落下去），BD 会报 `[BD 41-2383]` 宽度不符并只接最低位。这对 PS 侧 32 位整字写
（`WSTRB=0xF`）正好是对的，没有改。

**构建侧还有一个和工程无关的坑**：`create_bd_design` 偶发报
`[Ip 78-89] couldn't read file "testbench.tcl"`。不是脚本的问题，是内存压力下
Vivado 打开自身 tcl 失败（前一天连跑四次里前三次都是这类错）。删掉
`build/vivado/fir_rtl/` 整个重建即可。

### 9.5 上板实测（2026-10-25，PYNQ-Z2 板子上跑 `board/scripts/rtl_probe.py`）

环境：`fir_rtl.bit` 是 §9.3 那颗（WNS +0.151），PS 侧 Python 3 + PYNQ 2.7，
FCLK_CLK0 = 100 MHz，块数据走 AXI-Lite 逐字 MMIO。不是出货的 `fir.bit`。

**拍数和吞吐（判据 ③）。** 三种块长，两种模式：

| 块长 n | 模式 | total_cycles | 拍/采样 | 核内时间 |
|---|---|---|---|---|
| 1000 | 仅前端 | 3007 | 3.010 | 0.030 ms |
| 4800 | 仅前端 | 14407 | 3.002 | 0.144 ms |
| 8192 | 仅前端 | 24583 | 3.001 | 0.246 ms |
| 4800 | 前端+增益+WDRC | 14417 | 3.004 | 0.144 ms |

和外壳的公式 `3×(n−1)+10`（含 DRC 再 +10）逐位吻合：3007 = 3×999+10，
24583 = 3×8191+10，14417 = 3×4799+10+10。**8192 是 BRAM 满深度，没有溢出
（`stat_hi` 的 overflow 位一直为 0），也没有回卷** —— 说明 §9.4 那个地址修复是对的。

核内 3.00 拍/采样 = **33.3 M 采样/秒 @ 100 MHz**。

**逐位对拍（判据 ①）。** 两份黄金向量都过：

- 仅前端，4800 点：和 `golden_n4800/rtl_fe_out.txt` **0 点不同**
- DRC，4800 点（响音源）：和 `golden_n4800_drc_loud/rtl_fe_out.txt` **0 点不同**
- 仅前端另外用「输出 = 输入延后 96 拍」自校验：n=1000/4800/8192 分别 904/4704/8096 点全同

xsim 的结论在板上原样成立，包括压缩器真的启动的那份音源。

**块间可复现（判据 ④）。** 每档连跑两次，输出逐位相同、拍数相同。

**整块往返的墙钟（这是"整机吞吐"能报的口径）。**

| 块长 n | 写 BRAM | 核运行 | 读 BRAM | 合计 | 折算成 48 kHz 音频 |
|---|---|---|---|---|---|
| 4800 | 0.70 ms | 0.78 ms | 0.68 ms | **2.17 ms** | 100 ms 音频 → 约 46× 实时 |

`运行` 那一列含 0.2 ms 的状态轮询粒度，看核内时间更准。真正的大头是 PS 逐字
MMIO 搬运：8192 字写 1.17 ms、读 1.03 ms，合 140 ns/字 —— 这是 Python + `/dev/mem`
的逐元素开销，不是 AXI 带宽。**所以这张表只能说明"这条路能跑、能对"，不能当
连续流的吞吐**；连续流要走 DMA，那是没做的那一版。

**判据 ⑤（和出货 v25 同源对拍）在 §9.6 单独记。**

**越界块长的守卫**（`board/scripts/rtl_edge.py`）。外壳只在 `S_IDLE` 认 start，
进来先查 `n == 0 || n > MAXN(8192)`，命中就置 overflow、直接 done、不碰 BRAM。
板上实测 n=0 和 n=8193 都是立刻 done、`overflow=1`、`n_out=0`，缓冲里的图样没被改动；
之后紧接着跑一块正常 1000 点仍然对（冲激 500 → 596，差 96 拍）。

读状态寄存器时要注意两件事：`total_cycles` 只在**跑完**时才刷新，走 overflow
那条路它保留的是上一块的值（读到 `0` 不代表这块用了 0 拍）；`start` 在忙时来的
边沿被丢弃，不会排队 —— 离线搬块这条路上 PS 必须等 `done` 再起下一块。

**同一音源走两条通路（板上）**。同一份 `in_q15.mem`（noisy_voice）先 bypass 再
`drc_en=1`：

| | cycles | rms | peak | min |
|---|---|---|---|---|
| bypass | 14407 | 1540.3 | 7478 | −8684 |
| DRC | 14417 | 1540.3 | 7477 | −8685 |

4800 个采样里 4799 个不同、**最大差 1 LSB**，rms 比 1.0000（0.00 dB）。
这说明两件事：增益级确实在数据通路上（不是绕过），出厂增益 256 = 1.0 且这份音源
没进门限时，两条路的差别只剩定点取整 —— 和 xsim 那边「quiet 那份压缩器没启动」
的结论一致。

### 9.6 判据 ⑤：和出货 v25 同源逐位对拍（2026-10-25 下午）

判据 ⑤ 的原文是「同音源下，与出货 v25 的 bypass 输出逐位相同」。
§9.5 那轮只做到「两侧都与 xsim 黄金向量一致」，是传递论证，不是并排对拍。
这一轮把两个 overlay 放进同一个进程，先后加载、跑同一份 `in_q15.mem`：

    Overlay("fir_rtl.bit")  → 外壳 ctrl[17]=0（仅前端）          → y_rtl
    Overlay("fir.bit")      → FirMultiband.run(..., bypass=True) → y_v25

结果：

| 项 | 结果 |
|---|---|
| 全长逐位（4800 点） | **0 点不同，最大差 0 LSB** |
| RTL 输出 == 输入延后 96 | 4704 点全同 |
| v25 输出 == 输入延后 96 | 4704 点全同 |
| 两侧各自 vs xsim 黄金向量 | 0 点不同 / 0 点不同 |

v25 那一侧实测 4800 点 1.825 ms（0.380 µs/采样），和归档的 36 拍
（0.367 µs/采样）对得上 —— 先确认跑的是 v25 而不是 v19，再谈对拍结论。
RTL 那一侧 14407 拍，和 §9.5 的表一致。

**两侧都先各自和 xsim 黄金一致、再互相比对**，这是有用的一步：如果只做并排比对，
两边同时错成一样也会显示「逐位相同」。运行脚本是一次性的（不进仓库），
两个 overlay 必须在同一进程里先后加载才能在无 codec 的条件下拿到同源输出。

**为什么没有顺手把 DRC 通路也对 v25 比。** 两边参数来源不同：v25 的阈/比/增益/
起停时间是运行时写寄存器的，默认 attack/release = 0（不启用平滑）；
RTL 的 `fir_drc4` 是编译期参数（atk=17408 / rel=896，即启用平滑）。
要比就得先算出与编译期系数逐位对应的毫秒数，`ms_to_coef` 的舍入不一定回得来。
所以 DRC 那侧的黄金值仍然只对 Python 模型，不宣称和 v25 逐位相同。

### 9.7 连续流版本：DMA + AXI-Stream（2026-10-25）

§9.5 那张 46× 的表量的是 PS 逐字搬块，大头在 Python + `/dev/mem`，不是核。
把搬运换成 AXI DMA 之后是另一颗位流 `fir_rtl_dma.bit`：
`axi_dma/M_AXIS_MM2S → fir_stream_shell/S_AXIS`，`M_AXIS → axi_dma/S_AXIS_S2MM`，
PS 只在起头和等结束。外壳 `fir_stream_shell` 里没有任何 AXI 逻辑，只做 valid/ready。

**两版轮跑**（各自单独加载，同一份 `in_q15.mem` 4800 点）：

| 项 | 块模式 `fir_rtl.bit` | 连续流 `fir_rtl_dma.bit` |
|---|---|---|
| bypass 拍数 | 14407 | 14408 |
| DRC 拍数 | 14417 | 14418 |
| 两版输出 | — | 逐位相同，最大 0 LSB |
| 与 xsim 黄金 | 0 点不同 | 0 点不同 |
| 4800 点整块墙钟 | 2.17 ms | 0.90 ms |

差的那 1 拍是计时终点不同，不是核变了：块模式停在前端 `dout_vld` 那一拍，
流式要等这拍数据进了输出 FIFO、下一拍被 DMA 收走才停表（`fifo_cnt` 用的是寄存后的
`wptr`，写入当拍不含这一条）。

**持续吞吐**（`rtl_dma_probe.py --stream 10`，65535 点连发十次，先空跑一块去掉冷启动）：

    每块 2.55 ms = 核内 1.97 ms + DMA 与驱动 0.58 ms
    25.7 M 采样/s，约 536 倍实时 @48 kHz
    核内上限 33.3 M 采样/s

差的那 10 M 采样/s 是两个 AXI 通道在 DDR 上的读写。数字要这么报，别把 536×
和 46× 并列 —— 两者测的不是同一件事。

**两个把数报错的坑。**

- `axi_dma` 的 LENGTH 寄存器只有 14 位（`c_sg_length_width` 默认），19200 字节
  被截成 2816 字节，**IP 不报错**，4800 点只回来 704 个。PYNQ 驱动本来按
  `2^14-1` 卡住并给了提示，当时却把 `ch._max_size` 改成 `2^26-1` 绕过了它 ——
  等于把唯一的提示拆了。修法是在 tcl 里把 `c_sg_length_width` 设成 26 重编，
  驱动一个字不动。
- 第一版持续吞吐量成 15.6 ms/块（86×），和单次 1.59 ms 对不上。分阶段计时才看清：
  Cortex-A9 上那几句 numpy 整块校验就 5.7 ms，比一次传输还长；`wait` 前那 1 ms
  宽限循环也原样进了墙钟。改成 O(1) 状态检查 + 50 µs 宽限、并把逐点校验挪出
  计时区间（`verify=False`）之后才是 2.55 ms。

**握手时序（拔高档的图）。** 单独一颗 `fir_rtl_dma_cap.bit`，在 DMA 与外壳之间、
外壳与 DMA 之间各串一个直通监视器，接自研抓取器 `fir_wave_cap`：每拍记一条
32 位记录，输入输出各 1024 字 BRAM，PS 经 AXI BRAM 控制器读回。
`board/scripts/rtl_wave_probe.py` 抓两次（块头 / 块尾），出 `report/img/wave_timing.png`。

    块头  342 次输入握手，相邻间隔全部 = 3 拍（3 拍占 100%），第一个输出在触发后第 10 拍
    块尾  触发 = 带 TLAST 的输入握手，输出 TLAST 在触发后第 8 拍，输出共 4 次握手
    群延迟 前 96 个输出采样全 0，第 97 个起非零

最后一条是这张图最容易读错的地方：**96 采样群延迟不体现在拍数上**。
外壳每块开头复位前端延迟线，进多少出多少，输入输出 TLAST 几乎对齐，
延迟在数值里。按「输出比输入晚 288 拍」去验会读出一个不存在的错。
这颗位流只出图不出数（监视器让组合路径多一级），拍数吞吐一律引 `fir_rtl_dma.bit`。

**抓取器踩的三个坑（都是"图全零/全错"级的）。**

- `xlconcat` 的 **In0 是最低位**。`done` 接到 In1，板上读到 `cap=0x80000000`。
- `blk_mem_gen` 的 **`clka`/`clkb` 漏接**：BD 照样 validate 过、位流照样出、
  `done` 照样置起，但 PS 写不进也读不回、抓到的全是 0。判定方法是绕开抓取器，
  让 PS 自己往 A 口写 0xDEADBEEF 再读 —— 读到 0 就说明是 BRAM 通路，不是位序。
- 同一个 blk_mem_gen 的 B 口还有一根 `web`，只拉高 `enb` 不会写进去。
  这里 `web` 是 1 位（`Byte_Size` 没落成 8），接 4 位会被截成最低位，
  看着能过、实际只在 WSTRB=0xF 时写。

**为什么没用 Vivado 的 ILA。** `ila` v6.2 的 component.xml 里只有 JTAG 侧接口
