# 无记忆压缩档（atk=rel=0）的 THD+N 实测（2026-11-02，PYNQ-Z2 板上）

位流 `628b75b3d7a13015a69125fb8ac2d228`（与交付位流一致），服务 `fir-pl-webui.service`
在线（`fir_pl_live.py` PID 706）。探针 `board/probes/thdn.py`，1024 点 Hann 窗，
每档抓 8—12 帧、只保留进核 THD 低于 0.5% 的干净帧取中位。

## 为什么测这一档

37.24% 的机制是 `fir_drc4.v` 的减法式压缩 `y = sign(a)·max(0, |a|−gr)`：gr 由 5 ms
包络给出、在一个周期内近乎常数，零交叉附近 |a| < gr 的部分被整段挖成 0。这条路的
修法（乘法式增益）被 DSP 和时序挡着。但 RTL 里已经有一条现成的分支：`atk` 与 `rel`
同时为 0 时，包络直接取瞬时 |a|（`fir_drc4_chan` 的 `use_wdrc_r==0`，对应 HLS 的
`drc()`），减法变成逐采样按比例，死区消失。两个参数都是运行期寄存器，改预设即可，
不用改 RTL、不用重新布线。

## 三档对照（同一次会话，同一台板、同一串音源）

音源 `wav/tone1001_full.wav`，峰值 32000，经 −32 dB 播放衰减后入核峰值 803。

| 参数档 | 有记忆 5 ms / 100 ms | 无记忆 0 / 0 | 出核峰（有 / 无） |
|---|---|---|---|
| +24 dB / −40 dBFS / k 0.5 | **37.25%** | **3.37%** | 7224 / 6678 |
| +24 dB / −20 dBFS / k 0.7 | **9.32%** | **5.79%** | 11195 / 10866 |
| +22 dB / −10 dBFS / k 0.7（默认） | 0.093% | 0.092% | 10110 / 10110 |

默认档压缩器不启动，两档都是输入本底，换模式没有影响。

逐位整数模型 `sim/model/ref_model_wdrc.py` 对同样三档的预测是 3.45% / 5.82% /
0.08%，峰值 6676 / — / —，和板上差 0.1 个百分点以内、峰值差 2 个计数。

## 判读

1. 深压档失真降了 11 倍（37.25% → 3.37%），中档降 1.6 倍（9.32% → 5.79%）。
   压缩越深，这条分支的收益越大——因为它去掉的正是随压缩深度变宽的死区。
2. 出核峰值反而更低（7224 → 6678，−0.7 dB），不是"压缩变弱"。
   rms 上的增益衰减略少（模型里 −6.2 → −5.5 dB）：低电平段不再被整段减掉，
   峰值段照旧压。
3. 三次谐波从 −10.8 dBc 降到 −34.0 dBc，偶次谐波仍在 −80 dBc 以下，
   没有引入新的失真类型。
4. 这一档丢掉的是 attack/release 的时间常数：增益逐采样跟着波形走，
   本质更接近无记忆波形整形，而不是有起落时间的压缩器。

## 这条数不能说明什么

单音 THD 只说明它在这个激励下的非线性。无记忆压缩器在语音和音乐上的表现
（瞬态、互调、"泵动"的有无）单音测不出来，必须在板上用耳机听一次再决定能不能作为
预设发出去。听感没定之前，这组数只能作为"候选档"记着。

## 复现

```bash
# 1) 设参数（/api/tune 每次发全五项）
curl -X POST http://192.168.2.99:8080/api/tune -H "Content-Type: application/json" \
  -d '{"gain_db":[24,24,24,24],"thr_db":[-40,-40,-40,-40],"ratio":[0.5,0.5,0.5,0.5],"attack_ms":[0,0,0,0],"release_ms":[0,0,0,0]}'

# 2) 量
python board/probes/board_ssh.py --sudo \
  "cd /home/xilinx/dma_exp && XILINX_XRT=/usr /usr/local/share/pynq-venv/bin/python3 -u \
   thdn.py --wav wav/tone1001_full.wav --loop 8 --settle 6 --tag deep_memoryless"

# 3) 恢复默认预设并把音源切回麦克风
curl -X POST http://192.168.2.99:8080/api/play/stop
```

注意 `thdn.py --loop 3` 有时会把播放起始的斜坡帧算进中位数，读出一个虚高的值
（本次 −20 档先测出 85% 和 17.9%，换 12 帧后全部干净、稳定在 5.79%）。
帧里带 `in_pct`，低于 0.5% 才是可用帧。
