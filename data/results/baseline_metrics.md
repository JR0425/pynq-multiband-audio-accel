> 2026-10-08 在板上重测加速比：**19.5 倍**。
> 再往前：2026-10-07 更新核的计时（2026-10-01 重做的基线）。这是 W2 的交付物之一。
>
> 上一版（9/25）参数是旧的：44100 Hz、边界 300/600/1000、4 段各自 `firwin`。
> 现在硬件和软件都是**相减式 4 段 / 边界 500/1000/2000 / 193 抽头**，

## 一、三套数，别混着用

同一个算法，在三个地方跑过。**它们不是一回事**，报告里引用必须说清是哪一套：

| # | 在哪跑的 | 单采样 | 实时倍率 | 用来回答什么问题 |
|---|---|---|---|---|
| A | 桌面 x86（Windows 10 / Miniconda，3 GHz 左右） | 0.140 µs | 148.6× | "纯软件要多久" —— 只作参考 |
| B | **板载 ARM**（Zynq-7020 的 PS，667 MHz） | 6.199 µs | 3.36× | 和核**同一颗芯片**，这才是加速比的分母 |
| C | **PL 里的加速核**（100 MHz） | 0.317 µs（理论 0.280 µs） | 65.69× | 加速比的分子 |

**48 kHz 的实时预算是 20.83 µs/采样。** A、B、C 三个都在这条线以内。

**加速比：B vs C = 19.5 倍**（2026-10-08 在板上重测）。
**A 和 C 不能相除** —— 一个是 3 GHz 通用 CPU，
一个是 100 MHz 的 FPGA，说明不了"用 FPGA 值不值"。
详细论证和必须带上的四条免责声明见 `accel_cpu_vs_fpga.md`。

## 二、A：桌面 x86 逐段耗时

素材：`data/audio/real_voice.wav`，10.58 秒 @ 44100 Hz，重采样到 48000 Hz（507905 个采样）。
脚本：`src/python/multiband_baseline.py`，重复 3 次取最快。
环境：Python 3.9.12 / NumPy 2.0.2 / SciPy 1.13.1 / Matplotlib 3.9.4 / SoundFile 0.13.1。
同一脚本在另一台机器上用 `--repeat 5` 跑过，两次分别 100.7 ms 和 89.5 ms ——
**桌面计时对机器和当时的负载都很敏感**，下面这张表给的是量级和比例，不是可移植的基准。

| 阶段 | 耗时 | 占处理时间 | 备注 |
|---|---|---|---|
| a. 读入 + 混音 + 去直流 + 重采样到 48k | 13.0 ms | — | **含磁盘 I/O**，不和下面几项相加 |
| b. 3 个 193 抽头低通 | 39.7 ms | 56% | 和核里同一个循环 |
| c. 4 段压缩 + 求和 | 31.5 ms | 44% | 由"全流程 − b"推得，是估计值 |
| **处理合计（b + c）** | **71.2 ms** | 100% | 折算 **0.140 µs/采样，148.6× 实时** |
| （对照）4 段各自滤波的旧形状 | 82.7 ms | — | 乘加 4/3 倍，比上面慢 16% |

关于最后一行：CPU 侧如果按"4 段各自一个滤波器"写，乘加次数是核的 4/3 倍。
**这个形状不能拿来当基线**，会让加速比虚高。留在这里只为让这个差可见。

计时说明：桌面上的单次计时抖动大概 ±10%（同一脚本两次跑出 71.2 ms 和 80.8 ms，
后者是换形状之前的数）。**要写进报告的绝对值，请在同一台机器上重跑一次取均值**，
别直接抄这里。这里给的是量级和比例。

## 三、B 和 C：板载 ARM vs PL 里的核

素材：144000 个采样（3.0 秒 @ 48 kHz），11 根谱线铺在 100 Hz~4 kHz + 底噪。
脚本：`board/scripts/compare_cpu_fpga.py`，两边各跑 3 次取最快。
原始输出：`data/results/compare_cpu_fpga_run_20261008.txt`（**以这份为准**；
上一次还是 450 拍那一版，见 `compare_cpu_fpga_run_20261001_fix.txt`）。

| | 实现 | 单采样 | 实时倍率 |
|---|---|---|---|
| B | ARM（float64 + `scipy.signal.lfilter`） | 6.199 µs | 3.36× |
| C | PL 里的核（Q1.15 定点，AXI4-Master 直连 DDR） | 0.317 µs（理论 0.280 µs） | 65.69× |
| | **加速比** | **19.5 倍** | |

**结果一致性**（精度不同，不能逐位比，只查是不是同一件事）：

    输入有效值 0.10706 ｜ CPU 输出 0.10659（1.00 倍）
    CPU 峰值   0.28627 ｜ 核峰值   0.28625

**核的实测比理论吞吐慢一截**，差额就是 Python 那层开销：

    28 拍 @ 100 MHz = 0.280 µs/采样（理论）    板上实测（每块 8000 点）：0.317 µs

差 0.037 µs/采样 = 每块 **297 µs** 的固定开销（写 10 个寄存器 + 2 次 cache flush +
1 次 invalidate + 轮询 DONE），占长块实测的 **12%**。450 拍那一版它只占 0.2% ——
核变快之后这一项才显出来，**块长越小越重**（逐档量法见 `fir_chunk_sweep.py`）。

## 四、写报告时怎么用这张表

- 「软件基线」这一节：用 **A**，说明是桌面 x86，注明是参考量级。
- 「硬件加速效果」这一节：用 **B vs C**，这是同一颗芯片上的账。
- 加速比那一句必须带上四条免责声明（精度不同 / CPU 是优化过的库 / 两边乘法量对等 /
  CPU 不是极限实现），原文在 `accel_cpu_vs_fpga.md`。
- **加速比用 19.5 倍**（2026-10-08 板上重测，`compare_cpu_fpga_run_20261008.txt`）；
  旧写法「硬件通路比 scipy 参考实现快 1.4 倍」是 450 拍那一版的数，不要再抄。

## 五、附：核当初为什么慢（历史记录 —— 已修好）

**已修好：** 靠编译开关 `-DFIR_SHIFT_CHAIN=1`（延迟线改走移位链）把拍数从 450 砍到
**28**（理论 0.280 µs、板上 0.317 µs），**算法一个字没改**，默认关、默认路径逐字节不变。
下面这张表是 v13/v18 的历史循环表（结论来自 csynth 报告，两版数字一致）：

| 循环 | 迭代 | achieved II | 拍数 |
|---|---|---|---|
| 延迟线整体移位 | 194 | 2 | **398** |
| 3 个低通 | 3 | 1 | 11 |
| 4 段压缩 | 4 | 1 | 12 |
| 每采样合计 | | | **450** |

**88% 的拍数花在"把延迟线整体挪一格"上**，真正算乘法只占 11 拍。
瓶颈在数据搬动，不在乘法器 —— 这一段后来就是被上面那个开关修掉的。
当时估计改成环形缓冲区能快 6~7 倍；实际用移位链开关就拿到了同样的效果。

## 六、核的输出 vs Python 黄金参考（数值比对）

这一节不是计时，是"算得对不对"。拿仓库里现存的 1000 点 HLS 输出，
和重新生成的 Python 黄金数据对了一遍：

| 指标 | 值 |
|---|---|
| 信噪比 SNR | **75.4 dB**（判据 ≥ 70 dB） |
| 相关系数 | 0.999999986 |
| 均方误差 MSE | 6.810e-10 |
| 最大绝对误差 | 3.469e-05 |
| 最佳位移 | 0 |

同一份数据在**直通模式**下，输出和量化后的测试输入**逐位相同**，延迟 96 个采样。

Python 侧"四段之和 = 原信号延迟 96 拍"这条恒等式，当前实测的最大系数和误差是
**3.469e-18**（浮点精度级别；旧的四段各自设计那套是 +3.2 dB）。

**这两条数据的边界**：这是**拿仓库现存的 HLS 输出**和重新生成的黄金数据做复比，
**不是本次执行环境重新跑了 Vitis HLS**。队友 2026-10-01 的交接记录称其工作站上 Vitis HLS 2020.2（`-version` 退出码 0）；本次沙箱未挂载交接里给出的 E: 盘路径，因此无法独立重跑。要验证从当前源码复现，仍需在该工具链机器上跑一次 C 仿真。
