# 上板验收的两次读数假象（2026-11-02）

`board/probes/board_accept.sh` 全量验收时报了两处 FAIL，复查后都是**探针读法问题**，
硬件与位流没有回归。本文记录原因和改法。

## 一、DRC 第 3 项「压缩器随参数动」

`board_accept.sh` 第 3 项「压缩器随参数动」在 11-02 首次全量验收时报 FAIL，
复查后是**探针读法问题**。这一节记录原因和改法。

### 现象

`pl_drc_ply_probe.py` 的三步：

```
[2] factory:  env=[584614, 352866, 2088, 175] gr=[49455, 0, 0, 0]   OK
[4] THR 抬到 2.0FS: gr=[0, 0, 0, 0]                                  OK
[5] ATK=REL=0（无记忆）: env=[259037, 164566, 1472, 236] gr=[0, 0, 0, 0]  FAIL
```

第 5 步的判据是「无记忆压缩时 GR 仍然 > 0」，读出来恒 0。

### 原因

ATK=REL=0 时 RTL 走的是「包络 = 瞬时幅度」那条路（`src/rtl/fir_drc4.v`
级 5 注释与 `env_r <= use_wdrc_r ? enp : p_a3`），所以 ENV/GR 寄存器里是
**每个采样**的瞬时值，不是平滑包络。

原探针用 `stat()` 每 50 ms 读一次、取 8 次中位。测试音是 439.5 Hz，
0.05 s 正好约 22 个整周期（439.5 × 0.05 = 21.975），每次读到的相位几乎不变；
那一片相位恰好落在 |a| < THR 的半周里，瞬时包络 259037 低于门限 419456，
GR 自然是 0。中位数把同一个相位读了 8 遍，不管读多少次都不会变。

这是读数跟测试音混叠，不是压缩器没动：

- 同一时刻 `[2]` 的平滑包络 584614 高于门限，压缩确实在发生；
- 相位换成峰点时，瞬时包络到 640294，GR 到 66248。

### 改法

`stat_dense()`：50 µs 间隔连读 200 次（相位每次漂约 0.022 周期，覆盖 4 个多周期），
ENV、GR 各取峰值。两路寄存器的流水深度不同（GR 比 ENV 晚几拍出来），逐点相除
没有意义，所以判据改成看峰值比：

```
峰比 = max(GR) / (max(ENV) − THR) ≈ 1 − ratio
```

实测 `66248 / (640294 − 419456) = 0.30`，与出厂 ratio 0.7 → 0.30 一致。

改后重跑：

```
[5] ATK=REL=0（无记忆）: env峰=[640294, 386762, 2716, 525] gr峰=[66248, 0, 0, 0]
    峰比 0.30（应 ~0.30）  OK
DRC PLY PROBE PASS
```

### 边界

- 只改了读法，探针的前三步判据、参数序列、位流都没动；`[2]`/`[4]` 的读数与
  10-29 那次一致（`impl_metrics.md` 里记的「ATK=REL=0 时退回无记忆压缩」成立）。
- 平滑包络档（出厂的 5 ms / 100 ms）仍然是中位判据，不受影响。
- 教训：**读逐采样寄存器时，轮询周期不能是信号周期的整数倍**，否则看到的是一个
  冻结的相位；取中位也不行，得让读点扫过整个周期再取峰。

## 二、第 5 项「抓取窗口」的 und 判据

同一轮验收的另一项：

```
[4] ovf 0→0  und 1→1  FAIL
```

判据写的是 `und1 == 0`（累计欠载计数必须为 0），但这一节自己的标题是
「读窗口不打扰音频（ovf/und 不涨）」。计数在测量前已经是 1：上一个探针停过播放，
本探针 flush 后重开输出时有**一次启动欠载**，之后整个窗口读取期间没有再增长。

### 改法

判据改成比较增量：

```python
ok = (ovf1 == ovf0) and (und1 == und0)
```

改后重跑：

```
[2] 零穿越法测得 1502.0 Hz（写入 1500 Hz）  OK
[3] 冻结期间 ptr 不动(1578/1578) 数据一致  OK
[4] ovf 0→0  und 1→1  OK
CAP WINDOW PASS
```

### 边界

- 这条只放过「测量前已有的 1」，窗口读取期间只要再涨一个就仍然 FAIL。
- 那 1 次欠载是探针序列自己造成的（前一个探针停了播放，flush 后重开输出），
  不是播放通路的问题：605.4 秒长跑里服务连续运行，und 全程为 0
  （`soak_pl_20261102.json`）。
