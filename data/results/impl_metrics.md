# 布局布线后的实测结果

对手文件 `hls_synth_metrics.md` 里的数全是 `csynth_design` 的**估算值**，由脚本自动生成。
这一份是**实测值** —— HLS 生成的 RTL 经 Vivado 综合 + 布局布线之后的数，手工维护。

量法见 `build/hls/run_vivado_impl.tcl`。**本节三种配置**走的是同一套流程、同一个器件
（`xc7z020clg400-1`，-1 速度等级）、同一条时钟约束（10 ns = 100 MHz）、
同一组努力程度（综合 `PerformanceOptimized`，布局 `ExtraTimingOpt`，
两次 `phys_opt_design -directive AggressiveExplore`，布线 `MoreGlobalIterations`）。
所以**互相对照是成立的**。

复现命令（在仓库根目录）：

    MSYS_NO_PATHCONV=1 HLS_LABEL=<版本> HLS_SOL=build/hls/<存好的 solution 目录> \
      cmd /c "E:\Xilinx\Vivado\2020.2\bin\vivado.bat -notrace -mode batch \
              -source build\hls\run_vivado_impl.tcl"

RTL 得先存下来 —— HLS 每次综合都覆盖它的工程目录，所以量完一版要
`cp -r <HLS 的 solution 目录> build/hls/sol_<版本>` 留档。已留档的：
`sol_v4_float`（浮点限流5）、`sol_v11_fixed`（定点限流5）、`sol_v10_fixed_nolimit`（定点不限流）、
`sol_v12_sub_n65` / `sol_v13_sub_n193` / `sol_v15_sub_n193_mul64`（相减式那三版）。

注意 **HLS 综合用的工程目录是 `build/hls/synth_proj/`，不是 `impl_proj/`** ——
`impl_proj` 是 `export_design` 那个流程留下的，容易抄错目录，抄错了会拿到上一版
一模一样的 RTL 还不自知。验证办法是看 `hist_V_4_ram.dat` 的行数（65 抽头 14 行、193 抽头 40 行）。

换时钟频率用 `HLS_CLK_MHZ`：

    MSYS_NO_PATHCONV=1 HLS_LABEL=<版本> HLS_SOL=build/hls/sol_<版本> HLS_CLK_MHZ=80 \
      cmd /c "E:\Xilinx\Vivado\2020.2\bin\vivado.bat -notrace -mode batch \
              -source build\hls\run_vivado_impl.tcl"

### 第 ③ 步的整机复量（2026-10-01，in-context）

上面 `v18` 那一行仍是 `-mode out_of_context` —— 那是「把核当独立零件量」的数。
真正的整机数得在 block design 里量：核的 AXI 外壳接上 PS 的 `S_AXI_HP0`、
音频 IP 也一起布进去、顶层管脚有真实约束（OOC 那行顶层端口是不占管脚的）。
这一份才回答「整机能不能跑 100 MHz」。

| 量的是什么 | LUT | FF | DSP | BRAM | WNS | 失败端点 |
|---|---|---|---|---|---|---|
| `v18_axi_shell` 裸核（OOC） | 4960 (9.3%) | 7010 (6.6%) | 202 (91.8%) | 54.5 (38.9%) | **+0.932 ✅** | 0 |
| **整机（in-context）** | **6422 (12.07%)** | **9416 (8.85%)** | **202 (91.82%)** | **54.5 (38.93%)** | **+0.256 ✅** | **0** |

- **WNS 从 +0.932 掉到 +0.256。** 掉的那部分来自 AXI 互联、PS 的 HP0 口、音频 IP

### 450 拍花在哪（2026-10-01，读 csynth 报告）

`fir_multiband_csynth.rpt` 的循环表。**`v13_sub_n193` 和 `v18_axi_shell` 两版这四个数
一模一样**，说明套 AXI 外壳没有动循环结构：

| 循环 | 对应源码 | 迭代 | achieved II | 拍数 |
|---|---|---|---|---|
| `VITIS_LOOP_270_4` | 延迟线整体移位 `hist[k]=hist[k-1]` | 194 | **2** | **398** |
| `VITIS_LOOP_281_5` | 3 个低通 `for (b=0; b<N_LP; b++)` | 3 | 1 | 11 |
| `VITIS_LOOP_356_10` | 4 段压缩求和 | 4 | 1 | 12 |
| `VITIS_LOOP_263_3` | 每采样一遍（外层） | — | — | **449 / 450** |

**结论：88% 的拍数（398/450）花在"把延迟线整体挪一格"这个纯搬运上，
真正的乘法只占 11 拍。** 202 个 DSP 铺在片子上，97% 的时间是空着的。

源码里原来写的假设是"完全展开之后 192 次移动变成同一拍的 192 组线，从 192 拍降到 1 拍"
—— **这个假设不成立**。`#pragma HLS UNROLL` 在，但 achieved II 仍是 2：
`hist` 同时挂着 `ARRAY_PARTITION cyclic factor=5`，被拆进 5 个 RAM，
跨 RAM 边界搬数据没法一拍做完。

**瓶颈在数据搬动，不在乘法器。** 这也修正了早先"每拍只算 1.3 个乘加"的说法 ——
那个数把折叠结构里每一对的两个加数当成两次乘法数了。按源码 `N_FOLD=(193+1)/2=97`，
实际是 **3 × 97 = 291 次乘法 / 450 拍**。

标准修法是**环形缓冲区 + 转动的读下标**，每采样零搬运。按上表，移位那 398 拍
基本能去掉，每采样会落到 60~70 拍量级。**没做** —— 改结构要重跑综合、P&R 时序
和全套上板验证，而 DSP 只剩 18 个余量，改完还得重新确认收敛。

复现：`build/hls/sol_v18_axi_shell/syn/report/fir_multiband_csynth.rpt`（第 39 行起的 Loop 表）

### 结论一：限流省了 DSP，但时序全崩；而且还更费 LUT

DSP 从 202 降到 86、LUT 反而从 3962 涨到 10443。两条曲线都是往坏的方向走的：

    DSP：  202  →  132  →   86        （限流越狠越省）
    拍数： 449  →  452  →  455        （几乎不变，+1.3%）
    LUT： 3962  → 9702  → 10443       （限流越狠越费，2.6 倍）
    WNS：+1.624 → −0.138 → −0.620     （从过到不过）

**原因和 `v11_fixed_nosat_mul5` 那次一模一样**：复用乘法器 = 把两个 DSP48 串成一条链，
中间没有寄存器。最差路径长这样：

    ap_enable_reg_pp1_iter1_reg_replica_4/C
      -> mul_15s_16s_31_1_1_Multiplier_0_U   (DSP48E1)
      -> 累加器                              (DSP48E1)
      -> reg_13496_reg[27]/D
    Data Path Delay 10.491 ns，Logic Levels 4 = DSP48E1×2 + LUT2 + LUT5

而**不限流那一版的最差路径根本不在算术上**：它落在 `hist` 的**地址加法**上
（15 级逻辑、13 个 CARRY4，终点是 DRC 乘法器的 A 口），7.755 ns。
这和 `v10` / `v4` 当年的瓶颈是同一处 —— 地址逻辑是这几代共有的短板，以后想再提频就从它下手。

### 结论二：降价换面积这条路走不通

`v15` 在 100 MHz 下差 0.620 ns。把时钟降到 80 MHz，**真跑一遍布局布线**（不是重算报告）
的结果是 +0.386 ns —— 过了，但薄。

而且那一版的临界路径是 **`ap_CS_fsm_reg[47]` 到乘法器的 C 口，11.589 ns 里 7.018 ns（60%）
是纯走线**，逻辑只有 4 级。这不是逻辑深，是布得散、信号横穿了整个芯片。
这种余量靠不住：外围电路一加进去，布局一变就可能又不过。
所以**降频不是免费的**，"少用 116 个 DSP" 换来的是薄到 0.386 ns 的余量。

### 结论三：抽头数定 193，乘法器不限流，100 MHz

`v13_sub_n193`（不限流、100 MHz）：202 个 DSP 占板上的 **91.8%**，看着吓人，
但整个系统里除了这个 FIR **没有任何东西用 DSP48**（AXI DMA、I2S 控制器、AXI 互联都是 0 个），
这 202 个是真全花在刀口上的。它是唯一一个**时序余量真实（+1.624）且频段分得开**的配置。

为什么不能用 65 抽头 —— 这条是量出来的，不是估的：

| 抽头 | 过渡带 (3.3·fs/N) | 最差边界残留 | 段 2 在**自己**中心处 (707 Hz) |
|---|---|---|---|
| 65 | 2437 Hz | **−6.0 dB** | **−14.2 dB** |
| 129 | 1227 Hz | −14.5 dB | −4.1 dB |
| 193 | 820 Hz | **−21.4 dB** | −1.6 dB |

判据是"每条边界的两侧都 ≤ −20 dB"。65 抽头不是"串音大了点"，是**段 2 连自己该通过的
707 Hz 都压掉了 14 dB** —— 那四段根本就没分开，压缩比调什么都一样。
过渡带 2437 Hz 比要分的那几段本身（500 / 500 / 1000 Hz 宽）还宽，这是必然结果。

### 踩的坑（都是环境/流程的，不是设计的）

1. **顶层端口装不进封装。** 普通模式下 Vivado 把顶层端口当真管脚，布局第一步就得给它们
   找位置。这一版顶层有 **185 个端口位**（`in_r` 32 + `out_r` 32 + `length_r` 32 +
   两个 DRC 参数数组的存储器接口 80 + 握手位），而 clg400 **总共只有 125 个可用管脚位**：

       ERROR: [Place 30-58] IO placement is infeasible.
       Number of unplaced terminals (178) is greater than number of available sites (125).

   改 `synth_design -mode out_of_context`（IP 核的标准做法，顶层端口不是物理对象）。
   核将来是**被实例化进 overlay** 的，本来就没有"核自己是一颗芯片"这个用法。
   `v10` / `v11` 那两行是普通模式下量的，要复现它们加 `HLS_OOC=0`。
   （`v10`/`v11` 的端口少，恰好塞得进 125 个，所以当年没撞上。）

2. **拿一套布线去重算别的时钟频率，只能当粗估。** 用 `report_alt_clock.tcl` 在 100 MHz
   的布线上重算 80 MHz，得 WNS +1.880；真跑一遍 80 MHz 的布局布线，实测 **+0.386**。
   差了 1.5 ns。周期一变 Vivado 会布出完全不同的结果（关键路径都换了一条）。
   要出数就必须真跑 `run_vivado_impl.tcl`，重算只用来"决定值不值得真跑"。

3. **不要同时开两个 Vivado。** 并发跑的时候 `synth_design` 报过
   `invalid command name "rt-undefined"`，还有一次报
   `couldn't read file "E:/Xilinx/Vivado/2020.2/scripts/rt/data/common.tcl": no such file or directory`
   —— Vivado 读不到自己的脚本文件。重跑一次就好，跟设计无关。

## 实测和估算差多远

| 版本 | DSP 估算→实测 | LUT 估算→实测 | FF 估算→实测 |
|---|---|---|---|
| `v10_fixed_nolimit` | 67 → 70 | 6502 → 2493（估算偏高 2.6 倍） | 6071 → 2624 |
| `v11_fixed_nosat_mul5` | 6 → 35（估算偏低 5.8 倍） | 8714 → 3668（估算偏高 2.4 倍） | 6920 → 5045 |
| `v4_ref_limit5` | 27 → 27（分毫不差） | 9936 → 6396 | 12627 → 11051 |

**DSP 的估算在两个方向上都不准**，LUT 的估算一律偏高约 2.5 倍。
所以**不能拿任何一个固定的修正系数去换算**，估算值也不能当结果写进报告。

## 关键路径在哪

三个版本的最差路径分两类：

- `v10` 和 `v4` 的最差路径**都不在算术上**，而在 `hist` 采样缓冲区的**地址加法**上
  （9 级逻辑，`CARRY4=3`，路径终点是 `hist_V_*_U/.../q0_reg[*]/D`）。
- `v11` 的在算术上：穿过**两个串联的 DSP48**（`mul_18s_16s_34_1_1`），11.678 ns，
  其中逻辑 6.630 + 走线 5.048。这是乘法器复用（`-limit 5`）的固有代价 ——
  复用把两个 DSP 组合串起来，中间没有寄存器。

这条信息有用：**地址逻辑是三个版本共有的瓶颈**，以后想再提频率，从它下手目标明确。

## 别忘了这些没量到的东西

- **输入输出端口的时序没被约束。** 报告里 `no_input_delay (66)` / `no_output_delay (36)`
  就是这件事：66 = `in_r[31:0]` + `length_r[31:0]` + `ap_start` + `ap_rst`；
  36 = `out_r[31:0]` + 四个握手位。也就是说上面的 WNS **只对寄存器到寄存器成立**，
  **不能拿裸核的 WNS 说"整机能跑 100 MHz"**。

- **但补出来的那份带 I/O 假设的报告（`timing_impl_io_1.5ns.rpt`）也不能当"真实系统"的数。**
  加上 1.5 ns 的 I/O 假设后三个版本全崩：`v4` −8.750、`v10` −10.426、`v11` −11.783 ns。
  看着吓人，但**这个模型不对**，拆开最差路径就清楚了：

  - 时钟路径偏移 **−5.25 ns**。时钟从管脚进来，经过 IBUF(1.08) + 走线(2.21) +
    BUFG(0.10) + 走线(1.87) 才到源寄存器，共 5.25 ns；而 `set_output_delay`
    假设对面的器件看到时钟是 0 ns。这 5.25 ns **纯粹是"管脚级建模"的产物**，
    被单边扣在预算里。
  - 输出管脚缓冲 `OBUF` 本身就要 2.8 ns。
  - 剩下的才是设计的事：`ap_done` / `ap_ready` 由一个比较器（`icmp_ln204`）
    **组合**驱动，中间还有两级 `CARRY4`；`out_r` 也是从寄存器出来再过几级 LUT。

  真上板时这个设计**不会这样接**：时钟来自 PS 的 FCLK（同一个时钟域，偏移不会单边扣），
  输出直接进片内 FIFO / AXI 逻辑，不走 `OBUF`。所以管脚级的约束只在
  「裸核当独立芯片用」这个场景下才有意义，而那不是我们的用法。

  **真正有意义的那条结论是**：`ap_done` / `ap_ready` / `out_r` 都是**组合输出**，
  端口上没打拍。集成的时候外层必须给它们各打一拍，否则会拖出一条十几纳秒的组合路径。

  怎么出这份报告：`build/hls/report_io_timing.tcl`（加约束不改变布线，只重算要求时间，
  所以不用重跑布局布线，两三分钟）。假设值由调用方显式传、不写死在脚本里。
  **"整机能不能跑 100 MHz"这份报告回答不了 —— 要回答它，得先把外层那个壳搭出来再量。**
  （2026-10-01 补上了：见上面「第 ③ 步的整机复量」，整机 WNS +0.256 ns、失败端点 0。）
- **拍/采样是 HLS 的调度估算，不是实测。** 实测的是资源和频率；每个采样要几拍
  来自 `csynth_design` 的调度结果。不过拍的数是数出来的调度步数，不像资源那样是猜的，
  可信度高一档。
- ~~**没上过板。**~~ 这一条 2026-10-01 作废：核已经在真板子上跑过，见上面「上板实测」。
  不过**那张上板结果的表里，资源和时序仍是 Vivado 的数，不是硅片实测** ——
  板子验证的是功能（算得对不对），不是频率（能不能跑更快）。

## 撞到的工具坑

见 `build/hls/run_vivado_impl.tcl` 的文件头注释，那里写得比这里细。最要命的一条：

**`export_design -flow impl` 在 2022 年之后必挂**，跟设计无关。HLS 打包 IP 时会设
`core_revision`，值是 `YYMMDDHHMM` 形式的日期戳（2026-09-29 19:29 → 2609291929），
存成 32 位有符号整数，上限 2147483647 —— **2022 年 1 月 1 日之后任何日期都溢出**，
报 `bad lexical cast` / `ERROR: [IMPL 213-28] Failed to generate IP.`。
这是 Vivado 的 **Y2K22** 已知 bug，官方补丁 `y2k22_patch-1.2.zip`（AMD 支持文章 76960），
影响 2014.x ~ 2021.2，2020.2 在范围内。所以这里绕开了 `export_design`，
自己写非工程模式脚本直接喂 RTL 给 Vivado。
