# 实时丢块定位与调参（2026-10-21）

对象：PYNQ-Z2 上 `fir_live.py` 的实时麦克风通路（4 段分频 + 每段 WDRC）。
配置：`fir_webui.py` 开着、页面用 headless Chrome 真实打开（150 ms 拉状态、
250 ms 拉波形）、`LIVE_SCOPE=1`，和演示时一致。命令：

    python tools/board_debug/run_drop_matrix.py --seconds 60 --arms <臂名>

每臂起跑都对齐到板子 `uptime % 30 ∈ [1.0, 2.5]`，避免上一臂的 30 秒定时器
落在下一臂的开头。

## 指标

`lost_blocks` 是 `fir_live.py` 内部按「本档块长」数出来的：
`(墙钟 - n×块长) / 块长`。L=480 时一块 10 ms，L=960 时一块 20 ms，**两个
数字不能直接比**。本文另记一个统一尺子：

- 音频缺口 = `(1 - n×L/48000 / 墙钟) × 60000`，单位 ms/60 s；
- 折成 10 ms 块 = 缺口 / 10，等于「按 10 ms 一块算丢了多少块」。

探针在板内读状态（20 Hz），不走 SSH 轮询 —— 主机拉取本身会把丢块从
0.20 抬到 0.90 块/秒。

每个线程都 `sched_setaffinity` 到 CPU1。

| page_nopin_3_480 | 3 | 480 | 关 | 开 | 674 | 67.4 |
| page_pin_3_480 | 3 | 480 | 开 | 开 | 696 | 69.6 |
| page_nopin_4_480 | 4 | 480 | 关 | 开 | 581 | 58.1 |
| page_pin_4_480 | 4 | 480 | 开 | 开 | 591 | 59.1 |
| page_nopin_3_960 | 3 | 960 | 关 | 开 | — | 0 |
| page_pin_3_960 | 3 | 960 | 开 | 开 | — | 0 |
| page_nopin_4_960 | 4 | 960 | 关 | 开 | — | 0 |

（L=960/1920 那几臂 `rt` 略大于 1、缺口为负，是 `time.time()` 与音频时钟的
零点几个千分之一的偏差，不是真的多处理了音频。看 `lost_blocks` 的终值：
四臂都是 0。）

**看出来的事：**

- 网页开着和不开，差 3%，在噪声里；把非音频进程钉到 CPU1 也没有可测量的
  收益。上一轮「网页把丢块从 0.9 抬到 1.6 块/秒」主要是 L 和当时测法不同。
- NBUF 从 3 到 4 只从 69 降到 58，不是余量不够。
- 丢块时间戳在 60 秒里均匀分布，不是每 30 秒一簇 —— 和 kworker 重扫 timer
  无关（每 30 秒对齐起跑，相位也没有集中）。
- `LIVE_SWITCH=0.0001` 基本没用（64 vs 67）。
- **块长是唯一的强变量**：480 稳定丢，960 以上稳定不丢。

## 机制：两块之间那段时间

`duplex_block` 是逐采样轮询 I2S 状态寄存器的，调用期间就是 I2S 时钟本身。
调用返回后，搬样线程还要在 Python 里把槽位交给 dsp、再从 dsp 取下一个槽位；
这段时间没人取采样，只有 IP 里那一点 FIFO 能吸收。

在 `fir_live.py` 里加 `GAP_TRACE`，把每块拆成四段（单位 µs，中位）：

| 队列实现 | 等 dsp 槽位 | 进 C 之前 | 出 C 之后到 qput 完 | 下一轮循环开头 | 合计 |
|---|---|---|---|---|---|
| `queue.Queue` | 67.6 | 7.7 | 108.9 | 11.8 | 196 |
| `queue.SimpleQueue` | 22.1 | 7.3 | 39.9 | 12.8 | 81 |

`queue.Queue` 的锁和 `Condition` 在 Python 层，一次 get/put 就吃掉 176 µs；
`queue.SimpleQueue` 的等待和锁在 C 里（`_queue`），同样的两步只剩 62 µs。
I2S FIFO 能吸收的空档大约在一百微秒这个量级，于是：

- L=480：196 µs 空档 → 每块漏几个采样 → 60 秒丢 70 块；
- L=960：同样的空档摊在 20 ms 上 → FIFO 吸收得下 → 0 块。

## 第二轮：只换队列实现（L=480）

| 臂 | 队列 | 缺口 ms/60s | 丢块/60s | 自检 |
|---|---|---|---|---|
| page_nopin_3_480_qsimple | `SimpleQueue` | -46 (≈0) | **0** | 通过（6021 块） |
| page_nopin_3_480_qold | `queue.Queue` | 740 | 73 | 通过（5932 块） |

默认改成 `SimpleQueue`（`LIVE_QUEUE=queue` 可退回旧实现做对照），
**L=480、NBUF=3 保持不变**，所以端到端延迟公式不变：
`NBUF×L/48000 + 2 ms = 32 ms`。

## 第三轮：每 30 秒一次的内核线程重扫

改队列之后 600 秒那一趟跑完了、自检也过，丢块 4 块，但 trace 里搬样空档
不是平的：60008 个块间空档里有 28 个超过 5 ms，每 30 秒一簇，单次 5~80 ms，
最大 80.2 ms。

把每一簇的时刻换算成开机的秒数（`/proc/uptime` 起点 + 块内相对时刻），
周期是 **30.24 秒**，第一簇在开机 11112.8 秒、正好等于 `45 + 366 × 30.24`；
最大那一簇在开机 11264.0 秒，等于 `45 + 371 × 30.24`。也就是
`ksoftirqd-rt-refresh.timer`（`OnBootSec=45`、`OnUnitActiveSec=30`，
每次脚本自己还要跑 0.24 秒）的第 366~371 次唤醒。

链条：

1. timer 每 30 秒拉起一次 shell，systemd 自己会写 Starting / Succeeded /
   Finished 四行 journal（`LogLevelMax=warning` 管不到系统自己的这几行）；
2. journald 把日志落在 SD 卡上；刷卡的 `kworker/0:1H-mmc_complete` 是
   FIFO 50，在 CPU0 上直接抢搬样线程（FIFO 20）；
3. 把 timer 的服务钉到 CPU1 没用 —— 写盘是在 CPU0 上完成的中断。

改法：删掉 timer 和它调的脚本，换成一个常驻 Python 进程
`ksoftirqd_rt_watch.py`：每 30 秒扫一遍 `/proc`、对 ksoftirqd 和
kworker/[01]:* 调 `sched_setscheduler`。只读内存，不 fork、不写日志、不碰磁盘。
开机那一次仍由 `ksoftirqd-rt.service` 调 `ksoftirqd_rt.sh`，脚本改成只在
失败时记一条 warning。

验证：

- 空闲 45 秒，journal 里除 ssh 会话以外的行数 = 0（旧版每 30 秒 4 行）；
- 60 秒演示配置（L=480、NBUF=3、SimpleQueue、网页开着）：6017 个块间空档，
  中位 0.083 ms、最大 0.363 ms，没有一个超过 0.5 ms；丢块 0，自检通过。

## 第四轮：600 秒演示配置复测

同样的配置跑 600 秒（网页开着、服务开着）：

| 项 | 结果 |
|---|---|
| 处理块数 | 60066 |
| 丢块 | **0** |
| 自检 | 通过（`ok=true`） |
| 实时倍率 | 1.0008 |
| 块间空档 中位 / p90 / 最大 | 0.083 / 0.102 / **3.91 ms** |
| 超过 0.5 ms 的空档 | 17 次，最大 3.91 ms，没有丢块 |

`lost_blocks` 的瞬时峰值在开头 53 秒爬到 16，然后一路回落到 0 —— 这是启动
时的积压，`lost_blocks` 的定义是 `max(0, 墙钟 - n×块长)`，音频一旦追上就
归零，不是丢了 16 块。

剩下的 0.5~3.9 ms 空档 17 次，间隔 12~63 秒、没有 30 秒周期（最大那几个
出现在 401 / 451 / 508 / 571 秒，越往后越大）。没有造成丢块，暂时不追。

## 结论 / 演示配置

- 搬样线程每块只做一次 C 调用，别的都在 dsp 线程上；
- io→dsp、dsp→io 两条队列用 `queue.SimpleQueue`；
- NBUF=3、L=480；
- 不需要钉 CPU 亲和性，也不需要关网页；
- 板上要装 `install_ksoftirqd_rt.sh`：开机提权 + 常驻静默重扫，不能再用
  systemd timer。

600 秒复测：丢块 0，自检通过，最大空档 3.91 ms。10 月 26 日按这一套再跑一次。
