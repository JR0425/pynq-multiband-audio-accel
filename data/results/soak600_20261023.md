# 600 秒长跑 × 2（2026-10-23，36 拍核，演示同配置）

稳定性验收的硬证据：两趟 600 秒，网页和服务都开着，判据是**不挂**。

```bash
python board/probes/run_drop_matrix.py --seconds 600 \
    --arms page_nopin_3_480,page_nopin_2_360
```

板上 `fir.bit` md5 `5aa079f29e8d66c21d1d34f1302c3695`（36 拍那版，与仓库
`board/overlay/fir.bit` 一致）。`fir-webui` active，主机 headless Chrome 真实
开着页面（150 ms 拉状态、250 ms 拉波形）。每一臂起跑对齐到板子
`uptime % 30 ∈ [1.0, 2.5]`。

**两趟都过。** 和 10-21 那次（49 拍，60066 块、丢块 0、最大空档 3.91 ms、
倍率 1.0008）相比，最大空档从 3.91 降到 3.68 ms，其余同级。

## 两处读法，别看成故障

**1. 缺口是负数 ≠ 欠了。** 定义是 `(1 − n×L/48000 / 墙钟) × 60000`，
负数表示板子按 I2S 时钟采出来的音频**比主机墙钟跑得略快**（60192 × 480 / 48000
= 601.92 s 音频 / 600.02 s 墙钟）。10-21 那次是 +0.0009，这次 +0.003，
是板子晶振和主机时钟的相对偏差，不是丢块，也不是欠账。

**2. 低延迟档那 2 个事件不是丢块。** `events` 里两条 `lost: 1` 出现在
n=378（≈2.8 s）和 n=966（≈7.2 s），是起跑阶段 `lost_blocks` 的瞬时读数
（定义 `max(0, 墙钟 − n×块长)`，积压追平就归零）。整趟结束时
`lost_total = 0`，和稳定档一致。

## 和 10-21 那趟的区别

10-21 测的是 49 拍核；今天 36 拍。延迟几乎不变（数字法三档逐档相同，
见 `latency_retest_20261023.md`），这次长跑的空档分布也基本一样 ——
说明瓶颈一直在 `duplex_block` 的逐采样 I2S 握手和块缓冲，不在核里。
**核提速换来的是 CPU 余量**（dsp 线程 p90 1.27~1.33 ms / 块预算 7.5~10 ms，
占 13~18%），不是延迟也不是丢块。
