===== 2026-10-16 深夜「A_dump」那一轮的 RCU stall 全任务转储（串口原文，一个字节没改）
=====
===== 取自 tools/_tmp/round6/console.log 的头部（正文 1468 行；后面是板子自己重启后的 U-Boot）。
===== 这一份是用 kernel.panic_print=31 逼出来的 —— 等价于 panic 那一刻自动按了一下 sysrq-t。
===== 为什么非要绕这一下：panic_on_rcu_stall=1 是在 rcu_dump_cpu_stacks() **之前** panic 的，
===== 卡住那颗核的栈本来永远打不出来；而板上 hung_task / softlockup / sysrq(BREAK) / ftrace /
===== /proc/<pid>/stack 全都没编（见 probe_config.txt）。
=====
===== 这一份要证明的东西（转储里怎么找）：
=====   · 第 30 行  rcu: INFO: rcu_preempt self-detected stall on CPU  ← 挂的机制是 RCU stall
=====   · 第 31 行  0-....: (999 ticks this GP) ... softirq=10908/10908 fqs=500
=====              fqs=500 ⇒ **这一轮的 stall 超时被压到 10 秒**（默认 60 秒对应 fqs≈3000；
=====              这一臂带了 FASTSTALL=1，抓现场用的，做 A/B 时不能用）
=====   · 第 32 行  Kernel panic - not syncing: RCU Stall
=====   · CPU1 的栈停在 do_idle（空闲那颗），CPU0 才是被卡住的那颗
=====   · 第 1203 行  python3 R running task（pid 922 = fir_live.py 的搬样线程）；
=====              第 1218 行 它的栈尾是 __irq_usr，异常栈 CPSR 低 5 位 = 0x10 = 用户态
=====   · 第 88 / 98 / 117 / 218 / 449 行  CPU0 上的 5 个 kworker + ksoftirqd/0
=====             （98 和 449 那两个标着 mmc_complete）：
=====             全是 "R  running task" 而栈停在 __schedule ⇒ 可运行却一直轮不上
=====   · 对照：第 172 行  ksoftirqd/1 是 S（CPU1 正常）—— 出问题的只有 CPU0
=====
===== 结论（详见 data/results/board_hang_evidence_20261016.md）：
=====   CPU0 上一条 SCHED_FIFO 且永不阻塞的搬样线程把内核的延迟工作饿死，
=====   nice 0 的 ksoftirqd/0 抢不到 RT 限流留出来的那 5%（被 nice -20 的 mmc 工作吃光），
=====   CPU0 的 RCU 静默态报不上去 → stall（这一轮 10 秒）→ panic。
=====   ⚠ 这是「为什么 panic」的答案，**不是「为什么挂」的答案** —— 关掉实时照样挂（round7）。
=====
