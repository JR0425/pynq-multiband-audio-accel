# PYNQ-Z2 板子出声 / 录音

出厂 base overlay 的音频通路怎么跑通，以及七个会卡住人的地方。
实测：PYNQ-Z2 + PYNQ 2.7.0 + 出厂 base overlay，2026-09-27。

## 什么时候用

- 板子不出声，或者录音全是本底噪声
- set_volume 报 ValueError: Volume has to be in [0,63]!
- Audio.load() 拒绝一个 wav 文件
- 边录边放时录回来的电平贴着满量程，而且你不说话它也不掉（**其实只采不放、一次寄存器都不写也一样**）
- 要确认音频搬运到底是 CPU 干的还是 FPGA 干的
- 演示前要定用哪种接法（耳麦还是 Line-in）

## 什么时候别用

- 要把自定义核接进音频通路 —— 这一页讲的是出厂 base overlay 的通路
- 只需要验算法、不用真出声 —— Python 基线和 C 仿真就够

## 跑通它

从串口控制台（`xilinx` 用户）：

```
cd /home/xilinx/jupyter_notebooks && echo xilinx | sudo -S env XILINX_XRT=/usr \
    /usr/local/share/pynq-venv/bin/python3 verify_audio_playback.py
```

不带界面的脚本：`board/scripts/verify_audio_playback.py`
带波形图的 notebook：`board/notebooks/w2_audio_playback.ipynb`

核心就四行：

```python
audio = BaseOverlay("base.bit").audio   # 开机时出厂固件已经灌好了
audio.set_volume(62)
audio.load("x.wav")                     # 24 bit / 双声道 / 48 kHz
audio.play()
```

## 坑 1：命令行报 `OSError: Root permissions required.`

同一份代码在 Jupyter 里能跑，在串口控制台报这个错。差别不在代码，在「谁在跑」。

PYNQ 靠 `/dev/mem` 和 `/dev/uio*` 访问 FPGA 寄存器，两者都只有 root 能开：

```
$ ls -l /dev/mem        ->  crw-r----- root kmem
$ groups xilinx         ->  xilinx adm sudo        (不在 kmem 组)
$ ps -eo user,pid,comm | grep jupyter  ->  root jupyter-noteboo
```

Jupyter 服务本身是 root 起的，串口登进来的 `xilinx` 不是。

加 sudo，并且显式给 `XILINX_XRT` —— `sudo` 不读 `/etc/profile.d/` 里的开机设置：

```
echo xilinx | sudo -S env XILINX_XRT=/usr /usr/local/share/pynq-venv/bin/python3 脚本.py
```

## 坑 2：`set_volume(63)` 报 `ValueError: Volume has to be in [0,63]!`

报错信息里的区间是错的。源码判断是 `if not 0 <= volume < 63`。

**上限实际是 62。**

## 坑 3：`load()` 只吃一种 wav

`Audio.load()` 按每个采样 3 字节解包，只接受 **24 bit / 双声道 / 48 kHz**。
采样率固定 48000（codec 决定的，改不了）。

素材太安静时，不要靠猜着加音量。直接生成一段**数学上已知干净**的正弦波来判断：
如果放它还听到杂音，问题就在板子这一侧；如果是干净的一声蜂鸣，那杂音来自素材。
现成的生成函数在 `board/scripts/verify_audio_playback.py` 的 `make_tone()`。

## 坑 4：录回来的信号带直流偏置

录一段安静的信号，波形不围绕 0 摆动，整体抬高约满量程的 1.2%，还缓慢下滑。
这是采集通路的直流偏置，不是 bug。

算频谱或做前后对比之前先减均值：

```python
x = x - x.mean()
```

不减的话，频谱在 0 Hz 处会出现一根很高的假峰，把真正要看的东西压下去。

## 坑 5：耳机麦插着也不出声，要拔插到电平表跳起来为止

`HP + Mic` 口里有一颗 TI **TS3A226AE** 自动耳机开关（原理图 U41，9 球封装），
负责判断插头是 CTIA 还是 OMTP，再把麦克风接到正确的那根触点上。
**CTIA/OMTP 这一层不用管**——板子两种都认，这颗片子就是专门干这个的。

它的检测由插头插入时 `EN` 脚上的一个上升沿触发，**检测一次就记住结果**。
板子上电时插头已经插在里面，这一下就不存在了，开关停在「麦克风没接上」的状态。

症状：录音有效值只剩本底，左右两路都不动，说话、敲麦都没反应。

做法：板子开着，把耳机**拔掉再插回去**，然后重跑录音脚本看电平表。
**一次不一定够 —— 要拔插到电平表跳起来为止。**

10/09 实测：连续拔插，到**第 35.5 秒**电平才跳起来，之后一直是真的。
所以「拔了一次还是没声」不等于这条路不通，是还没插到那一下。

拔插前后实测（`board/scripts/mic_watch.py`，int16 域有效值）：

| 状态 | 有效值 | 峰值 |
|---|---|---|
| 插着但没检测到 | 7 ～ 45 | 70 ～ 113 |
| 拔插一次之后说话 | 400 ～ 1200 | 2000 ～ 5400 |
| 拔插到第 35.5 秒跳起来（10/09） | 11822 | 32768 |

麦克风是单声道，被同时送进左右两个声道，所以两边数字几乎一样。

依据：`TUL_PYNQ_Schematic_R12.pdf` 第 7 页 "USB & Audio"。插口是 `CN_AUDIO1`
（SJ-43515TS-SMT），四段触点走 `FRONT_L` / `FRONT_R` / `RING2` / `SLEEVE`，
后两根都接到 U41；U41 的 `EN` 脚经 1 MΩ（R681）上拉到 AVCC3V3，
并接插口自己的插入检测触点，正是 TI 数据手册推荐的那种接法。

## 板子上只有两个 3.5mm 口，而且外放和拾音互斥

| 口 | 方向 | 接什么 |
|---|---|---|
| `HP + Mic` | 输出 + 麦克风输入，**一口两用**（TRRS 四段） | 耳机 / 有源音箱 |
| `Line-in` | 只能输入 | 电脑耳机口（当测试音源） |

有源音箱必须插 `HP + Mic`（`Line-in` 是输入口，插不了）。**插上音箱就没有麦克风了。**
耳机麦插着却录不到声音，先看坑 5——多半要拔了重插，而且要拔插到电平表跳起来为止。

演示前先定走哪一种，两种的数字通路是同一条，代码不用改（区别只是 codec 选哪个输入口）：

- 说话型：带麦耳机，麦和听都走 `HP + Mic` —— 外放时容易啸叫
- 放音频型：电脑 → 公对公线 → `Line-in`，板子 → 音箱 —— 不啸叫，前后对比更清楚

## 坑 6：上电后耳机里一直嗡嗡响 —— codec 还没被配置

板子一上电，PYNQ 会自动加载出厂的 base overlay（`fpga_manager/fpga0/state` 会是
`operating`），但**不会**替你做 `codec.configure()`。这一步没走之前，耳机口停在
未配置的状态，听起来是一大团嗡嗡声。

症状：刚开机、还没跑过任何脚本，插上耳机就有很大的底噪。

做法：跑一次任何调了 `codec.configure()` 的脚本就行 ——
`board/scripts/replay_own_overlay_tone.py` 就是干这个的（装 overlay → configure →
放三遍干净正弦）。跑完嗡嗡声立刻消失。

最快的一条判据，是看板子**开机之后到底有没有跑过脚本**：

```sh
uptime                                                    # 开机多久了
find /home/xilinx/jupyter_notebooks -newermt "<开机时刻>"   # 开机后有没有文件被改过
```

一条都没跑过，那这声音就不是程序发出来的，先怀疑这一条，别先去翻代码。

实测（10/08）：开机后未配置 → 嗡嗡声；跑一次 `configure()` 之后 → 三遍
1 kHz 干净正弦每遍都是干净的一声「嘟」，停下之后也没有底噪。
**实时通路代码一个字没改** —— 它本来就不是坏的。

## 坑 7：边录边放时，麦克风输入被推成满幅自激

**症状**：一边收一边放（自己编的 `duplex_block` 那条边录边放通路）时，
录回来的电平贴着满量程，**你不说话它也不掉**，耳机里是一直在响的噪声，
不是人声。而**同一个麦克风口**、同一时刻，让 `audio.record()`（只录不放）
或者只调 `capture_block`（不写 TX）去读，是安静的。

实测（10/10）：

| 量法 | int16 域 rms |
|---|---|
| `mic_level.py`，走 PYNQ 驱动的 `audio.record()` | 28 |
| 自己编的 C 库，`capture_block` 只收不放（不写 TX、不写 I2C） | 230 |
| `stream_begin` 那 4 次 I2C 写**之后**再只收 | **46551** |
| duplex 且 TX 全填 0 | **45843** |

后两行相等、而且 TX 填的是 0 —— **跟发出去什么、输出多大都无关**。
收到的那一块长这样：`min=7815  max=16777199`，在 0 到 2^24 整个范围里乱撞。

**先排掉这几条**（10/10 都试过，都不是）：

- **不是靠输出幅度撑着的声学反馈。** 把播放音量设成 0（耳机"全哑"）
  电平仍 29803；把四段增益压到 −41.9 dB（送出去的只剩 0.008 倍）电平仍 32740。
  → **10/13 更正**：这组数只说明"跟送出去多大无关"，**并没有**排除耳机那条路
  —— 当时那个"音量 0"实际写的是 `0x03`，是 −57 dB、**功放还使能着**（见下）。
- **不是 24 位转 16 位写错了。** 加 `to_signed` 前后 rms 一模一样
  （10191.4 / 10191.4），原始值全都远小于 2^23，那一步是空操作。
- **不是直流偏置。** 加一阶高通去直流之后电平不动。
  （坑 4 那 1.2% 的直流是真的，但只有 1.2%，撑不起满量程。）
- **不是 `duplex_block` 的实现。** 它读 RX `0x00/0x04`、写 TX `0x08/0x0C`，
  和驱动自己的 `bypass()` 一致。

**剩下的差别只有一处**：`stream_begin` 会写 4 个 I2C 寄存器，
`capture_begin` 一个都不写。地址从板上 `audio_adau1761.h` 抄来，不用猜：

| 寄存器 | 地址 | 是什么 | `stream_begin` 写 | `stream_end`（静音）写 |
|---|---|---|---|---|
| R22 | 0x1C | 左播放混音控制 0 | 0x21 | 0x01 |
| R24 | 0x1E | 右播放混音控制 0 | 0x41 | 0x01 |
| R29 / R30 | 0x23 / 0x24 | 左/右耳机音量 | `(vol<<2)\|3` | 不动 |
| R23 / R25 | 0x1D / 0x1F | 左/右播放混音控制 1 | **不动** | 0x00 |
| R8 / R9 | 0x0E / 0x0F | 左/右输入音量 | 不动 | 不动 |

**10/13 一度以为查清了：环路的另一头就是耳机功放，而且环路增益只是刚刚超过 1。**
⚠️ **这条下面这一整段的结论，当天深夜被 probe9 推翻了 —— 见本节末尾「最后一档也测了」。**
下面留着，是因为"错在哪"比结论值钱。

先查手册把芯片内部排除掉：能录播直连的两条旁路在 PYNQ 的默认配置下都是 mute，
环不在 codec 内部。反倒查出**话筒那一路 PYNQ 自己就给了 +41 dB**
（R5/R7 的 LDBOOST = +20 dB，叠上 R8/R9 差分输入 = +21 dB）。

再把播放通路钉在坏状态、**一次只掐一处**、每组三遍、顺序交替：

| 掐哪一头 | 三遍结果（16 位域 rms） |
|---|---|
| **耳机功放整个关掉** R29/R30=0x02 | 195 / 173 / 179 —— 全静 |
| **话筒 PGA boost 降 20 dB** R5/R7=0x08 | 154 / 107 / 165 —— 全静 |
| 差分输入关掉 R8/R9=0x00 | 264 / 148 / 313 —— 全静 |
| 关录音混音器 R4/R6=0x00 | 65445 / 140 / 65197 —— 照样满 |
| 把 DAC 摘出播放混音 R22/R24=0x01 | 43037 / 5990 / 47287 —— 照样满 |
| 耳机音量 −57 dB（**功放还开着**） | 145 / **65430** / 150 —— 照样满 |
| 关噪声门 R14=0x00 | 45142 / 48477 / 45703 —— 更凶 |

1. **环路的另一头在耳机功放上。** 上面那条"把播放音量设成 0"不能算数：
   音量 0 对应的寄存器值是 `0x03` = **−57 dB，功放仍然使能**；芯片真正把功放
   关掉是它的默认值 `0x02`，那样三遍全静。所以那个测试只证明了"环路不靠输出
   幅度撑着"，没证明环路绕过耳机 —— **只要功放使能，送出去哪怕全是 0，环路也成立。**
2. **环路增益只是刚刚超过 1。** 两头各砍一刀都能断；而 −57 dB 那一档开始出现
   "三遍里满一次"的双稳态。10/09 量到健康值、10/10 量到满量程，不是"假线索"，
   是同一个状态在两半边之间翻；"同一个寄存器值结果会翻转"也是同一回事。
   → 10/13 深夜 `cap_probe7.py` 把这条钉实：`R5/R7=0x08`（只降 boost）这个状态，
   probe6 三遍全静、probe7 三遍里满一遍。**所以修法必须两级一起调**（见下）。

**⚠️ 10/13 深夜定案：修法不在话筒这一侧 —— "降话筒增益"那条路是错的。**

先把当时的推理留着（它错在哪，是这一条里最值钱的部分）：话筒那两级增益 PYNQ 默认
就给了 +41 dB —— `R5/R7`(0x0B/0x0D) `[4:3] LDBOOST` 0x10 = +20 dB，`R8/R9`(0x0E/0x0F)
`LDVOL` 0xB3 = +21 dB。`cap_probe7.py` 把这两级拆开扫过，boost 0 dB + 输入 +27 dB
那一档"三遍全静"（188 / 213 / 166）。

然后 `cap_probe8.py` 把**同一个寄存器状态**跑满 3 秒，它就现形了：

    fix_silence_v40（boost 0 / 输入 +27 / TX 送 0，音量 40）
      pass0    286    74    20  2120 29070 39740 44967 47011 47436 47900 ... 44211
      pass1  16963    59    18  1500 28713 42354 42090 47858 43960 50484 ... 42030

头三格确实"安静"（286 / 74 / 20）—— probe7 每步只跑 20 块 = **0.2 秒**，正好停在这
三格上。**第四格 2120、第五格 29070，一路贴到满量程。** 两遍都一样。
所以"三遍全静"不是状态好，是**观测窗口太短**。

同一轮探针还排掉两件事（方向比结果更值钱）：

| 条件（3 秒窗口） | 结果 |
|---|---|
| 话筒差分输入**整级 mute** `R8/R9=0x00` | 照样满（~44000） |
| 输出拧到 −57 dB（音量 0，**功放仍使能**） | 照样满（~48200） |
| TX 送 0（同一套寄存器） | 安静 → 约 0.8 秒爬到满 |
| TX 送 1 kHz | 第一格就已经满（42320） |

1. **不是从话筒那条链路进来的。** 把话筒输入整级关掉照样满 —— 话筒 PGA、差分输入
   音量、录音混音器，前面所有关于话筒增益的结论方向都错。
2. **不靠输出幅度撑着。** −57 dB 照样满（10/10 就量到过，这次复现）。
3. **输出信号不是必要条件，但是催化剂。** TX 送 0 也会满（慢些，~0.8 秒）；送信号
   就立刻满。
4. 顺带作废"双稳态"那条解释：不是"同一状态有时静有时满"，是**它一直在长**。

**最后一档也测了：`R29/R30 = 0x02`（耳机功放整个关掉），3 秒里照样爬满。**
`cap_probe9.py` 回读确认 `R29/R30 = 02 02`（功放**真关上了**，不是写失败），曲线和开着
功放的对照没有任何区别（pass0 1116 / 7080 → 第三格 42087 → 约 0.4 秒贴顶）；"功放关
**并且**话筒差分输入整级 mute"也是头两格 130 / 20、第三格起照样爬。**所以 probe6 那张表里
唯一全静的一档同样是 0.2 秒窗口的假象 —— 环路的两端都不在 codec 的模拟侧。**

只剩两条路：① **数字侧** —— `duplex_block` 读 RX 拿到的不是 ADC 的真实输出（读偏移不对，
读到会自己累加的寄存器 / FIFO 填充量 / 计数器），或者数字通路把输出又送回了输入；
② **自动增益（ALC）** 把本底慢慢推上来 —— "先停 1-3 格、再单调爬、最后稳住"这个形态最像它
（ADAU1761 的 ALC 控制寄存器是 R14-R16，PYNQ 开局写了 R14=0x20）。下一步 `cap_probe10.py`
把 probe2/probe3 那条"只收不放就安静"用 **≥3 秒窗口 + 逐格电平**重做，并把 ALC 寄存器全程钉住。

**实验记法（这条比结论本身重要）：** 探针的**观测窗口**是实验设计的一部分。这个故障
的增长时间常数是 ~0.7 秒，而 probe6/7 用的是 0.2 秒 —— 把"在长"读成了"静止"，还在那个
假象上选出了一个"修法"。**只要被测对象可能慢慢长起来，窗口就得比时间常数长几倍**；
并且**逐段打电平**（这次每 0.2 秒一格），全部信息都在"第几格开始跳"里面。

### 坑 7 收尾：连"只采不放"也照样爬（2026-10-13 深夜，`cap_probe10.py`）

这个坑的**地基**（"`stream_begin` 那 4 次 I2C 写是扳机"，来自 `cap_probe2` 的
seg1 安静 / seg2 满）从来没被长于 0.2 秒的窗口量过。补量之后地基也没了：

    条件（每格 0.2 秒，共 3 秒，两遍）
    cap_none   零 I2C 写、只 capture_block   889 271 79 44 24916 … 43285 / 92 41 22281 … 45691
    cap_i2c    同路径 + 4 次裸 i2c 写         63 31650 43947 …            / 49 21775 25279 …
    str_zero   stream_begin + duplex, TX 0     93 9459 33020 …             / 100 4086 30574 …

**六行全部在爬，包括一次 I2C 事务都不做的 `cap_none`** —— `capture_begin` +
`capture_block` 自己就爬到满。所以：

1. **那 4 次 I2C 写是清白的**；`cap_probe2` 的 seg1 同样是 0.2 秒窗口的假象。
2. **整条线上不存在"写某个值就能治好"的位置。** 前面 probe6/7/8/9 里那些
   "降增益 / 静音 / 关功放就静"的读数，败因不只是窗口短 —— 是方向本身没有解。
3. 起跳点跑动很大（第 1～5 格才开始爬），形态是**"停几格 → 单调爬 → 在 40000~53000
   停住"**，像一个带时间常数的自动过程，不像"某个寄存器接错"。
4. **这 3 秒里 R11–R16 读回来一字未变**（`11=00 12=00 13=00 14=20 15=00 16=00`）。
   能排掉"软件在改寄存器"；排不掉"芯片内部在自己动"（读回来的是控制寄存器，
   不是 ALC / 噪声门的内部动态增益）。注意 `R14=0x20` 就是 PYNQ 自己写的**噪声门
   NGEN=1、阈值 0**，这个配置本身就不正常，值得单独试一档。

还剩两条，都能用一个探针分清：

- **加载 overlay 之后什么都不配**（不调 `configure()` / `set_volume()` /
  `select_microphone()`）直接 `capture_begin` + `capture_block`：还爬 = 纯数字侧
  （读通路 / I2S / AXI）；不爬 = 是那套 codec 配置点着的。顺手**把右声道也打出来**
  （codec 内部问题该两个声道都中招）。
- **噪声门 `R14`**：写 0x00 再跑，并**在爬的过程中**读一次，看它是不是爬起来才动。

一个**没解释的线索**（别急着下结论，得单独设计探针）：每个 chunk 的**第一个块**读出来的
前 8 个采样都是安静的 —— 哪怕这个 chunk 的 20 块 rms 中位是 43000。现在的数据分不清是
"chunk 开头几拍读到旧值 / 0"还是"块内部前几个采样恰好小"，**要逐块打电平才分得清**。

**顺带：** `stream_reg_write` 是这次加进 `audio_stream.cpp` 的，**加完必须重编板上那份库**，
否则调用它的脚本报
`AttributeError: function/symbol 'stream_reg_write' not found in library`：

    sh /home/xilinx/jupyter_notebooks/build_audio_stream.sh

（脚本末尾会 `nm -D --defined-only` 把导出符号打出来，对着看一眼最省事。10/13
实测：重编之后符号表里出现 `00001528 T stream_reg_write`，调用它的脚本才跑得起来。）

**实时环路那边也贴顶，和探针的"全静"正好对不上：** 10/13 深夜把四行装进
`fir_live.py`、库重编之后，`sh run_live.sh 20` 跑下来进核电平中位 **18330** /
峰 **31671**。**现在知道原因了** —— 不是通路别处有问题，就是上面那条：那个寄存器
状态本来就会在 ~0.8 秒里爬到满，探针只是没看够时间。逐位自检 960000/960000 是过的，
通路本身没错。

探针要在**实时条件下**验，得同时满足三条（`cap_probe8.py` 就是这么做的）：寄存器
**读回来**（`stream_reg_write` 的返回值被丢掉了，写失败看不出来）+ TX 送 0 与送真音频
**各跑几秒** + 把话筒输入整个关掉看还满不满。三样都上了，结论才可信。

**排查这类问题的方法提醒**：同一个进程里连着做三段、每段只差一个动作
（不写 / 只写 I2C / 写 TX），比"改一次跑一次想一次"快得多，结论也硬。

## 实测：搬运是 CPU 干的，不是 FPGA

放一段 3 秒音频：

| 动作 | 墙钟 | CPU |
|---|---|---|
| 播放 | 2.96 s | 2.96 s |
| 录音 | 2.95 s | 2.95 s |

芯片是双核，所以「CPU ≈ 墙钟」= **一个核被 100% 占满**。

旁证：`audio_codec_ctrl_0` 在 `.hwh` 里只有一条 BUSINTERFACE —— `S_AXI`（从接口），
音频通路里没有任何 DMA。它自己没有去内存取数据的能力，数据只能由 CPU 写进去。

量 CPU 时间要注意 `resource.getrusage` 返回的是**进程累计值**，直接读会把加载 overlay
的时间一起算进来，得出过「墙钟 2.96 s / CPU 13.21 s」这种超过双核上限的数。必须前后差分。
