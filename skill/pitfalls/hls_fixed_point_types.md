# HLS 定点化（`ap_fixed`）：省不省，取决于「复用」还是「铺开」

实测：Vitis HLS 2020.2，目标 `xc7z020clg400-1`（PYNQ-Z2），10 ns 时钟（100 MHz），2026-09-29。

## 一、先看结论

**同一份源码、同一个器件、同一个工具版本，只换数据类型**，量出来是这张表：

| 设计点 | 浮点 | 定点（开着饱和） | 定点（关掉累加器饱和） |
|---|---|---|---|
| **乘法器限 5 个**（复用） | 327 拍 / 27 DSP / 9936 LUT | 253 拍 / 8 DSP / 19130 LUT | **252 拍 / 6 DSP / 8714 LUT** |
| **不限流**（全并行铺开） | 274 拍 / 345 DSP / 52953 LUT | 185 拍 / 67 DSP / 17552 LUT | **173 拍 / 67 DSP / 6502 LUT** |

两条能带走的：

1. **同一点上，定点都比浮点快、都比浮点省 DSP。** LUT 谁省，取决于**那层白花的饱和逻辑关没关**。
2. 关掉之后，**两个设计点上定点都省 LUT**（限流 5：8714 < 9936；不限流：6502 < 52953）。
   所以「定点更费 LUT」这句话**只在「限流 5 + 开着饱和」这一格成立**。

## 二、饱和：一笔被误判成「定点本身开销」的 LUT

第一次量的时候，看到定点版表达式层占 16730 LUT，就下了结论「这是 `ap_fixed` 逐次运算
的延位/饱和逻辑本身的成本，不是哪处写错了」。**这个归因是错的。**

把那 16730 LUT 按**运算类型**拆开（报告里的 Expression 明细表）：

| 运算 | 条数 | LUT | 占比 |
|---|---|---|---|
| `select` | 193 | **7024** | **43%** |
| `+` | 192 | 6525 | 40% |
| `lshr` / `shl` | 7 | 889 | 5% |
| `xor` / `and` | 356 | 750 | 4% |

`select` 是「1 位选 40 位」的二选一，**193 条就是饱和逻辑** ——
`AP_SAT` 在每个运算后面挂一个「超范围就钳住」的比较器 + 选择器。

**而累加器这个饱和一次都不会触发**：它是 65 个 16 位 × 18 位乘积之和，
最坏放大 65 倍，而 `ap_fixed<40,8>`（Q8.32）有 8 位整数位 = 256 倍余量。

所以把一个开关加上（`FIR_ACC_SAT=0`，`src/hls/fir_types.h`），只改累加器的溢出模式
`AP_SAT` → `AP_WRAP`：

| | 拍/采样 | DSP | LUT |
|---|---|---|---|
| 限流 5 + `AP_SAT` | 253 | 8 | 19130 |
| 限流 5 + `AP_WRAP` | **252** | **6** | **8714** |
| 不限流 + `AP_SAT` | 185 | 67 | 17552 |
| 不限流 + `AP_WRAP` | **173** | 67 | **6502** |

**LUT 掉到 45%（限流）和 37%（不限流），csim 输出与饱和版逐位相同**
（1000 点，最大差 0.0）—— 因为那些选择器本来就一次都不会触发。

**判据：不要看到「表达式层 LUT 很大」就归因于「定点运算本身贵」。
先按运算类型拆开看 —— 如果大头是 `select`，那是饱和，不是定点。**

⚠️ `data_t` 那一层的饱和**不能关**：它的输入是外部送进来的 float，真可能超出 [-1,1)，
绕回会变成一个反号的大数（爆音）。有「不可能溢出」这个前提的只有累加器。

## 三、机制：HLS 对两类算术的「复用」能力不一样

为什么限流这一格定点反而费 LUT，不限流那一格定点又大获全胜？看报告的 Expression / Instance 两栏：

| | 浮点 | 定点 |
|---|---|---|
| 算术放在哪 | **绑成可复用的运算实例**（`fadd` / `fmul`） | **留在表达式层**，每处各生成一份 |
| 限流指令的效果 | 真能复用：Instance LUT **50527 → 4885** | 压不动：Expression LUT **16201 → 16730**（几乎没动） |
| 全并行时每个乘法 | ~5 个 DSP | 1 个 DSP |

于是同一个「定点化」动作，在两个设计点上结论相反：

- **不限流**：两边的算术都得各铺一份。定点一个乘法只吃 1 个 DSP，浮点要吃 ~5 个
  → 定点 67 DSP / 17552 LUT 对浮点 345 DSP / 52953 LUT，**定点全胜**。
- **限流复用**：浮点有「实例复用」这条路可走，能把 LUT 从 50527 压到 4885；
  定点的算术 HLS 不给绑成实例，**限流只能压住乘法器个数（67→6），压不住围在它周围的对齐逻辑**
  → 这一格浮点的 LUT 反而更低。

**判据：问「定点省不省」之前，先问「这个设计点靠复用省面积吗」。**

## 四、外部对标：`Nunigan/FIR-FIlter_HLS`

GitHub 上能找到的最接近的开源对照（2022-07 ~ 2023-03）。
它一个仓库里放了 float 和 fixed 两份综合报告，是同一类对比：

| | 类型 | 拍（1024 采样） | DSP | LUT |
|---|---|---|---|---|
| `fir` | `float` | 1344 | 372 (29%) | 31017 (26%) |
| `fir_fixed` | `ap_fixed<32,1>` | 1057 | 162 (12%) | 14705 (12%) |

74 抽头、`#pragma HLS pipeline II=1`、抽头延迟线**完全展开**、器件 `xck26`（KRIA）。
**它的结论是定点全面更省，和本页「不限流」那一格方向一致。**

两个要注意的差别：
- 它的两版报告是**不同工具版本**出的（fixed 用 2022.1，float 用 2021.2），
  严格说不是受控对照，只能当方向性旁证。
- 它写 `ap_fixed<32,1>` 没指定溢出模式，用的是**默认 `AP_TRN` + `AP_WRAP`**
  （`ap_decl.h:201`）—— 也就是说它那一版**本来就没有饱和逻辑**，
  LUT 低有一部分是这个原因。

## 五、四个实际踩到的坑

### 1. 乘法两个操作数不能先转成宽类型再乘

```c
// ❌ 两边都被撑到 40 位 → HLS 综合出 33×33 的乘法器，一个 DSP 都用不上
y[p] += (acc_t)hist[k + p] * (acc_t)(coef_t)FIR_COEFFS[b][k + p];

// ✅ 在各自原始位宽上乘（16 × 18，正好塞进 DSP48 的 25×18 输入），乘完再转
acc_t prod = (acc_t)(hist[k + p] * FIR_COEFFS[b][k + p]);
y[p] += prod;
```

证据：错的那版是 65 个 `mul_33s_33s_65`、**总共只用了 3 个 DSP**；
改对之后变成 `mul_18s_16s_34`、DSP 涨到 68。

数值结果**完全一样**（csim 输出逐字节相同）—— 量化仍然发生在「接收」那一步。

### 2. `-type operation` 的名字分浮点和定点

| 名字 | 管的是 |
|---|---|
| `fmul` | **浮点**乘法器 |
| `mul` | **定点/整数**乘法器 |

从浮点版抄过来的 `set_directive_allocation ... fmul` 在定点版里
**一个字都不生效，而且不报错**。

证据：那一版 65 个乘法器一个没复用、DSP 只有 3 个（`v5_fixed`）；
换成 `mul` 之后 DSP 从 68 掉到 8（`v6_fixed_mul5`）。

**判据：换数据类型之后，所有按「运算类型」下的指令都要重新验一遍** ——
验的办法是看报告里的数变了没有（DSP 掉没掉），不是看命令报没报错。

### 3. 系数表本身必须是定点类型，不能存 `float` 现转

```c
// ❌ 以为 HLS 会在综合时折掉这个转换 —— 不会
static const float FIR_COEFFS[N_BANDS][N_TAPS] = { ... };
... (coef_t)FIR_COEFFS[b][k] ...

// ✅ 表本身就是定点类型
static const coef_t FIR_COEFFS[N_BANDS][N_TAPS] = { ... };
```

错的写法生成 **65 个 `fpext_32ns_64`**（float→double 扩位器），
系数表从 8 块 BRAM 涨到 **128 块**，LUT 炸到 **123550（232.2%，装不下）**。
改对之后降到 28309（53.2%）。

### 4. 定点下取绝对值不能写成三元表达式

```c
// ❌ 编译不过：operands to ?: have different types
acc_t a = (x < 0) ? -x : x;

// ✅ 拆成 if 赋值
acc_t a = x;
if (x < (acc_t)0) { a = -x; }
```

原因：定点下 `-x` 比 `x` **宽一位**，三元表达式要求两个分支类型相同。
拆成 `if` 之后，窄类型接收宽结果是允许的 —— **那正是量化发生的地方**。

## 六、位宽怎么选（配 `src/python/quantization_sweep.py`）

判据用 **SNR（dB）**，不用「误差小于多少」—— 音频里 SNR 才是行话，
而且它和位宽近似线性（每多 1 位约 +6 dB），一眼能看出还差几位。

实测（采样位宽 × 系数位宽）：

| 采样 | 系数 | SNR | 最大单点误差 |
|---|---|---|---|
| 12 | 18 | 54.6 dB | 1.056e-03 |
| 16 | 12 | 64.2 dB | 8.285e-04 |
| 16 | 16 | 76.7 dB | 1.070e-04 |
| **16** | **18** | **77.1 dB** | 6.017e-05 |
| 16 | 20 | 77.2 dB | 5.653e-05 |
| 20 | 18 | 98.4 dB | 9.563e-06 |
| 24 | 18 | 104.6 dB | 6.287e-06 |

- **系数位宽到 16 位以上不再是瓶颈**（16→18 只涨 0.4 dB），给 18 就够。
- **采样位宽是主要杠杆**（12→16 每多 1 位涨 5.6 dB）。
- 20→24 只剩 1.6 dB/位，说明那一段已经撞到别的噪声底了 ——
  **算斜率要用相邻两行比，不要拿最窄的一行直接除最宽的一行**（会得出虚高的「每位涨多少」）。

音频通行做法是 Q1.15（16 位），正好落在这张表上。

### 别把「分频段 SNR」当成「哪一段量化得差」

把总 SNR 拆成四个频段看，会看到很大的落差（16/18 那档：0-300 Hz 只有 70.3 dB，
600-1k 有 105.6 dB）。**但这不代表第 1 频段量化得差。** 验过：

| 输入 | 0-300 | 300-600 | 600-1k | 1k-8k |
|---|---|---|---|---|
| 真实语音 | 73.9 | 97.3 | 110.1 | 93.5 |
| 白噪声（等有效值） | 85.4 | 87.6 | 85.3 | 85.6 |
| 纯 288 Hz 正弦 | **105.1** | 98.5 | 86.6 | **65.8** |

白噪声下四段是平的，正弦下顺序**反过来**。所以这个分布由**测试信号的频谱**决定。
原因：四个滤波器重叠得很厉害（65 抽头在 48 kHz 下频率分辨率约 740 Hz，
而第 1、2 频段只隔 300 Hz），「某频段的 SNR」量的其实是「信号和误差各自落在哪」。

**判据：分频段指标只在滤波器分离度够高时才有意义。分离度不够时，它反映的是测试信号。**

### 两个会让数字失真的因素

1. **核的接口是 `float in / float out`**（测试台按文件读 float）。
   所以定点版比浮点版**多付两次 float↔定点转换**的逻辑，
   而真实系统里输入是 I2S 来的 int16，不会有这个转换。
   → 这一项让**定点版的 LUT 偏大**，也就是说本页「定点省 LUT」的幅度是**保守的**。
   要精确知道它值多少，得把接口换成 int16 再综合一次。
2. **采样位宽超过 24 位就没意义了**：输入本来就是 float32 送进来的（24 位尾数），
   所以 dw=24 那一行量到的是 float32 的底，不是 `ap_fixed` 的底。

## 七、这些数还是 HLS 的估算值

上面全部数字来自 `csynth_design`，是**综合估算**，不是布局布线后的实测。
要换成实测值需要跑 Vivado implementation（`export_design -flow impl`）。
在没跑之前，引用这些数时要说明它们是估算。
